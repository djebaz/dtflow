## Highlights

- Fix the Prepare background-hashing pause callback's missing argument; distinguish Close editor from Stop after current file without changing cancellation or admission rules. Source/static verification is separate from runtime acceptance (#437).

## Added

- Prepare reads a `.safetensors` LoRA's descriptive header metadata: two inline lines with bold values and muted labels (training facts including the declared base model, top tags) with a styled selected-training-metadata tooltip (one trigger phrase, emphasized values, and a separate section of up to 50 retained tags with counts) in the preview band and in Edit metadata (training facts only: not the file's own title, author, license, date or description, which are also not stored; the CLI JSON report is unchanged), a Trigger Words suggestion only from an explicit trigger declaration (a typed value or a non-empty saved value wins; an empty saved value counts as not set, so the file's trigger is offered again), and the same details in Edit metadata after conversion without the original file. The metadata is display-only and never affects family detection or conversion. The converter CLI gains `--metadata` (`-m`), which converts nothing and writes a JSON report of the descriptive metadata of a file, folder or glob.

## Changed

- Prepare automatically reuses verified current-version conversions, or a verified newer-version result when no current result is usable; older/unknown converter provenance converts again. Changed output receives a safe managed name without replacing old accepted assets, and that name is carried through Prepare and progress. The shipped damaged-output fallback is preserved (#403, PR #435; source/static checks only, runtime acceptance pending).

- CI selects the **Fast** offline suite when an ordinary PR becomes Ready for review, the **Full** suite when a PR from a `release`-named source branch becomes Ready, and **Full** again when a release PR is merged into `main`. Manual Fast/Full dispatch remains available; intermediate PR commits do not automatically rerun CI. Documentation-only PRs remain excluded by the workflow path filter.
- Developer UI screenshots use one **Preview** Action (`preview-ui.yml`) with change-selected, category, all-state and workflow-file modes; `preview:PART`/`preview:ALL` requests, automatic draft guards, shared GitHub artifacts/thumbnail comments and `preview_*` tooling names replace the separate render workflows. A native PR-path allowlist now prevents runs for documentation-only or unrelated YAML PRs, including label requests; explicit manual dispatch remains available. Preview capture and native acceptance remain separately evidenced (#421).
- Tooltips fade in quickly instead of sliding, app-wide (where the desktop allows UI effects). The Prepare rows align all their controls on one top edge.
- LoRA prompt hints now use an icon-only toggle beside each relevant prompt instead of a hover tooltip: Generate and Queues show a full-height, scrollable overlay in the right inspector below Images; Workflows shows it over the center canvas so node parameters remain accessible. A second click closes it. Removed redundant “File declarations · unverified” text from metadata tooltips and LoRA hover cards.

## Fixed

- Developer Preview's legacy LoRA details journey now completes the current metadata/editor approval path using offline synthetic transport, and requires confirmed assets and editor cleanup before continuing. Timeout diagnostics retain individual wait counts separately from affected captures, including waits without a later capture (#423; owner ALL at `52215e8` and revised-source targeted capture saved all selected states without timeout events; revised-head ALL and forced failure recovery remain unverified).
- Cloud Prepare distinguishes partial success from a wholly failed batch: mixed results use amber styling and a short toast, with concise per-file reasons in the side panel and full literal-text reasons in its tooltip and dev Logs. Definite failures with no successes retain red styling even while the editor stays open; a wholly failed closed-editor toast keeps full reasons. No retry, upload, receipt or uncertainty behavior changes (#419, #420). Review fixes are source-reviewed; edge-case Windows smoke remains pending.
- Cloud LoRA Prepare reports a full DT+ account as such: when `get_byom_urls` answers HTTP 200 with `data.storageLimitExceeded` and no existing reference or upload entry, Prepare stops with `cloud_storage_limit_exceeded` (resource limit; nothing uploaded, nothing retried) and the message names the account storage limit and, when DT+ reports it, the free space in MB. This replaces the misleading `no_matching_asset_entry` seen for that response. Other unmatched responses log bounded, sanitized response-shape evidence (counts, field names that look like schema names, types and matching booleans; never file lists, hashes, names, URLs or raw bodies). Free-space unit (bytes, shown in decimal MB) is inferred, not confirmed; reading and freeing DT+ storage is tracked separately (#436, PR #438, #440; owner Windows runs on two keys, CI pending).
- Connection > Custom LoRAs has a **DT+ storage…** action. Opening it sends one lookup for a made-up file (random hash per open, never stored; size just above the last reported free space, or 30 GiB when unknown) to the selected DT+ key and, only when DT+ answers that the storage limit is exceeded, shows a usage bar (accent below 80% used, warning from 80%, error from 90%), the free space of the total in GB (one decimal, bold values) and the stored files (name, size in MB; largest first by default, or by name) with tick boxes. DT+ gives no file list while the key has room for that size, and the panel says so. Nothing is uploaded; any upload URL DT+ returns is ignored. **Delete selected from DT+…** asks for a second click that names the file count and total size, then calls `/delete_uploaded_files` once with the chosen keys (no retry) and reads the list again once; a timeout or lost connection reports an unknown outcome and asks you to read again. After DT+ accepts, this key's local receipts whose remote reference matches a deleted file stop counting as confirmed, so Prepare uploads them again; other keys, retained copies, saved results and original files are untouched. Logs hold counts and field shapes only, never names, keys or hashes. Whether a LoRA still applies in generation on an over-limit key, and the free-space unit, remain unconfirmed (#440; source-reviewed, owner Windows smoke pending).
