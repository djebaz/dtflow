# Unreleased

Changes through 6.2.0 are consolidated in [DTFlow 6.2.0](v6.2.0.md); its published GitHub release body records final acceptance. This file tracks subsequent changes.

## Highlights

## Added

- The checkpoint catalogue now classifies **26 newly listed official DT+ Cloud filenames** that previously appeared as unclassified/other files: 17 with existing exact Draw Things community descriptions (Anima, FLUX.2, Ideogram 4, Krea 2, MiniMax H3 and Qwen Image 2.1), four MOSS Image variants confirmed in the upstream Draw Things built-in model registry, four FLUX.3 Klein/Base variants, and FastH3 OmniRef (MiniMax-H3-derived reference-to-video/audio). Existing Prime/Niche tiers are preserved for sibling models; `FLUX.3` and `MiniMax H3` are now recognized browsing groups. All 22 non-MOSS entries now have exact-file published Draw Things community descriptions after the upstream registry refresh (including `flux3_5b` for FLUX.3 and `minimax_h3` for FastH3); the four MOSS variants have official Draw Things built-in `moss_image` specifications. Exact versions are independently resolved from those metadata sources rather than broad browsing groups. FastH3 is recorded as reference-conditioned video/audio, but native DTFlow audio conditioning and provider generation have not been smoke-accepted. No invented model description, generation profile or compatibility fallback was added. Source-reviewed only; no Windows/provider execution performed.
- Connection > Custom LoRAs now shows the locally retained converted LoRA files and total disk usage. Select a copy and click **Remove selected** or press **Delete** to remove it immediately; only the managed local file is removed. There is no opt-in preference, deletion confirmation, or automatic expiry. Source-reviewed only; Windows acceptance pending.

- F10 opens the Logs workspace from any page and, pressed again, returns to the previous page (same as the Logs status button). It follows the other workspace function keys, never starts generation, and the button tooltip now names it. Source-reviewed only; no local tests or renders.
- Ctrl+Enter (including keypad Enter) launches the enabled action from anywhere in Generate, Workflows or the Queues composer—not just a focused prompt field. It uses the current Generate/Edit image, Run workflow, Run Script or Start now/Add to queue button, including Start/Start next for a selected queue, without bypassing disabled states, confirmations or popups; Setup, Continue, Pause, Resume and Save paused are excluded.
- Images slideshow: F6 or the Slideshow toggle beside the buffered count opens fullscreen Detail, looping through the filtered gallery at 0.5–8 seconds per image. The right-hand thumbnail carousel is replaced by a scrollable grey prompt/LoRA panel reusing the info card, and restored on exit. Immersive playback hides the first header and floats the pager plus top-right Forward/Backward toggle controls over the picture; both auto-hide after 2.5 seconds of inactivity. A numbered photo slider seeks on release, and F6 works across sibling shell focus. Rate and direction persist in the existing viewer preferences, never playback resume. Drag/wheel/held-arrow positioning pauses new image admission and commits only the final target, without old-result slider snapback. Controls become opaque on hover/focus; wheel over the position slider moves 10 photos per step, wheel over other controls adjusts rate, and Left/Right navigate manually. Images remain visible during decoding and use a short crossfade after successful loading. Playback stops on exit/navigation/shutdown and never starts generation. Source-reviewed only; native acceptance pending. See [plan](../plans/2026-11-08-images-slideshow.md).
- F5 opens Images from any workspace and enables Live + Follow with newest-first sorting, returning to the newest matching image without changing filters or the selected view. Repeating F5 resumes following; it never submits generation or starts a queue.
- Ctrl+Tab cycles Generate → Workflows → Queues → Images → Generate, entering at Generate from Connection or Logs without changing Images Live/Follow settings or submitting work.

## Changed

- Switching a saved/environment DT+ API key on Connection now automatically checks that connection and reloads its model/LoRA inventory through the existing refresh path. Previous-key availability is cleared immediately; rapid switches coalesce refreshes and stale asynchronous results are discarded. Manual Check and Reload Models remain available; no generation, uploads or billing operations are added. Source-reviewed; Windows/key-switch smoke pending.

- Generation-end gallery snapshot publication now reports a short-lived shared-cache lock miss as INFO rather than WARNING. The diagnostic event remains available; app-close or other publication failures still warn. No retry, image persistence or Images fallback behavior changed. Source-reviewed only; Windows contention/freshness acceptance remains open.
- DT+ LoRA resolution now emits one diagnostic summary per scoped operation, counting local reuse, verified matches, relinks, restores and failures without repeating per-LoRA success records. The Generate/Queue feedback overlay names restored LoRAs and reports affected names on resolution errors. Routine reuse/match summaries are verbose-only; relinking/restoration remains visible in normal logs. Safe pinned DT+ key attribution now accompanies key switches, relevant generation/Queue/provider diagnostics and asset summaries (opaque digest and optional four-character hint; never raw key material). Asset-row states once left at `intent` by per-key Prepare are now settled without overwriting other keys' confirmed receipts, and Logs gives Search less room to prevent filter overlap at narrow widths. Source-reviewed; owner-reported CI and native/DT+ acceptance require revalidation.
- Logs can select a bundled, source-generated Component before its first logged event; Event/characteristic discovery happens on explicit Refresh, not startup, Logs open, or Follow. Component/Event selectors are wider, Search is narrower, and filter settings are durable across restarts. The new persisted Compact toggle switches resident rows between one terminal-like line and the wrapped view without requerying logs.
- Queue polls skip full panel rendering only for unchanged *idle* results; active runs always redraw their Queue status/items so live progress remains visible even when persisted snapshots are unchanged. Returning from Logs to Queues now forces a fresh read/render, including completed History entries and the selected Queue detail. Thumbnails revalidate less frequently; Open in Images no longer blinks during background checks because the Images workspace validates the saved identity on click.

- Restyle the shared Images gallery link above ordinary right inspectors with selection-blue navigation states, a 14 px existing image icon and keyboard focus, rather than run-action accent blue. Keep navigation and responsive placement unchanged; align the web reference and document Qt styling differences. Source-reviewed only; no local tests or renders.

## Fixed

- Custom DT+ LoRAs now inspect converted Draw Things `.ckpt` tensor names and dimensions read-only to identify eight guarded architectures: Z-Image, Krea 2, MOSS Image, SD 1.x, SDXL Base, FLUX.1, FLUX.2 Klein 9B and Qwen Image 2.1. Detected file evidence (or explicit Unknown) is retained in existing asset receipts and shown across LoRA selectors, editors, Connection and diagnostics; known LoRA/checkpoint mismatches are refused before dispatch. Re-Prepare persists detection on reused content without a duplicate upload; old verified retained files can be inspected locally without a DT+ call. Owner-provided inspection first recognized **11/11 valid converted files** across seven architectures; the full **73-file** inventory initially recognized **59/61 readable LoRA-bearing CKPTs**. After a bounded Z-Image FFN/modulation-only signature fix, the owner reran the same 73-file scan and confirmed **60/61 (98.4%)** classified across all eight families. The remaining 11 Unknown CKPTs comprise six non-LoRA files, four with no visible SQLite tables (only one confirmed corrupt), and one two-tensor adapter with insufficient evidence for safe automatic classification. Both initial and final reports contain two original safetensors header summaries, which are not classified as converted CKPTs. This is **metadata-inspector smoke**, not acceptance of Prepare, native UI, DT+ upload, LoRA application or generation. **P1 follow-up:** newly detected LoRAs now store and dispatch exact Draw Things versions (`v1`, `sdxl_base_v0.9`, `flux1`, etc.) without an alias table. Shared preflight prefers published exact-file checkpoint metadata, then server Echo versions, and leaves broad catalogue-only checkpoints Unknown rather than guessing; an explicitly prepared LoRA with no detected version now fails clearly before cloud submission (also guarded in wire encoding) instead of inheriting the checkpoint version or disappearing from its override. Existing confirmed receipts and remote references are preserved; previously stored broad labels are not silently converted and require an explicit re-Prepare to refresh from file evidence. #373's editable architecture choice and batch Prepare editor remain separate follow-ups. After the canonical version-ID change, the owner reran the full 73-file inspector on 2026-11-11 (`report_head_all(5).json`): **60/61 readable LoRA-bearing CKPTs classified (98.4%)**, all eight architectures represented, and **zero legacy detector IDs**. The seven previously affected outputs now read `v1` (3), `sdxl_base_v0.9` (2) and `flux1` (2), with no loss of classification coverage. **Canonical-ID metadata smoke passed**. The owner subsequently confirmed that a LoRA visibly affected output during Generate (**user-reported generation-effect smoke passed**); this supports actual application for the tested case, not all eight architectures or all dispatch paths. An owner-provided diagnostic log then confirmed an actual **Z-Image Turbo q8p checkpoint + Krea 2 prepared LoRA** was submitted and generated: preflight had lost the checkpoint's exact architecture because its published per-file description and Echo metadata were absent. Shared preflight now falls back **only** to unambiguous bundled exact versions (`z_image`, `krea_2`, `moss_image`), emits WARNING diagnostics for mismatch or unknown compatibility, and rejects a confirmed mismatch before generation. Generate filters known-incompatible LoRA choices without silently removing selections; unclassified checkpoints with no reliable exact version keep their choices and unknown status. This correction has source review and an updated existing offline regression assertion, but awaits CI and owner Windows verification. Unknown-LoRA refusal and Queue/Workflow/Script end-to-end acceptance remain unverified; comparison settings and artifacts are not recorded here.

- LoRA runs after a relink (#361): before every cloud generation (Generate, queues, workflows, scripts) each LoRA receipt is swapped for the current receipt of its name: the one prepared on purpose last (explicit Prepare or a refresh), so preparing older bytes again is honoured, else the content first seen last, so a relink on another key cannot make old bytes look new. Prepare remembers the source file per LoRA name (path, size, modification time, edge digest, measured with the hash). If that file later holds different bytes, it is prepared again from it before the request is sent, with a real upload when DT+ asks for one: one shared measurement, copy and upload for all queue slots, run under the asset writer like a restore, cancelled when the last waiter leaves, and shown as "Restoring LoRA on DT+". If the refresh cannot finish, the request fails with the reason (nothing is sent with the old bytes) and the queue or workflow pauses so the remaining items wait (a script batch stops); only a DT+ limit error is remembered, for 15 minutes, every other cause is tried again on the next request, and a locked or missing source file is logged once. A receipt swap is recorded on the attempt (`receipts_updated`, old and new 8-character hashes). A DT+ "unknown error processing request" on a request with custom LoRAs checks the LoRAs like a not-found rejection (the check uploads nothing when DT+ already has the file); a check that itself fails is logged and the request gets its normal retry. Every runner allows one extra automatic retry for it, workflows count it in their allowance, and queues, workflows and script batches stop after 5 items in a row end that way for the same LoRA. `backend.loras_selected` is logged at INFO with prepared counts, unprepared counts split into listed and custom, short LoRA hashes and whether the override was sent, with the reason when not; file names are not logged. Queues no longer drop a LoRA whose receipt is newer than the one the composer remembered. Checked with a stub DT+ backend (changed file, five concurrent slots, copy under another name, preparing older bytes again, putting the old file back, a busy writer, a failed upload); awaits Djé's DT+ smoke; no tests run.
