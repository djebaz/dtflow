## Added

- Prepare storage recovery (#442): show the refused file's required size against reported key headroom, open DT+ storage without losing the editor, and unlock storage-refused rows for another explicit Prepare action. Advisory total input-size estimates and held-name/size ordering hints do not block Prepare or authorize transfers. Runtime acceptance is separate from source presence.

- Stored LoRAs at generation (#443): a generation that needs a LoRA the key no longer holds still re-prepares it from the kept local copy. When DT+ refuses for storage, Generate shows what is needed against the reported free space and offers DT+ storage, whose **Select to free space** ticks files this computer has no record of first, then the oldest recorded ones (DTFlow stores no per-generation use time, so this is a recency estimate); deleting still needs the second confirming click and nothing is deleted automatically. The Generate LoRA picker shows a small amber **not on key** pill on custom LoRAs the key is not known to hold (their tooltip says it is restored at generation and may use storage); held LoRAs carry no extra text, and none are hidden. The stored list read for the free-space line is compared with this key's receipts, so files deleted elsewhere (even the last one) are marked stale; this needs DT+'s list, which it gives only when the key is within the lookup size of its limit. The comparison always belongs to one key: switching keys while a read runs never applies one key's list to another, hints disappear until the new key is read, and the check no longer touches unrelated interrupted upload records. Re-attach on an already full key is not verified.

- Prepare reads a `.safetensors` LoRA's descriptive header metadata: two inline lines with bold values and muted labels (training facts including the declared base model, top tags) with a styled selected-training-metadata tooltip (one trigger phrase, emphasized values, and a separate section of up to 50 retained tags with counts) in the preview band and in Edit metadata (training facts only: not the file's own title, author, license, date or description, which are also not stored; the CLI JSON report is unchanged), a Trigger Words suggestion only from an explicit trigger declaration (a typed value or a non-empty saved value wins; an empty saved value counts as not set, so the file's trigger is offered again), and the same details in Edit metadata after conversion without the original file. The metadata is display-only and never affects family detection or conversion. The converter CLI gains `--metadata` (`-m`), which converts nothing and writes a JSON report of the descriptive metadata of a file, folder or glob.

- Connection shows the selected DT+ key's free space at the top of the DT+ credentials card, above the key selector, as a line ("2.6 GB of 21.5 GB") with the same segmented usage bar as the storage panel (accent below 80% used, warning from 80%, error from 90%). It is read after each successful connection check (a key switch triggers one) and after a delete, with one lookup for a made-up file; nothing is uploaded. The bar needs DT+ to report the total (it does when the key is near its limit); when DT+ gives no list the line says "more than N GB" with no bar. The credentials help paragraph is now a tooltip on the key selector. The DT+ storage panel marks files without a known matching managed copy as **Cloud only**, counts them in its status line, and offers **☑︎ Cloud only** to select visible matching rows; it sits with the search box and sort order above the list. Deleting still needs the second confirming click. Whether batching the Prepare lookups saves enough time is not measured (#444).

## Fixed

- Developer Preview's legacy LoRA details journey now completes the current metadata/editor approval path using offline synthetic transport, and requires confirmed assets and editor cleanup before continuing. Definite failures with no successes retain red styling even while the editor stays open; a wholly failed closed-editor toast keeps full reasons. No retry, upload, receipt or uncertainty behavior changes (#419, #420). Review fixes are source-reviewed; edge-case Windows smoke remains pending.
- Cloud LoRA Prepare reports a full DT+ account as such: when `get_byom_urls` answers HTTP 200 with `data.storageLimitExceeded` and no existing reference or upload entry, Prepare stops with `cloud_storage_limit_exceeded` (resource limit; nothing uploaded, nothing retried) and the message names the account storage limit and, when DT+ reports it, the free space in MB. This replaces the misleading `no_matching_asset_entry` seen for that response. Other unmatched responses log bounded, sanitized response-shape evidence (counts, field names that look like schema names, types and matching booleans; never file lists, hashes, names, URLs or raw bodies). Free-space unit (bytes, shown in decimal MB) is inferred, not confirmed; reading and freeing DT+ storage is tracked separately (#436, PR #438, #440; owner Windows runs on two keys, CI pending).
- Connection > Custom LoRAs has a **DT+ storage…** action. Opening it sends one lookup for a made-up file (random hash per open, never stored; size just above the last reported free space, or 30 GiB when unknown) to the selected DT+ key and, only when DT+ answers that the storage limit is exceeded, shows a usage bar (accent below 80% used, warning from 80%, error from 90%), the free space of the total in GB (one decimal, bold values) and the stored files (name, size in MB; largest first by default, or by name; the panel fills the central column, has a search box, rows styled like the LoRA picker, click anywhere on a row to tick it and Shift+click to tick a range) with tick boxes. DT+ gives no file list while the key has room for that size, and the panel says so. Nothing is uploaded; any upload URL DT+ returns is ignored. **Delete selected from DT+…** asks for a second click that names the file count and total size, then calls `/delete_uploaded_files` once with the chosen keys (no retry) and reads the list again once; a timeout or lost connection reports an unknown outcome and asks you to read again. After DT+ accepts, this key's local receipts whose remote reference matches a deleted file stop counting as confirmed, so Prepare uploads them again; other keys, retained copies, saved results and original files are untouched. Logs hold counts and field shapes only, never names, keys or hashes. Whether a LoRA still applies in generation on an over-limit key remains unconfirmed (#440; owner Windows runs confirmed the listing, delete and that free space is in bytes).
