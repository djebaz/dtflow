# Unreleased

Pending changes for the next DTFlow release.

## Added

- `tools/packaging/build_exe.py` stamped one-file build: records the full source commit and clean/dirty status in an ignored generated `dtflow/_buildinfo.py`, so a frozen executable reports its identity without Git, and names the artifact `dtflow-<version>-g<short-sha>-<platform>-<arch>.exe`. Source runs still report `unknown`. Verified offline by unit tests and one Linux PyInstaller build in the agent sandbox; no Windows build, generation or billable action was run.

- Durable queues and rolling dispatch (Phase 3B, queue half): `dtflow queue add|list|show|start|pause|resume|cancel|override|cap`. Queue, item, control and event tables join the attempts database (schema version 2; a release 0.1.0 database migrates atomically after a recoverable `attempts.pre-v2.sqlite3` copy, newer versions are refused). The dispatch owner is the process holding the state directory's ownership lock; other processes read and post controls only. Items reserve slots before any attempt exists, refill immediately on release, honour the queue and backend maximum, restore paused after restart, and keep `unknown` reservations blocking until an explicit recorded override. Verified offline only (3B-O1 to O5 and O10); no live queue run, generation or billable action was performed.

- Minimal Qt shell (Phase 4): `dtflow gui` launches a PySide6 Widgets window loaded from the canonical Designer file `src/dtflow/ui/forms/main_window.ui`. It selects fake/local/cloud, runs the bounded non-generative connection check through the shared composition root on a background asyncio thread (the GUI thread never awaits backend work) and shows healthy/auth-failed/unreachable/unknown status. API-key entry, replace and removal go through the shared `SavedCredentials` service backed by Windows Credential Manager via `keyring`; any other keyring backend is refused (no plaintext fallback), and `DRAWTHINGS_API_KEY` keeps precedence. The CLI stays environment-only and never imports Qt. The status bar shows the shared version and commit identity and the state path from the new `dtflow.paths`. New dependencies: PySide6-Essentials and keyring (runtime), pytest-qt (dev). Verified offline on Linux with the offscreen platform; the real Credential Manager boundary, a visible Windows launch and the packaged executable were not exercised, and no generation or billable action was run.

- Qt UX design foundation: a centralized Splitvids-inspired dark QSS now styles the source-run shell through semantic object names and dynamic status properties instead of inline status colors. Canonical `main_window.ui`, `generation_page.ui` and `queue_page.ui` sources define the three-area desktop information architecture, accessibility names and presentation seams under `src/dtflow/ui/forms/`. The native Windows frame follows Splitvids' DWM attribute 20/19 dark-title-bar path before and after first show. Only the existing Phase 4 connection shell is wired; the Phase 5 generation and queue forms are design sources, not usable workflows. The forms were mechanically converted with `pyside6-uic`; the owner confirmed the corrected proportions and native dark title bar in a visible Windows run. Tests and packaged-resource validation remain pending.

- Qt workspace preview composition: the shell now provides Connection, Generate, and Queues navigation and loads all three canonical Designer forms into one stacked workspace. Connection remains the only wired page; every interactive control on Generate and Queues is disabled and both pages are labelled preview-only. No generation, queue, inventory, configuration, LoRA, network, or persistence behavior was added.

- Cloud LoRA assets (Phase 3B, cloud half): `dtflow assets prepare|list|show|reconcile`; an independent durable asset registry `<state>/assets.sqlite3` (schema version 1, never reset); BYOM negotiation with streamed, hash-verified signed PUT (no DT+ authorization, redacted URLs); explicit `unknown` evidence for ambiguous transfers, failed receipt writes and interrupted operations, never re-uploaded automatically; metadata-only reconcile; in-process coalescing of identical concurrent prepares; `-z/--asset` binding of confirmed receipts into generation and queue requests with a metadata-only revalidation before every cloud dispatch. Verified offline with in-memory fixtures (3B-O6 to O9). No live upload, generation or billable action was run; `3-LG4` and custom cloud LoRA support claims remain pending.

- Desktop generation, first step (Phase 5A, PR 1): the Generate page now submits single txt2img requests on the fake, local and cloud backends. The CLI's generation orchestration moved into the Qt-independent `dtflow.services.session` (bounded open, inventory refresh, optional trigger prefixes, LoRA preflight, prepared-asset binding, generation, ordered close); `dtflow generate` is a thin caller of it and the desktop calls the same functions through the existing background runner. The page maps widget values through the shared resolver with a field-error table, shows real progress (coalesced before reaching the GUI thread), previews that never become results, saved output and metadata paths, `Outcome unknown` and `State is busy` wording, and a local "stop waiting" whose text comes from the recorded attempt evidence rather than the button press. Models come from an explicit inventory refresh. Configuration save/load uses the versioned credential-free contract; a loaded LoRA is displayed and round-trips but is not bound to a cloud receipt. LoRA selection, cloud asset actions and the Queues page remain disabled previews. Decision: the state ownership lock is held per generation, not per window. Verified offline on Linux (offscreen Qt, fake backend; the sandbox SQLite is older than the guard requires, so SQLite-backed tests ran with a sandbox-only override). No live desktop generation, upload or billable action was run; `5-LG1`/`5-LG2` remain pending and Windows visual review of the Generate states is pending.
