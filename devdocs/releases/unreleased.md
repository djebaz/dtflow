# Unreleased

Pending changes for the next DTFlow release.

## Changed

- GUI-first README now presents the application, implemented features, design principles, setup/desktop launch and repository navigation. Detailed desktop, CLI, queues/batch plans, testing and diagnostics move into linked `devdocs/guides/`; `devdocs/current_dev_status.md` provides a short initial-plan-aligned coding snapshot, separating implementation from acceptance. Repository instructions maintain this boundary. No runtime behavior or dependency changes.

- Connection, Generate and Queues share one persistent Designer shell, coordinated content stacks, scrolling rails, navigation and global responsive Inspector behavior. Existing workflow controllers and shared QSS are reused; no provider or dispatch policies change. Windows interactive and packaged acceptance remain unverified.

- Generate image-first workspace: rail-local header, parameters on the left, full-resolution fit/zoom/pan preview and canvas-local saved-output inspection. Shared theme tokens, native interaction states, expandable prompts, collapsible details, retained navigation on narrow windows and deterministic fake grid/model/ LoRA fixtures accompany a network-guarded twelve-state Qt renderer. See [the refinement plan](../plans/2026-10-05-preview-workspace.md) and the [design system](../../DESIGN.md) for extending this style to other tabs. The DTFlow monogram is the window and Windows build icon; the empty canvas can show a labeled illustrative portrait without enabling saved-output actions. No provider compatibility, Windows packaging or live inference acceptance is claimed.

- Review follow-ups to the Generate workspace and shell: the Queues "Cloud max" box now edits the shared cloud default when the cloud provider is chosen and no paused, running or blocked queue is selected (a finished queue no longer swallows the change), with a tooltip saying why it is fixed otherwise, the right Inspector rail is wide enough for the Generate inspector and scrolls instead of clipping, the Inspector's user choice survives crossing the narrow breakpoint, 100% in the image preview means true device pixels with crisp pixels at 100% and above, multiple saved outputs open the details chooser, the fake calibration grid renders much faster with identical bytes, the Queues item panel shows a short outputs summary (full paths in the tooltip) with an Open folder button instead of long paths, attempt ids show their first 8 characters (full id in the tooltip), cloud no longer displays a local host:port in the effective request or queue backend line, and a seed of 0 in the desktop Generate form (its default) now picks a random seed for each submission or queue, recorded in the effective request, metadata and resolution evidence (`seed.resolved`); saving a configuration, the LoRA check and the CLI keep 0 as a real seed. Source runs report source status `dev` with the newest package file's modification time as the revision (also stored as `source_modified` in build identity) instead of unknown/unknown, and the identity line reads `DTFlow <version> | revision <value> | source: <status>`; stamped packaged builds keep their commit and clean/dirty status. The illustrative lighthouse is now the fake provider's generated result (cropped to the requested aspect and resampled to exactly the requested size, so the shared output validation is unchanged; the `fake-grid` model still returns the calibration grid) and the separate sample button is gone. A fake-only Simulation group on Generate sets the outcome (succeeds, rejected, connection lost, terminal error, no image), a duration (stepped progress and Stop waiting work during it) and optional previews; queues created from the form record the same settings. A request the selected provider cannot serve (for example a model it does not offer) now says what is not offered instead of only `unsupported_request`; the code and its diagnostics are unchanged. The Generate form remembers its fields per provider (model, seed, size, steps, guidance, sampler, LoRAs and bound cloud receipts for fake, local and cloud separately, stored under `forms` in `last_session.json`, schema unchanged and an older file still loads for its provider); switching provider restores that provider's last values or defaults, while the prompt and negative prompt stay shared. Small label/error-message fixes. Verified offline (lint, format, imports, grid byte-for-byte comparison, layout size hints, fake backend with injected sleep); no Windows visual check, generation or billable action was run.

## Added

- `tools/packaging/build_exe.py` stamped one-file build: records the full source commit and clean/dirty status in an ignored generated `dtflow/_buildinfo.py`, so a frozen executable reports its identity without Git, and names the artifact `dtflow-<version>-g<short-sha>-<platform>-<arch>.exe`. Source runs still report `unknown`. Verified offline by unit tests and one Linux PyInstaller build in the agent sandbox; no Windows build, generation or billable action was run.

- Durable queues and rolling dispatch (Phase 3B, queue half): `dtflow queue add|list|show|start|pause|resume|cancel|override|cap`. Queue, item, control and event tables join the attempts database (schema version 2; a release 0.1.0 database migrates atomically after a recoverable `attempts.pre-v2.sqlite3` copy, newer versions are refused). The dispatch owner is the process holding the state directory's ownership lock; other processes read and post controls only. Items reserve slots before any attempt exists, refill immediately on release, honour the queue and backend maximum, restore paused after restart, and keep `unknown` reservations blocking until an explicit recorded override. Verified offline only (3B-O1 to O5 and O10); no live queue run, generation or billable action was performed.

- Minimal Qt shell (Phase 4): `dtflow gui` launches a PySide6 Widgets window loaded from the canonical Designer file `src/dtflow/ui/forms/main_window.ui`. It selects fake/local/cloud, runs the bounded non-generative connection check through the shared composition root on a background asyncio thread (the GUI thread never awaits backend work) and shows healthy/auth-failed/unreachable/unknown status. API-key entry, replace and removal go through the shared `SavedCredentials` service backed by Windows Credential Manager via `keyring`; any other keyring backend is refused (no plaintext fallback), and `DRAWTHINGS_API_KEY` keeps precedence. The CLI stays environment-only and never imports Qt. The status bar shows the shared version and commit identity and the state path from the new `dtflow.paths`. New dependencies: PySide6-Essentials and keyring (runtime), pytest-qt (dev). Verified offline on Linux with the offscreen platform; the real Credential Manager boundary, a visible Windows launch and the packaged executable were not exercised, and no generation or billable action was run.

- Qt UX design foundation: a centralized Splitvids-inspired dark QSS now styles the source-run shell through semantic object names and dynamic status properties instead of inline status colors. Canonical `main_window.ui`, `generation_page.ui` and `queue_page.ui` sources define the three-area desktop information architecture, accessibility names and presentation seams under `src/dtflow/ui/forms/`. The native Windows frame follows Splitvids' DWM attribute 20/19 dark-title-bar path before and after first show. Only the existing Phase 4 connection shell is wired; the Phase 5 generation and queue forms are design sources, not usable workflows. The forms were mechanically converted with `pyside6-uic`; the owner confirmed the corrected proportions and native dark title bar in a visible Windows run. Tests and packaged-resource validation remain pending.

- Qt workspace preview composition: the shell now provides Connection, Generate, and Queues navigation and loads all three canonical Designer forms into one stacked workspace. Connection remains the only wired page; every interactive control on Generate and Queues is disabled and both pages are labelled preview-only. No generation, queue, inventory, configuration, LoRA, network, or persistence behavior was added.

- Cloud LoRA assets (Phase 3B, cloud half): `dtflow assets prepare|list|show|reconcile`; an independent durable asset registry `<state>/assets.sqlite3` (schema version 1, never reset); BYOM negotiation with streamed, hash-verified signed PUT (no DT+ authorization, redacted URLs); explicit `unknown` evidence for ambiguous transfers, failed receipt writes and interrupted operations, never re-uploaded automatically; metadata-only reconcile; in-process coalescing of identical concurrent prepares; `-z/--asset` binding of confirmed receipts into generation and queue requests with a metadata-only revalidation before every cloud dispatch. Verified offline with in-memory fixtures (3B-O6 to O9). No live upload, generation or billable action was run; `3-LG4` and custom cloud LoRA support claims remain pending.

- Desktop generation, first step (Phase 5A, PR 1): the Generate page now submits single txt2img requests on the fake, local and cloud backends. The CLI's generation orchestration moved into the Qt-independent `dtflow.services.session` (bounded open, inventory refresh, optional trigger prefixes, LoRA preflight, prepared-asset binding, generation, ordered close); `dtflow generate` is a thin caller of it and the desktop calls the same functions through the existing background runner. The page maps widget values through the shared resolver with a field-error table, shows real progress (coalesced before reaching the GUI thread), previews that never become results, saved output and metadata paths, `Outcome unknown` and `State is busy` wording, and a local "stop waiting" whose text comes from the recorded attempt evidence rather than the button press. Models come from an explicit inventory refresh. Configuration save/load uses the versioned credential-free contract; a loaded LoRA is displayed and round-trips but is not bound to a cloud receipt. The Queues page remains a disabled preview. Decision: the state ownership lock is held per generation, not per window. Verified offline on Linux (offscreen Qt, fake backend; the sandbox SQLite is older than the guard requires, so SQLite-backed tests ran with a sandbox-only override). No live desktop generation, upload or billable action was run; `5-LG1`/`5-LG2` remain pending and Windows visual review of the Generate states is pending.

- Desktop LoRA selection and cloud assets, second step (Phase 5A, PR 2, same pull request): the Generate page adds LoRAs by exact identifier with an explicit weight (suggestions come from the last inventory refresh; any identifier can be typed), and an explicit Check refreshes inventory and renders the shared preflight diagnostics (architecture match/mismatch/unknown, availability, and the fixed "application unconfirmed" evidence) without any compatibility logic in Qt; a confirmed mismatch or absence still blocks dispatch in the shared service and the page shows its codes. An unchecked-by-default option prepends server trigger prefixes. For the cloud backend a local-registry asset list (stated not to be DT+ account inventory) offers Prepare (the only upload path, behind a confirmation that says bytes may be uploaded and that upload itself does not consume credits while a later generation may), Reconcile (metadata only) and Use for LoRA, which binds a confirmed receipt by identifier for the next generation (revalidated by the server before dispatch, never exported to a configuration). An interrupted or unconfirmed upload is shown as `Outcome unknown` with its evidence code and is not retried; writer-lock contention is shown as `Assets busy`. The CLI's `assets prepare|reconcile` now call the same `services/session.py` functions (`open_assets`, `prepare_asset`, `reconcile_asset`, `list_assets`, `check_loras`). Verified offline with the in-memory DT+ fixture and a scripted inventory (5A-O3, O5); no real upload, generation or billable action was run, and custom cloud LoRA support is not claimed (`3-LG4` pending).

- Phase 5B plan: [desktop queue controls](../plans/2026-10-04-phase-5b-desktop-queue.md) sequences the shared queue session extraction, the read-only queue surface, creation/control/concurrency/uncertainty wiring and the desktop gate, with its decisions and risks. Planning only; no queue behavior was added to the desktop.

- Desktop queue controls (Phase 5B): the queue orchestration moved out of the CLI into the Qt-independent `dtflow.services.queue_session` (`expand_items`, `create_queue`, `dispatch_queue`, `read_queue_views`, `post_queue_control`, `set_concurrency`) and `dtflow queue add|start` call it. The Queues page creates a paused queue from the Generate form, shows queues and items in stable order with in-place updates, and offers Start, Pause, Resume, Cancel and Override (controls always go through the shared posted-control path). Start makes the window the dispatch owner and holds the state lock for the run, so Generate is disabled meanwhile and the CLI reports a busy state; closing during dispatch asks first and the stop is recorded as unknown, never as a remote cancellation. Unknown reservations stay distinct, Resume cannot clear them, and Override is confirmed, recorded and never replays an attempt. One concurrency control sets the queue cap and, for cloud, the shared maximum (values above two are tinted; the hint states the memory-budget finding). The queue read view now lists pending controls so Start is offered when an override awaits an owner. Verified offline on Linux (offscreen Qt, fake backend; SQLite-backed tests used a sandbox-only override of the SQLite version guard). No live queue run, generation, upload or billable action was performed; Windows visual review and the packaged executable are unverified.

- Phase 6 plan: [queue planning and batch expansion](../plans/2026-10-04-phase-6-queue-planning.md) sequences a pure planner (seed, pair and cross modes, bounds, dry run), CLI and desktop entry points and its decisions. Planning only; no planner behavior was added.

- Queue planning, first step (Phase 6): the Qt-free `dtflow.services.planning` turns a base request plus varied dimensions into an ordered list of fully resolved requests. Modes are `seed` (the `queue add -k` rule, now the shared path behind `expand_items`; its items and `queue_position` evidence are unchanged), `pair` and `cross` (last dimension varies fastest); dimensions are prompt, model, seed (list or range), steps, guidance, sampler, size (width/height pairs) and per-LoRA weight. The cardinality is computed arithmetically and refused above 1000 before anything is enumerated; unequal pair lengths, empty or duplicate-valued dimensions, validator-rejected values and seed overflow fail before enqueueing. Items carry `plan.index`, `plan.mode`, `plan.seed` and `plan.dimension.*` evidence. `dtflow queue add` gains `-r/--plan FILE` (a versioned, credential-free `dtflow.queue-plan` document; mutually exclusive with `-k`) and `-u/--dry` (prints the item table and count as JSON and creates nothing). Decision: in pair and cross batches the base seed stays fixed unless a seed dimension is listed or the plan says `"seed": "increment"`, unlike `queue add -k`. The plan's proposed `-l/--plan` clashed with the existing `-l/--lora`, so the canonical pair is `-r/--plan`. Verified offline (6-O1 to 6-O4, CLI dry run); no live queue run, generation, upload or billable action was performed.

- Queue planning, second step (Phase 6, same pull request): the Queues page gains a checkable Plan batch area (Cross or Pair; prompts one per line, other dimensions `;`-separated, LoRA weights per line, an optional per-item seed increment), a live item count that states the 1000-item refusal, and a Dry run table. `ui/planning_presenter.py` only splits text and maps planner errors to the owning field; Create calls the shared `describe_plan`/`expand_plan` and `create_queue`, so a rejected plan creates nothing and the persisted items equal the table. The count box remains the seed-sweep shortcut. Verified offline with offscreen Qt (SQLite-backed tests used a sandbox-only override of the SQLite version guard); Windows visual review of the Plan area and dry-run table and the packaged executable are unverified, and no live queue run, generation, upload or billable action was performed.

## Changed

- Desktop startup memory, inventory cache and GUI logging: the window remembers the last provider, local endpoint and Generate form (prompt, negative prompt, model, LoRAs and weights, seed, size, steps, guidance, sampler) in `<state>/last_session.json` (versioned, credential-free, durable; written on submit, after a successful connection check and on quit; an unreadable or newer file remembers nothing and is not rewritten). `dtflow models` and Refresh inventory now write the raw `local_inventory.json` / `cloud_inventory.json` cache (`cache_version` 2; endpoint match; cloud also source plus salted hash of the key) and the desktop uses it only to prefill the model and LoRA lists, marked cached; generation still refreshes live. `-nc/--no-cache` now bypasses it and is accepted by `dtflow gui`. The Generate model list uses the same `eligible_model_ids` rule as the request gate (moved to `core.models`), so a server that sends no model metadata, such as the cloud, now lists its files instead of an empty list; the list is cleared when the provider changes. The GUI now logs actions and results as one short line each (provider and endpoint changes, connection checks, inventory refresh counts, cache hit/miss/write, generate submit and outcome, key save/remove, session save/restore) and, with `-x`, field-error codes, a sanitized request summary without prompt text, and page state changes; inventory and settings JSON are never logged. The Generate page now snaps width and height to the nearest multiple of 64 (halves round up, within 128..2048) instead of rejecting them: the boxes show the adjusted value, the status says what changed, and the recorded request uses it; the CLI and loaded configurations stay strict. A portrait result is no longer clipped top and bottom: the preview frame grows to the scaled image (it was held at 210 px, so the label was 192 px tall for a 360 px image in an offscreen 1366x800 check). Verified offline on Linux (offscreen Qt, fake backend and fixtures; SQLite-backed tests used a sandbox-only override of the SQLite version guard). Not verified: Windows, a real local or cloud server, and the saved-credential path. No generation, upload or billable action was run.


- Desktop design fixes from the round 1 and round 2 critiques (styling and UX only): Generate parameters use compact fixed-width fields, saved results offer Open folder and Copy path, the Model field shows a hint, the evidence box is taller with the attempt line above it, and Remove key is enabled only when a key may exist and asks first; Generate and Queues scroll instead of crushing their inputs at 1366×800; the Queues header stays one line; the DESKTOP PREVIEW badge, "Planned for Phase 5A/5B" box and internal scope text are removed; tables get dark alternate rows, one navy selection colour, no duplicate row header and right-aligned numbers; checkboxes have visible indicators; spin box values are no longer left disabled by the preview-control pass. The Connection result resets when the provider or endpoint changes; a new queue offers Start rather than Resume; a dispatch run reports the outcome that happened; an item is selected after create and finish; the Plan form shows one error beside the plan, has format placeholders and labels Create with the planned count. Times are local to the second, a saved generation states what was saved with paths listed once, and the state folder moved to About. Verified offline with offscreen Qt on Linux; Windows visual review is pending and no generation, upload or billable action was run.

## Fixed
