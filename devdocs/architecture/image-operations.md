# Image-operation preparation

## Current slice and boundaries

Draft PR #64 provides a source-present headless single-shot path for img2img and mask-file inpaint: immutable preparation, request v2/DB v3, durable input commit/restore, exact-scope permit gates, provider wire configuration, and separate raw/final saving. No permit ships and default construction remains txt2img-only. No runtime/checkpoint compatibility is established, no inference has run, and no production ONNX dependency or editor wiring is introduced here. The owner's UX work is separate.

The [implementation plan](../plans/2026-10-10-smart-mask-inpainting.md) requires separately authorized exact-checkpoint local/cloud acceptance before editor/analysis promotion. Source presence is not acceptance.

## Preparation contract (source implementation)

- File reads snapshot at most 64 MiB actual bytes. Decode rejects images over 16 million pixels and animated/multiframe inputs; MPO explicitly uses primary frame 0.
- EXIF orientation is applied before coordinates/dimension comparison. Source is RGB with transparency composited on white. Canonical PNG snapshots contain fresh pixels only, without inherited EXIF/ICC, prompts, paths or provider references. Encoded bytes are excluded from dataclass repr.
- Mask luminance strictly above 127 selects pixels; alpha is ignored. Unsigned 16-bit integer masks are scaled over the full 0..65535 range using floor(value/257) before thresholding, never clipped or per-image contrast-stretched. Out-of-range integer and floating-point masks are refused. Source and mask must have identical EXIF-oriented dimensions. Do not resize an arbitrary mismatched mask silently.
- Masks are binary 0/255: white edits, black preserves. Empty mask after threshold/adjustments is rejected. Grow/shrink is an integer in -64..64 source pixels using repeated 3x3 Max/Min filters and a black source boundary, equivalent to square-radius adjustment; not anatomical expansion. The -64..64 range is an absolute schema bound, not the usable range at every image size. Before padding/filtering, (source width + 2*radius)*(source height + 2*radius)*radius must not exceed 32 million pixel-passes; the effective range therefore shrinks with source size. Do not silently clamp or raise the budget to advertise full-range operation. Larger requests refuse with a reduce-grow/source-size explanation.
- Feather is finite in 0..64 source pixels. Gaussian softness is multiplied by the adjusted binary support, so the blend alpha is exactly zero outside the selected region. Defaults are grow 0 and feather 0.
- Target dimensions remain multiples of 64 in 128..2048. Source/mask share centered aspect-preserving fitting with rounded integer dimensions. Source uses LANCZOS, binary mask nearest-neighbour; image padding is white and mask padding unselected. Preparation and restored-snapshot validation refuse a mask retaining less than 75% of its area normalized to the exact fitted grid. This global area guard does not guarantee stroke connectivity or retention of every small component.
- Immutable preparation includes original-grid source, adjusted source mask/blend alpha, fitted image/mask and exact fit crop. SHA-256 identifies canonical PNG bytes, not the untouched external file. Preparation schema v1 is independent of future request/attempt/DB versions.
- `composite_image` checks prepared content digests/grids, generated target dimensions and binary source-mask support. It unpads/resizes the raw result to source dimensions and blends against the prepared source. Outside alpha support the source RGB pixels are retained. Preservation refers only to the normalized 8-bit prepared RGB source, not original-file pixels, transparency, high-bit-depth values or color-managed appearance. No ICC transform is applied and profiles are not retained. The image-operation output metadata records this normalization policy, algorithm and outside-mask reference explicitly; it does not infer the original mode/profile. This is not a promise of identical external compressed file bytes or a proof of backend success. The caller must retain raw output separately.
- CPU-intensive decode/filter/encode/composite must run on a worker. These helpers do not own cancellation, durable success or provider protocols. The morphology work budget is not a latency guarantee; target-machine performance is unverified.

## Durable snapshots and tensor preparation (source implementation)

- Worker-facing `services/image_inputs.snapshot_image_inputs(state, attempt_id, prepared, preserve_outside=True)` validates pixels and exclusively commits a prepared set. It does not create an attempt, authorize generation or submit work. The generation orchestrator supplies a fresh lowercase UUID hex attempt ID while holding durable ownership. Img2img records preservation as false; inpainting defaults to true.
- `ImageInputSnapshot` schema v1 is independent of the execution database. It is JSON-safe: fixed content identities, byte counts, dimensions, channels, fit/grow/feather and preservation only. No encoded bytes or external source paths. Strict decoding requires every top-level field and rejects unknown fields.
- `persistence/image_inputs` writes only `<state>/inputs/<attempt-id>/source.png`, `image.png` and, for inpainting, `source_mask.png`, `mask.png`, `blend_mask.png`. `manifest.json` is the final commit marker. Existing sets, including incomplete sets, cannot be overwritten or reused. Failed partial directories remain evidence; no repair, deletion or dispatch replay occurs.
- Reads require the expected immutable snapshot, compare the committed manifest and verify each actual byte count/SHA-256. Per-file reads are bounded at 64 MiB, combined prepared PNGs at 128 MiB, and manifest at 16 KiB. Existing redirected ancestors/directories/files, Windows reparse points and non-regular files are refused. The strict ancestor check includes junctions above the state directory, including a redirected user home; choose a non-redirected state location rather than bypassing it. These are application-owned paths, not a security claim against a hostile process racing filesystem replacement.
- Content files and the marker are fsynced; POSIX additionally fsyncs the containing directory. Windows power-loss durability and concurrent filesystem behavior remain owner acceptance work. The standalone input helper never performs execution DB migration; the owned store handles it separately.
- `restore_image_inputs` verifies content mode/grid, canonical centered fit, fitted source pixels, exact nearest-neighbour mask/padding, nonempty binary support and inward feather pixels. Canonical PNGs with inherited metadata are rejected. Decode/filter/check work must stay on a worker with an orchestration resource reservation; no worker scheduling is introduced here.
- Provider-local `backends/drawthings/image_inputs.encode_image_inputs(prepared, limits)` produces fitted RGB float16 [-1,1] and optional single-plane uint8 0/2 mask tensors using the locked SDK. Header dtype/layout and exact size are checked; every mask payload byte is independently compared to prepared binary pixels. Preflight bounds tensor/content sizes before encoding. No provider type or image library enters core or Qt.
- Its immutable result has 32-byte SHA-256 tensor references plus the actual tensors in `contents`, with pixel payloads excluded from repr. PNG snapshot hashes and tensor hashes are distinct. This helper does not build/authorize/send a generation request or establish deployed compatibility. The existing txt2img builder is unchanged.
- Upstream reference: [service contract](https://raw.githubusercontent.com/drawthingsai/draw-things-comfyui/main/resources/imageService.proto), [server content-reference unwrapping](https://github.com/drawthingsai/draw-things-community/blob/main/Libraries/GRPC/Server/Sources/ImageGenerationServiceImpl.swift), and [mask 0/2 semantics](https://github.com/drawthingsai/draw-things-comfyui/blob/main/src/image_handlers.py). The installed drawthings-py 0.4.0 source supplies the matching encoder. Source inspection is not runtime acceptance.

## Single-shot session and ownership (source implementation)

- `services/session.generate_image_files_once(selection, state, base_request, source, *, permit, mask=None, ...)` is an explicit prepare-and-submit action. It runs `prepare_image_files` on a worker and then uses `generate_image_once`. It is not a preview API: invocation requests real generation and cloud may consume credits/send source and mask off-machine.
- `generate_image_once(selection, state, base_request, prepared_inputs, *, permit, strength=0.75, preserve_outside=True, allow_image_probe=False, ...)` accepts prepared immutable inputs. The base must be single-output txt2img settings with target dimensions already matching preparation. Mask presence chooses inpaint, otherwise img2img. No silent dimension changes. Each call gets a fresh request ID and fresh owning attempt; the returned request references that actual attempt, not the temporary preparation identity.
- The required `ImageOperationPermit` identifies exact backend, endpoint, checkpoint, operation and path-free evidence ID. `owner_probe` additionally requires `allow_image_probe=True` for that invocation. No compatibility is inferred from inventory or a model family; no permit is bundled, generated automatically or persisted as proof. Caller-supplied evidence still needs owner review.
- Cloud also requires `core/model_profiles.exact_model_description_digest(model_id)` matching a published exact-file description. The canonical digest includes all description fields; no derived/family fallback is accepted for image operations. Missing/mismatched evidence refuses. Composition preflights permits and concurrency before allocating the cloud auth client; backend construction repeats validation.
- `open_session(..., image_permits=(permit,), allow_image_probe=...)` supplies a state-bound synchronous managed-input loader to composition/backend and `input_state` to `GenerationService`. Image sessions require durable ownership. The adapter restores/validates committed snapshots on a worker, not Qt or the orchestration loop.
- `run_generation(..., prepared_inputs=...)` checks exact permit scope and prepared/request identity before inventory/auth refresh. Generation commits attempt-owned source/mask/settings before the GenerateImage submission path; external files are never reread. Preparation cancellation settles its worker before returning without dispatch. Existing service uncertainty, timeout, shutdown and no-retry semantics remain authoritative.
- Provider configuration verifies requested strength, mask blur/outset zero and provider preserve-original false. Tensor layout/polarity/contents checks run before cloud authorization. Source checks do not prove deployed checkpoint behavior.
- Dedicated saving retains untouched `outputs/<attempt-id>/raw-1.png`; only `final-1.png` and metadata enter the committed artifact ledger. Optional preserve-outside produces a source-sized normalized-source composite; OFF uses a raw provider copy. Raw/final have distinct IDs with a raw-evidence link. Aggregate raw-plus-final encoded limits apply in both modes; failures retain partial/raw evidence without publishing success or retrying generation.
- The session returns registered final bytes for display and the effective attempt-bound request. Gallery/export/recycle operate on registered finals only. Inputs, masks and raw evidence are durable, not cache; no cleanup scans/registers them automatically. Raw provider inspection UI and image-operation portable export acceptance remain pending.
- Generic `generate_once`, CLI/config, queues, planners and batches remain txt2img-only. Dedicated APIs do not broaden those contracts. No default verified permits are introduced; the dedicated probe harness below is the only CLI image-operation entry.

## Manual editor support helpers (source-only)

- services/session.image_operation_status inspects supplied exact-scope permits and bundled description digests without backend/client/state open, credential resolution, writes, network or inference. core/image_operations.inspect_image_operation is the pure status/reason function. No permit registry ships; probe status is not consent and dispatch still revalidates. Owner-confirmed is an evidence label, not compatible or installed: status does not check checkpoint availability. Keep selection filtered by active inventory independently of permits.
- core/image_inputs.suggest_generation_size derives a bounded 64-multiple target from oriented source dimensions and an explicitly chosen max_edge, with no automatic request mutation or no-upscaling guarantee. Canonical fitting may upscale small sources to the minimum box; padding depends on aspect mismatch (64x64 -> 128x128 fills it). Display recorded ImageFit dimensions/padding. max_mask_grow reports the exact source-size pixel-pass radius limit shared with preparation.
- services/image_preparation.mask_coverage measures supplied binary pixels without PNG decoding. preview_mask_pixels works only on an already downsampled binary grid <=512x512, scaled grow/feather and approximate thumbnail coverage; no full-source RGB fit. Its approximate flag and note must be shown: grow below about half a thumbnail pixel rounds to zero and may not appear. It is deliberately approximate, not provider evidence or a performance benchmark. Caller runs it on a worker and owns cancellation/stale-result handling.
- load_mask_bytes/file return fresh, unadjusted source-grid binary masks. save_mask_file (or save_mask_pixels_file for an editor binary buffer) exclusively writes a new PNG, fsyncs and never overwrites or makes an attempt; failed writes may retain partial files. Save the editor base mask, not the already-grown prepared.source_mask. These helpers do not provide a Qt file picker or edit history.
- The [UX alignment addendum](../plans/2026-10-10-inpaint-editor-ux.md#backend-alignment-addendum-2026-10-10-source-only-supersedes-conflicting-demo-wording) documents normalized-source preservation, OFF result fit/tint, signed size-budgeted grow, single-shot-only actions and one-invocation inline probe consent. No mockup, Qt or ONNX implementation is added here.

Use worker-facing `prepare_image_bytes` / `prepare_image_files` for offline previews, not a generation entry. `PreparedImageInputs.fit` gives the immutable source-to-target transform; edits remain in the original oriented source grid. Helpers return no Qt/Pillow/provider objects. Source import, Edit, mask selection, preview and save-mask must not dispatch or create attempts.

Only an explicit Generate action may call the dedicated single-shot entry with a reviewed permit and credit/off-machine disclosure. Default permit-free construction refuses image operations. UI/raw-evidence presentation and ONNX remain separate work.

## Request and execution schema (source implementation)

- `ResolvedGenerationRequest` schema v2 adds `strength` and optional immutable `image_inputs`. Txt2img requires strength 1 and no inputs; img2img/inpaint require target-matching snapshot references and exactly one output. Inpaint requires all masks; img2img refuses them. Strength is finite 0..1; the dedicated image-operation entry chooses the approved 0.75 default rather than inheriting txt2img's 1.
- `core/request_records` is the authoritative nested decoder. Explicit v2 records require operation/strength/input fields. Historical v1 or missing-version records are accepted only as txt2img, upgraded with no image inputs and strength 1. Unknown fields/newer schemas, malformed nested records and ambiguous legacy image operations are refused, not silently coerced or discarded. Request expressibility does not imply a backend capability.
- `SQLiteAttempts` writer schema v3 accepts upgrades from DB v1/v2. Before migration, SQLite's consistent backup writes a fresh `attempts.pre-v3-from-v<old>-<uuid>.sqlite3` beside the active DB. Each attempt gets its own backup rather than trusting a stale/partial file from a failed migration. No output/input files are copied or modified.
- One `BEGIN IMMEDIATE` transaction creates missing queue tables, upgrades requests in stable primary-key batches of at most 128, sets user_version 3, and performs existing ownership reconciliation. Malformed requests/schema errors roll back the transaction and preserve the original version/records. Backups from interrupted/failed migration remain evidence. New image attempts must reference their own attempt ID; persistence refuses cross-attempt binding.
- Migration does not change request/attempt/item identities, output paths, queue order, failure evidence or remote outcomes. Existing reconciliation still pauses running queues, preserves unknown reservations, maps possibly-submitted attempts to unknown, interrupted saves to save_failed, and never makes ambiguous work eligible for automatic replay. Older writers refuse schema 3; do not downgrade an active DB in place. Schema 4 (queue up next, #125) reuses the same backup-then-migrate transaction, now named `attempts.pre-v4-from-v<old>-<uuid>.sqlite3`. Recovery from a reviewed backup is owner-controlled, never an automatic retry/replay path.
- Read-only gallery accepts DB v1/v2/v3 without migration; read-only queue listing accepts v2/v3. Queue controls/deletion require current writer schema. Saved metadata readers accept v1/v2; existing metadata files remain untouched. New txt2img saves record metadata v2 and the explicit request v2.
- Queue creation accepts a non-txt2img request only from the Queues tab's staged-edit path (`check_queueable`): a snapshot reference, one output and per-item `owner_probe` consent evidence (`image_permit_evidence`, `image_permit_status`); every other image-operation request is rejected. Staged inputs live under their own id in `<state>/inputs/`; the dispatcher restores them, rebuilds the owner-probe permit from the recorded consent and the service re-snapshots them under the minted attempt. Planners accept image-operation bases only with `edit=True` (adds the `strength` dimension; `size` refused). The rest of this paragraph describes the unchanged txt2img-only paths (CLI, plan files). Claim transactions fail and audit invalid pending requests without reserving/submitting them, retaining original JSON and continuing to the next item in bounded order. Existing attempt links or identifiable request/attempt associations instead fail closed for owner inspection, preserving uncertainty. Queue inspection tolerates malformed request JSON without inventing missing IDs/seeds. Planners otherwise reject image-operation bases. Generic config/CLI resolution, metadata import and config export refuse image operations rather than strip inputs/strength and dispatch txt2img. No image flags or CLI image dispatch are added.
- The generic artifact saver refuses image operations; the dedicated saver owns raw/final evidence. Default adapters advertise txt2img only; explicit permit-scoped construction enables just those operations. The shared generate-once entry refuses images before opening backend/state, run-generation refuses unsupported operations before inventory/auth refresh, and the adapter refuses them before model-spec/auth preparation. The normal orchestration capability check also refuses image dispatch before attempt creation. Source/request encoding helpers are not an alternate dispatch entry point.
- Existing authoritative migration test fixture/assertions are adapted to valid historical request JSON, DB v3 and the new backup naming. No tests added or run. V1/v2 upgrade, rollback, queue uncertainty, read-only compatibility and metadata reuse acceptance remain required owner/CI work.
