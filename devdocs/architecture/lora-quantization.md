# Experimental LoRA q8p storage (#353)

This is a source CLI experiment, not supported Prepare behavior or a production quantization decision. It transforms an already converted F16 Draw Things CKPT into a separate file. Safetensors conversion, retained-store authority, receipt identity, cloud restoration, upload consent and generation remain unchanged.

## Boundaries

- `lora_cli.py` owns arguments/presentation; `services/lora_quantization.py` owns closed SQLite input, identity, inspection, comparison and no-clobber publication; `services/lora_q8p_codec.py` owns tensor codecs. None opens application state, a credential provider or a generation backend.
- Inspect/compare accept paired LoRA up/down tensors with supported CPU F16 storage: raw, q8p or ezm7. They validate finite decoded values, not generation quality. Names, dimensions and format must match for comparison; encoded file bytes need not match.
- The initial writer requires `-e/--experimental`, raw F16 and the existing structural detector's Krea 2, Z Image or SDXL Base signature. Unknown/partial adapters and other families fail closed; a shared codec is not all-family acceptance.
- Inputs must be closed standalone SQLite files with one indexed `tensors` table and no WAL/SHM/journal. Caps are 8 GiB/file, 20,000 tensors and 64 MiB decoded bytes/tensor. Metadata projection and per-tensor payload reads are bounded; numerical statistics use small chunks. Clustering uses independent blocks of at most 16,384 values, with the queue spanning tensor boundaries rather than draining each tensor first. `-j/--jobs 0` auto-detects available CPUs; 1 stays serial in-process, another positive count overrides. Windows caps auto-selection at 61 and rejects larger explicit counts. A reusable spawned pool admits at most one outstanding block per worker and returns results in source order. Whole small tensors that need ezm7/raw fallback are single tasks. Workers receive only arrays and return encoded bytes; SQLite, progress, validation and publication remain parent-owned. Parent values/assembly buffers stay with admitted tensors until writing, so memory scales with worker count as well as the tensor cap. This is not a measured memory/performance guarantee.
- Hold a read transaction, fingerprint the file and rehash it before accepting results/publication. Never substitute stat-only identity. The output is a unique same-directory temporary SQLite file, committed, reopened/decoded, hashed and fsynced before an exclusive hard-link publication. Existing targets are never overwritten; filesystems without hard-link support fail explicitly. Output directories must exist and cannot redirect; `.dtflow` and `lora_files` paths are refused. No automatic report directory, conversion reuse or state migration is added.
- On cancellation/failure, close SQLite and remove only this invocation's temporary file/journal. A published output is never deleted by cleanup. Best-effort cleanup failures emit a fixed diagnostic; after interruption the owner checks the requested destination before retrying. This is not the managed Prepare staging protocol.

## Codec and numerical provenance

Research pins: Draw Things `4e986724c6c65cdc8b9eeb8a2d2f4775c698e007`, s4nnc `50d060dba795a6d9ca8497ed0222dde7492a8d12`, ccv `5c6c18fd0a10e17071e63dc4156a5efb5d41bb01`. See [issue evidence and source links](https://github.com/djebaz/dtflow/issues/353).

- q8p is palette encoding, not affine INT8: a little-endian UInt32 block-size header (16,384), then 256 F16 palette entries and one UInt8 index per element in each block. The final block has only its actual number of indices. The stored codec identifier is `0x8a1e8b`.
- For N F16 elements, q8p needs `4 + N + ceil(N/16384) * 512` bytes. Match ccv's CPU encoder capacity of raw F16 bytes plus four. If it cannot fit, try ezm7 (`0x511`), then retain raw F16 if that also cannot fit. Packed `type` is `(codec << 32) | 1`; datatype stays `0x20000`, dimensions/format/names are preserved.
- ezm7 stores the compressed exponent-stream size, raw-DEFLATE exponents and sign/seven-bit mantissa bytes. Round discarded mantissa bits to even, backing down if rounding would overflow the seven bits. It is lossy, not untouched F16. Decoder expansion is capped at the declared element count.
- Native MIT-licensed `kmeans1d==0.5.1` supplies optimal 1D DP/SMAWK clustering in the optional `quantization` uv group; its public API and cost/backtracking implementation were inspected. Compatible Windows ABI3 wheels exist and the native import succeeded locally. This does not validate conversion arithmetic or legacy-CPU/package compatibility. It is not a runtime dependency of the ordinary application and is imported only for the experimental writer.
- The objective matches ccv's 1D clustering, but tie/summation/cluster-label decisions are not claimed bit-identical. Pad unused final-block palette entries with zero. Palette centroids go through Float32 and DTFlow's existing ccv-style F16 truncation helper. Compare decoded results against the owner's iOS references before asserting numerical equivalence.
- The public iOS “Create an 8-bit model” handler was not located. The q8p/ezm7 policy is supported by the shared codec and supplied Krea 2/SDXL/Z Image samples, not proof of every app/family decision.

## Reports and diagnostics

Schema-1 JSON on stdout records build identity, optional owner-supplied checkout revision, upstream pins, full file digests, family, sizes, tensor/codec counts and validity. Comparison adds aggregate MAE, RMSE, maximum absolute error, different F16 bit-pattern count and equal encoded-payload tensor count. Quantization adds its clustering implementation/version, detected available logical CPUs, effective worker count, whole-operation seconds, size reduction and error relative to the input. Before progress starts, the CLI prints detected CPUs and effective workers (auto/explicit); this uses the service's resolved count after platform/task caps, not a second notebook-side estimate. Reports never claim that numerical closeness proves visual quality or DT+ acceptance. Private paths/names/tensor data are absent; full digests belong to the explicitly requested derived report, not persistent diagnostics.

Use the existing logging setup only. `lora_quantize.started|completed|failed|interrupted|cleanup_pending` carry fixed actions/reasons, bounded counts, sizes, seconds, quantization worker count and shared `asset_ref_data` prefixes. No exception text, tensor names, paths or new sink is introduced. Blocks print throttled progress, elapsed time and approximate encoding ETA to stderr, separate from stdout JSON. The ETA uses elapsed time per completed block, not a forecast for final validation/publication. On interruption, workers ignore Ctrl+C while the parent stops admission, cancels pending futures and drains admitted blocks before exit. Broken workers produce the fixed `worker_failed` error, not raw process exceptions.

The separate `tools/colab/dtflow_lora_q8p.ipynb` notebook runs the same argument/command/service functions through a lightweight `q8p_cli.py` subprocess, never multiprocessing directly from notebook-defined functions. Its markerized `.py` is canonical. GitHub API requests resolve one source SHA and download only the 18 manifest-listed Python/launcher/lock files, verifying their Git blob identities. GitHub username and secret-ID inputs select optional Colab Secret authentication in memory; headers are discarded before uv. There is no Git checkout or credential-bearing URL/config/error output. The standalone PEP 723 script's uv-generated lock installs only NumPy/kmeans1d, leaving the kernel and desktop dependencies alone; source-build installed version can therefore be unknown, while recorded revision remains explicit. `lora_family` imports retained-store support only inside the retained-list function, not during standalone file detection. Only uv bootstrap uses the notebook interpreter. File upload or explicitly mounted Drive is owner-selected; output staging/publication stays on local `/content` storage, followed by optional CKPT/report downloads. No Swift build or GPU is required. Owner reports establish one full Z Image conversion through the minimal setup with a temporary lock workaround; the later locked-setup correction and newest startup line still need Colab recheck.

## Evidence boundary

Initial implementation checks were static, CLI help and native dependency import only. The owner subsequently authorized local checks at `71661d93`: all payloads in three supplied F16/iOS pairs (Krea 2, SDXL and Z Image; 3,246 tensors per side) decoded successfully and their inventories matched. Eleven representative encoded blocks (nine q8p and two small ezm7 tensors; 139,680 values) matched the iOS decoded F16 values exactly. This is sampled numerical evidence, not whole-file encoding equivalence. Original/reference SHA-256 values stayed unchanged, and existing-output refusal preserved all three sentinel files.

Initial serial samples of full 16,384-value q8p blocks took 2.719–3.525 seconds on this Windows host. The files require 5,520–8,006 blocks; multiplying sampled block times suggests hours, not a measured full-file duration. An initial Krea 2 whole-file attempt was force-stopped before publication; its tiny staging file/journal were removed explicitly. No complete experimental CKPT was produced by the agent; subsequent owner reports below supply publication/time/size evidence for one Z Image file. The initial redirected progress stream did not expose live progress; isolated block runs established that clustering finishes, rather than proving a native deadlock. The owner later reported roughly 1–1.5 seconds per block and accepted long offline runtimes; speed alone is not a merge blocker. These serial observations do not validate the newly added multicore path, ETA accuracy or Colab execution. No new conversion was started while the owner's run was active.

Owner reports subsequently establish one full Z Image conversion on Colab: baseline `d7e3c957` took 455.531 s with 12 configured workers but ineffective within-tensor parallelism; corrected cross-tensor `03f5e7a6` took 103.483 s with 12 workers (4.40× faster in this single comparison). Both report the same input SHA, output SHA, all numerical metrics and 420 q8p tensors: 14,798,848 → 7,901,184 bytes (46.609% smaller). The reported output hashes are identical, not just close decoded values; reports were inspected read-only, not a separate rehash of the downloaded CKPT. Successful reports are returned only after reopening/decoding and exclusive publication. The owner removed `--locked` for the corrected run to work around setup; the later script-policy fix has independent Windows launcher-help evidence, not another Colab run. The new CPU/worker startup line is static-checked only. Earlier unverified whole-file/multicore statements above describe the pre-report checkpoint, not the current evidence.

Go: retain the opt-in CPU CLI experiment and minimal notebook. No production/Prepare integration or GPU recommendation follows from one paired run. Existing iOS references establish approximately 48% smaller files on four samples, not whole-file equivalence to this Z Image output or generation quality. No renders, provider operations or Actions ran during these checks. A separately authorized DT+ Prepare/generation smoke is still required for provider/quality claims. Other-family whole-file writing, cancellation/fault paths and Windows standalone packaging remain unverified. ## Owner GPU evidence and review follow-up (2026-11-15)

The optional notebook GPU path (cells 4–5) uses installed CUDA/PyTorch and **approximate FP32 Lloyd clustering** with quantile initialization. It reuses the shared CKPT decoder, writer, validation and no-overwrite publication, but is **not** the source CLI's optimal `kmeans1d`/DP-SMAWK path and does not establish ccv/iOS-equivalent centroids or labels. The CPU CLI remains the default; no GPU is required.

- **Full Krea 2 GPU report** (`recorded_revision=2cdeb7f6786e8428462088cc51524f9a8124c3c7`, NVIDIA L4, CUDA 13.0, PyTorch 2.14.1+cu130): 194,363,392 → 100,569,088 bytes (**48.257% smaller**), 474 input/output tensors and 96,891,296 elements, including 472 q8p and two ezm7 outputs. The owner-supplied report records **11.632 s** whole-operation time, 7.373 s GPU encode pipeline time, 750 GPU batches and zero batches reported nonconverged. Whole-file F16 comparison: MAE 0.000117069, RMSE 0.000374652, maximum absolute error 0.0651855. `whole_file_output_written=true` and the recorded digest are report evidence following code-path reopen/decode and exclusive publication, **not** an independent rehash or provider acceptance test.
- **Krea 2 GPU sample report**, from the same reported input SHA at the same revision: 256 full blocks / 4,194,304 elements; warmed measured pipeline 0.354 s, excluding source I/O, warmup, comparison, SQLite writes and final verification. GPU-vs-F16 RMSE is 0.000378990; owner-supplied iOS reference-vs-F16 RMSE is 0.000134157 (approximately 2.82× lower numerically on these sampled positions), and GPU-vs-reference RMSE is 0.000398804. The reference inventory matches, but a matching original-weight SHA/provenance has **not** been established, so this is **not** a controlled conclusion about relative algorithm or visual quality.
- The Z Image CPU report remains a **different input**: 14,798,848 → 7,901,184 bytes (46.609%) in 103.483 s at revision `03f5e7a6`. Do **not** present that as a direct CPU-versus-GPU speedup comparison; family, file size and clustering algorithm differ.

**Review finding — Python compatibility (not fixed in this documentation change):** the optional GPU full-conversion cell calls `quantize_file()` in the notebook **kernel**, not the separate managed Python environment of the CPU launcher. `quantize_file()` calls `os.process_cpu_count()` (available since Python 3.13); a Python 3.12 kernel can raise `AttributeError` before encoding. Use a compatible kernel until a fallback is implemented, then verify the GPU cell on the supported Colab kernel. A successful owner GPU report establishes only that the reporting environment completed.

**Decision:** continue as opt-in CPU/GPU experiments, without Prepare or production integration. The next separately authorized owner check is F16 versus iOS q8p versus GPU q8p on the **same verified original weights**, checkpoint, prompt, seed and LoRA weight, recording DT+ acceptance, actual LoRA effect and generation quality. Keep AC-4 unchecked until that evidence exists. No new tests, conversion, render, provider call or CI run was performed for this documentation update.
