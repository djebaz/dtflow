# LoRA conversion service (#400, #401, #402, #403, #414)

**Current source as of 2026-11-14:** DTFlow has a Qt-free, synchronous converter at `src/dtflow/services/lora_convert/`. This is a current-code reference, not the earlier [planning document](../plans/2026-11-12-lora-convert/architecture.md). The service converts a known-family `.safetensors` LoRA into Draw Things F16 SQLite/NNC `.ckpt` locally on Windows, without calling DT+ or uploading.

## Components and contracts

The separate [q8p CLI experiment](lora-quantization.md) works on already converted F16 CKPT files only. It does not change this converter, Prepare, retained-store behavior or upload approval.

- `convert_lora(ConversionRequest, *, progress=None, cancel=None) -> ConversionResult` is the importable, synchronous API. Callers choose their worker thread; the converter has no Qt dependency. The request includes source/destination, required family, scale and experimental/unmatched options. The result retains output SHA-256, bytes, tensor count, exact architecture and provenance. Progress events describe reading/converting/writing/finishing, and cancellation is cooperative.
- The API refuses to replace existing outputs. `ckpt_writer.py` writes a temporary `.part` then renames it, so failed conversions do not publish a partial checkpoint.
- `registry.py` binds explicit family keys (`krea2`, `zimage`, `flux1`, `sd1`, `sdxl`) to exact architecture and status. `families/` holds their resolver/table rules; `safetensors_io.py`, `keys.py`, `numeric.py`, `ckpt_writer.py` and package-owned `data/lora_mappings.json` implement the file conversion. Historical `tools/drawthings/` remains untouched.
- `detect.py` holds the header-only source-family detector and `services/lora_convert_prepare.py` the Prepare-time conversion (below). `__main__.py` exposes `uv run python -m dtflow.services.lora_convert`. Single files write one destination; folders and filename globs are non-recursive and case-insensitive, and select only `.safetensors`. A batch skips existing outputs unless `-w/--overwrite` stages explicit replacement. Individual failures do not prevent other items from proceeding. Every batch writes a schema 1 JSON report.
- `-a/--analyze` enables schema 2 reports for batch **or single-file** conversions. `analysis.py` reports source dtype/rank/alpha, mapping coverage and possible shape problems. After a successful conversion, the CLI invokes existing `services.lora_family` functions to check the **output CKPT** structure and detect its family. This output check is not proof of numerical equivalence or applied LoRA effect; source detection lives in `detect.py` (below).

## Conversion correctness and history (#452)

- An alpha tensor is optional, but when present it must contain exactly one value. The shared numeric reader rejects empty or multi-value alpha tensors with a converter-domain error before any Prepare upload; valid scalar scaling is unchanged.
- Retaining an identical conversion no longer adds provenance whose only difference is `converted_at_utc`. The earliest matching history record and its timestamp are kept; source observations, converter versions and other meaningful differences remain separate. Existing historical entries are not rewritten, and content retention, no-overwrite and explicit upload consent are unchanged.

## Prepare integration (#401, #402)

- **Disposable staging (#451).** Before reuse/conversion, the explicit Prepare worker makes a bounded best-effort pass over `lora_files/.convert`. New `job-<uuid>` directories are published only after acquiring their stable `.owners/job-<uuid>.owner` OS lock, held through conversion, retention and final cleanup. Cleanup must acquire that same lock; neither age nor the retained-store lock proves inactivity. The sibling lock files remain as tiny coordination metadata (not scanned or deleted), allowing Windows to remove a job while it is still owned. Legacy unowned jobs, unknown contents, links/junctions/reparse points and hardlinks are not reclaimed. A sweep examines at most 128 root entries and 16 candidate jobs, preflights at most 32 flat regular files per job, removes at most 8 GiB and checks a 0.5-second scheduling budget between jobs; filesystem calls are not interruptible. Oversized/unsafe jobs remain, and bounded passes do not promise to clear every backlog. No retained index, accepted CKPT, source, receipt or output is swept. See the [design and evidence boundaries](../plans/2026-11-14-conversion-staging-cleanup.md).

- **Picker and rows.** The Prepare picker takes `.ckpt` and `.safetensors`. A `.safetensors` row is labelled as a source, offers the registry families (F16 output only) and keeps the family dropdown empty and required until one is chosen or detected. Selecting a file never converts, uploads or saves metadata.
- **Source-family detection (`detect.py`, #402).** Reads only the safetensors header (tensor names and shapes): never weights, never the filename, never `__metadata__`. A family is suggested only when **every** recognised module maps under that family's resolver or tables, a family-specific group is present, q/k/v input widths corroborate it, nothing contradicts it, and, for every family except Flux 1, the source has the parts the converted-output check in `services/lora_family.py` will require. **Flux 1 is the one exception:** a source with distinctive Flux-only module names (or full 19 double + 38 single block coverage) is detected even when it is partial, but the converted-output check needs the full block coverage, so Prepare converts such a file and then refuses the output ("could not be verified as the selected family"); only the CLI keeps that output. A detected family is therefore a suggestion, not a promise that Prepare will accept the result. One passing family is preselected (SDXL included; the experimental confirmation is still required); several passing families are ambiguous, and anything weaker stays unknown with a fixed one-line reason. SD 2.x and the SDXL refiner are explicit negatives, mixed plain and LoHa/LoKr/DoRA/bias/diff tensors are unknown, and corrupt or non-safetensors files make the row unreadable. Manual choices are never overwritten; clearing one shows "Required · file suggests X". Detection is a suggestion: the converter still validates the source.
- **Descriptive metadata (`source_metadata.py`, #414).** Beside the structural detection, the same single header read (`detect.inspect_source`, kept briefly per path, size and modification time so the later conversion does not parse the header again; unreadable results are never cached) yields a bounded selection of the header's `__metadata__` strings, which are **display and suggestion data only: never evidence for the family, never an input to detection, readiness, confirmation or conversion** (#402 stays structural). Reading is best effort: empty or `"None"` values, wrong types, invalid JSON, non-finite numbers, very deep nesting, huge integer counts (clamped) and any other failure leave a file with fewer fields or none, never an error; an `ss_tag_frequency` string over 1 MB is not parsed. Kept fields: title, output name, author, description, date, license, declared architecture and base model, base model file name (reduced to a name), network type, rank, alpha, resolution, epochs, class tokens, trigger phrase and usage hint, each with a character cap, plus the top 50 training tags summed over datasets. Dataset folders (`ss_dataset_dirs`, `ss_datasets`) and training comments are never kept. **Trigger suggestion** comes only from an explicit declaration: `modelspec.trigger_phrase`, or the ai-toolkit one-tag `ss_tag_frequency` (`{"1_<word>": {"<word>": 1}}`); a phrase over 200 characters is rejected, never truncated, and the general tag vocabulary is never a trigger. In the Prepare row the Trigger Words field is pre-filled with the saved value for that content when the registry holds a non-empty one, otherwise with the suggestion. An empty saved value counts as **not set**, so the file's declared trigger is offered again (badge "from file"); a non-empty saved value beats a suggestion, a value typed or cleared in the row by the user always wins for that row, and when the saved values cannot be read no suggestion is applied. Nothing is saved until the user prepares the row. The selected row shows two inline plain-text lines in the preview band (line 1 training facts, line 2 top tags; `ui/source_details_view.RunsLine`, painted with QPainter from `theme.load_tokens()`: labels and separators `color.secondary` at `type.weightBody`, bold values `color.text` at `type.weightEmphasis`, `type.small`; no text boxes, no popup, no hardcoded colors), each elided to the width. Line 1 appends `base <name>` when the file supplies a base model. The file's own title, author, license, date and description are never shown in the app and are not kept in the retained record; they remain in the CLI JSON report only. File text is never interpreted as markup. The region tooltip lists all selected training facts (including one trigger phrase, class tokens, network type and usage hint) and up to all 50 retained tags with counts, independently of the shortened inline summary and its 12 tags. The tooltip covers the whole metadata area (the lines, the gap between them and the margins; `RegionTooltip` event filter) with the heading "Training metadata"; values use shared emphasis weight, labels, separators and counts are quieter, and file text is HTML-escaped. Tooltips are shown with a quick fade-in app-wide (`QApplication.setEffectEnabled(UI_FadeTooltip, True)` once in `run_gui`, unless the desktop disabled UI effects). If the declared trigger lists several comma/semicolon-separated phrases, display only the first non-empty phrase, without altering saved Trigger Words, suggestions or generation. After a conversion, `LoraStore` keeps **one** bounded `source_metadata` record per retained file (newest wins, so reconversions add no copies; only the training facts (including declared architecture, base model and base model file name), tags, via `SourceMetadata.retained_record`; never the file's own title, author, license, date or description; the CLI report keeps everything); the Edit metadata dialog shows the record read-only without the original file. The CLI `--metadata` mode (`metadata_report.py`) reads the same single header per file and writes a schema 1 JSON report (`lora-metadata-v1-<timestamp>.json`, never overwriting; with `-a` also the structural family and whether the declared one agrees), best effort with per-file failures and conversion-only options refused. Conversions made before #414 have no retained metadata until their original source is selected again.
- **Conversion step (`lora_convert_prepare.convert_for_prepare`).** After the explicit **Prepare N ready LoRAs** action, each source row is converted on the existing worker, one file at a time, then goes through the unchanged asset Prepare. The worker hashes the source once, looks for a verified retained conversion with the same source SHA-256, family and scale using the version policy below, converts into a staging folder on the store volume when there is none, checks the output with `validate_converted_lora` and `detect_lora_family` (it must equal the chosen family's exact architecture, otherwise nothing is retained), re-checks that the source did not change, and adopts the file into `LoraStore` with a conversion record and the bounded source metadata (#414). Identical output bytes share the existing retained copy.
- **Reuse.** A retained conversion matches source SHA-256 + family + scale independently of the source name or location. Parse simple decimal converter-version strings numerically: verified current-version results win (latest valid UTC conversion timestamp first), otherwise the highest verified newer version wins (timestamp tie-break). Older, missing or unparseable versions require conversion with the installed converter, without an extra user decision. Skip damaged candidates in that priority order. Lookup runs only inside the explicitly authorized worker, not on file selection. The existing editor hash remains separate from the worker hash; no third hash is added for this lookup. A missing or altered earlier output is skipped and the file is converted again; retention then repairs that entry from the freshly converted, hash-checked bytes (a missing file is recreated, an altered one is moved aside to a hidden `.<id>.damaged` file in the store, never deleted), while an unsafe name or a link is still an error before any reconversion; an unreadable or malformed store index is still an error and nothing is reset. For a conversion with different bytes, use the existing name allocator after conversion when the requested name is reserved for other content. Read accepted-name reservations after conversion (refreshing them again before the bounded retry) and retained names, then recheck retention under the existing store lock; a specific retained-name conflict permits one allocation/retry only. No old accepted file, metadata or receipt is renamed to make room. An unavailable safe name or another conflict fails the row without overwriting. `PreparedConversion.metadata` carries the final retained identifier (same family and format) into the existing asset-service call; ordinary source reuse keeps the retained name even when a different Short name was typed. Non-canonical retained identifiers fail before metadata backfill or reporting successful reuse, with an explicit recovery message; no accepted data is renamed as an implicit repair. An explicitly approved Re-Prepare can still use the existing accepted-name rename path. The CLI converter and legacy conversion-helper callers without authoring metadata keep their no-overwrite behavior.
- **Progress.** Conversion feeds the same Prepare progress as upload (reading, converting, checking, uploading, confirming). The bottom bar shows the source name while inspecting, reading and converting and the retained managed `.ckpt` name afterwards. The open editor row status also shows that actual managed identifier, without rewriting the typed draft or granting new consent.
- **CLI.** `--family` is optional: without it each file's family is detected from its header, a file that cannot be identified fails with the detector's reason (batches continue and exit 1, a single file exits 2), and an explicit `--family` overrides detection. A detected SDXL file still needs `-xp/--experimental`. With `-a`, each item keeps an additive `source_family_detection` object, and reports carry `"family": "auto"` plus a per-item `family` and `family_source` when `--family` was omitted. Schemas stay 1 and 2.
- **Diagnostics and privacy.** Events carry the first three filename characters, short SHA-256 prefixes (via `diagnostics.asset_ref_data`), outcome, family, candidate count, fixed evidence and reason texts and timings; never a full name, path, tensor key or `__metadata__` value. No provider call occurs before a conversion succeeds, and conversion never switches backend, account or billing mode.

## Evidence

On 2026-11-12/13 the owner converted two real Krea 2 files on Windows, compared their 474 and 512 output tensors with Draw Things iOS reference conversions (zero missing names, shape/datatype mismatches or tensor-data hash differences), prepared them in DTFlow and confirmed their expected effect in DT+ generations. The Prepare path was smoke-tested on real Krea 2, Z Image, Flux 1, SD 1.x and SDXL files (conversion, post-check, upload, confirmed receipt, reuse and deliberate refusals); the owner reported that the converted LoRAs applied on DT+ on 2026-11-13. This is owner smoke on specific files, not exhaustive family coverage, and packaged-executable acceptance is a separate check. See [converter/CKPT guide](../guides/lora-ckpt-format.md) and [#405](https://github.com/djebaz/dtflow/issues/405).
