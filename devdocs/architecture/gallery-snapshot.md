# Cross-runtime gallery browsing snapshot

## Scope and publication

`persistence/gallery_snapshot.py` publishes `<state>/cache/derived/gallery_snapshot.sqlite3`, a disposable version-1 browsing projection, not an execution database or source of removal/export authority. It contains only committed succeeded-attempt gallery columns, removal identity/outcome rows, a source-change signature and an explicit UTC publication timestamp. It contains private saved prompts/settings/paths; do not share it as a diagnostic log. No images, provider payloads, active queues or credentials are intentionally copied. No output-folder scan or raw live-database/WAL file copy occurs.

Publication is requested once a durable generation session or queue dispatch closes its store, and at clean GUI process close after Qt's event loop exits and runner shutdown is requested. A single background worker performs session publications without awaiting them on the generation result path. Clean close waits for the final publication outside Qt's event loop. The signature compares committed-attempt count, newest saved timestamp and aggregate serialized lengths plus removal-row count/newest outcome timestamp; immutable committed records and the existing ledger writer timestamp contract define changes. An unchanged signature skips rewriting. Missing snapshots are created, including an empty publication when no execution database exists. There is no per-image publication inside a queue, periodic publisher or provider retry.

The publisher takes the existing removal-batch lease (brief bounded acquisition) and cache coordination, waiting up to 0.5 s for the cache lock rather than skipping on a brief overlap, then reads a consistent live SQLite transaction. It does not hold the originals lease while projecting metadata and does not delay paid image saves on that lease. It writes bounded batches to a fresh standalone SQLite file in the same category, closes/fsyncs it with a writable descriptor (required on Windows), and atomically replaces the previous publication. Source query/work budgets and a 2 GiB publication limit refuse oversized work. Failure preserves the previous publication before replacement and logs only stage/type/numeric OS codes, not paths or prompts. Missing bridge support, cache contention, active removal or a cross-runtime SQLite failure can prevent publication; that never changes generation outcomes or resubmits work.

## Publication diagnostics

Before allowing an unchanged-signature skip, the publisher validates the same-version previous file's canonical gallery query structure and runs SQLite `quick_check(1)`. Both validation and any delta comparison share the existing publication deadline and size limit; validation is not an unbounded repair pass. An unreadable same-version baseline rebuilds from live state with unknown deltas. If a later baseline comparison fails, counting retries against the new projection alone within the remaining budget. Unsupported schema versions remain protected from replacement. No live authority or ledger behavior changes, and a failed replacement still retains the previous file. This adds bounded previous-file validation work; no runtime performance claim is made.

Normal logs distinguish `generation_session_end`, `queue_session_end` and `app_close`. A saved publication reports `images_added`, `images_removed` and `images_total` separately from `committed_attempts_total`, plus its persisted `last_updated` UTC timestamp and elapsed milliseconds. Counts compare visible gallery identities, including the canonical removal exclusions, not physical files, metadata sidecars or attempt counts. Ordered identity cursors stream from the new projection and the retained previous immutable connection inside the publication deadline; no Python identity set, image scan or hashing is added. The previous connection closes before atomic replacement. A first publication counts all included images as additions; an unreadable prior baseline reports unknown deltas rather than inventing additions.

Unchanged checks log their trigger, skip reason and retained timestamp without rewriting. App close also reports whether this process published before close, whether close itself saved, the close result, and cumulative additions/removals across this process's successful publications (not net changes and not other processes' activity). A later removal does not subtract an earlier addition from those activity totals. Unknown deltas make that session total unknown. `timestamp_source` distinguishes a checked publication from the last known session publication when the close check fails, or unavailable; clean `--no-cache` close reports bypass without snapshot I/O. Diagnostics contain counts, timestamps, stage/type/numeric OS failure codes, never identities, prompts or private paths. The owner reports current-PR smoke passed; measured performance remains separate.

## Browsing fallback

Review follow-up: the reader establishes its deadline before opening/setup and installs SQLite progress cancellation before schema/metadata reads. It no longer copies or indexes removal rows in memory: `SNAPSHOT_BASE` is derived directly from canonical `BASE`, replacing only `image_recycle.records` with the same immutable connection's `main.records`. Its primary-key index is already published. The canonical `recycled`/`restored`/`deleted`/`absent` exclusions and all filtering/order/paging semantics remain identical; default live queries still use unchanged `BASE`. Page, count, anchor and facets share the one open file even if the pathname is atomically replaced meanwhile.

Normal live queries remain first choice. Only a live persistence failure invokes the snapshot fallback; failure without a supported snapshot retains the live error and already-loaded cards. One immutable snapshot connection serves anchor lookup, count, page and facet queries together. Readers never attach live removal state to the snapshot. Filters, sorting and pagination reuse the canonical gallery SQL rather than duplicate query rules; metadata remains read-only and original bytes retain existing shared leases/provenance checks.

The desktop displays a persistent **Read-only snapshot** notice with its UTC timestamp and **Live updates unavailable**, keeps retrying live access, and returns to live browsing when a query succeeds. A snapshot may omit recent generations or show historical records/files since changed or removed; it is not proof of current availability. Detail can read surviving sidecars without querying the blocked live database. Snapshot-backed selection cannot authorize export, edit/reuse/regeneration or removal; their actions are disabled/guarded until fresh live state returns. Opening the export panel alone remains non-mutating; the checked-identity provider refuses snapshot authorization. General concurrent Windows/WSL execution-state writers and WSL2 support remain out of scope.

Derived-cache cleanup may remove the snapshot, and `--no-cache` bypasses both publication and fallback reads for the launched run. Missing/unsupported/unsafe snapshots produce no fallback; newer publication schema versions are preserved rather than downgraded. Snapshot timestamps and source-change signatures are convenience evidence, never content hashes or durable attempt outcomes.

## Evidence and acceptance limits

The fallback condition uses a separate keyed `activity_status_row.ui` in the shared activity overlay: amber, single-line height, persistent without result expiry or countdown. It coexists with active feedback rather than replacing confirmations/editors; the regular snapshot timestamp stays in the gallery. Each retry updates the same row. Dismissing it suppresses the whole fallback episode, including timestamp updates, navigation and brief successful live reads. The first live success keeps the same row with **Live gallery access recovering · Checking stability** wording; another consecutive live success at least one five-second polling interval later ends the episode, removes the row and resets dismissal for a genuinely new fallback. Snapshot results or failed refreshes restart that recovery interval. No new timer is added. Fresh live data and operation authority return immediately; only warning presentation is stabilized. It hides outside Images without clearing dismissal. Focused dismiss-button Escape and × remain local. All transient warning/result rows keep their existing six-second policy. Preview states 47/48 include the row, 49 covers dismissal across a brief live success and renewed snapshot, and 50 covers recovering wording. Fixture definitions are extended, not rendered.

The two-read stability rule applies only with Auto-refresh On. With polling Off, a successful live refresh ends the episode immediately rather than waiting indefinitely for another manual refresh. Turning polling off while a successful live read is already recovering also ends the episode. Failed refreshes and snapshot-backed results cannot clear it. The shared episode-ending helper resets dismissal/stability state consistently; no recovery timer or new authority path is introduced. Offline preview state 51 defines the single-manual-refresh recovered presentation; not rendered.
