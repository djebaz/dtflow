# Direct DT+ integration (Phase 2C)

Desktop LoRA Prepare accepts multiple supported converted `.ckpt` files and remembers its folder per runtime (see [runtime layout](runtime-layout.md)). The presentation controller snapshots and deduplicates selected paths, holds one page-busy ownership across sequential calls to the unchanged `services.session.prepare_asset`, and merges each confirmed receipt into the current selection without resetting weights. Stale registry-list callbacks are discarded. No new uploader, provider protocol, durable batch queue, parallel upload or automatic generation retry is introduced. An unknown remote outcome remains unresolved, never successful; later explicitly selected files may still be prepared. Backend or desktop credential changes stop further admission after the current service call settles. Runner shutdown retains existing service settlement semantics and admits no next file; navigation/dismissing feedback does not cancel work. The final multi-file summary counts confirmed, failed, unresolved and unstarted files. Native/platform acceptance remains separate from source presence.

**Status:** implemented against HTTP mocks and the existing scripted TLS/gRPC fixture. The owner reports a passing
Windows offline suite and successful deployed token/inventory and bounded generation checks through this adapter, using `z_image_turbo_1.0_q6p.ckpt`. This is user-reported evidence for that workload, not broad model compatibility. The latest runtime/evidence changes still need a Windows repeat; broad model/LoRA compatibility, production cancellation latency, charging/refunds and packaged execution remain unverified. See the [pinned protocol](cloud-protocol.md) and [Phase 2 plan](../plans/phase-2-backends.md).

## Implementation and probe reuse

`cloud_auth.py` follows the probe's `/sdk/token`, `/authenticate`, raw short-token Authorization header, contents-free protobuf blob, `fromBridge: true`, and lowercase gRPC `bearer` metadata. Optional generation-auth fields are omitted as specified by the official Codable path, rather than sent as null by the probe. No PAYG or billing lookup is performed. Tokens and blobs never enter durable metadata or public errors.

The deliberate production changes are scoped async HTTPX instead of diagnostic `to_thread(urllib)`, bounded HTTP responses/deadlines, and expiry-aware shared refresh. The API origin and selected credential are fixed per auth client. The selected API key is resolved once and cached for that client's lifetime: changing `DRAWTHINGS_API_KEY` does not update an existing `CloudAuth`; close it and create a new client. A valid cached token is reused; concurrent refresh callers join one shielded task. Cancellation of one waiter does not cancel that task. Each generation obtains its own authorization; failures do not silently retry or switch credentials. HTTP uses normal verified HTTPS; gRPC explicitly chooses system trust with h2, exactly the probe baseline. No cloud certificate pinning or local bundled-CA exception is introduced.

`DirectCloudBackend` inherits the actual `DrawThingsBackend.generate` implementation, including channel creation, wire configuration, codec validation, stream completion, previews, deadlines and failure evidence. Its hook authorizes the same built message before the submission boundary and supplies its metadata to the shared stream. Echo obtains a short token but carries no generation bearer. Health reports API authentication separately from transport and inventory; it never requests generation entitlement. A successful token exchange is not a quota or billing check.

The cloud backend supports a configurable client cap of 1–10 (default 4), using the shared semaphore; local remains one lane. The 320 MiB shared admission budget reserves 32 MiB per direct-cloud text-to-image request (one encoded output cap), allowing ten simultaneous client submissions at a selected cap of ten. Image edits keep their larger buffers. Neither peak RAM nor provider entitlement is verified. This is client support and a product cap, not a server entitlement or the Phase 3B rolling scheduler. Only discovered model IDs are admitted. Generation scope remains txt2img, batch 1/1 and the two existing samplers. Initial custom LoRA preparation (Phase 3B cloud half) is explicit; a later generation reuses its confirmed per-key receipt without a repeated check, and may restore verified retained bytes **before submission** on first use under a new key (or after a relevant failure) only after a positive DT+ missing-file answer: `DirectCloudBackend` implements the asset-side `AssetBackend` protocol (`negotiate_asset`, `upload_asset`; no list or delete). Negotiation posts `file`, lowercase SHA-256 and byte `size` to `/get_byom_urls` and consumes usable `alreadyExists` and `signedUrls` evidence independently, preferring a valid existing reference; the upload response's `sha256` is a private server-returned value, not a required echo of the measured local checksum. Missing usable evidence, an unsafe destination or an unusable reference stops admission without guessing a receipt. A required upload streams the file once in bounded chunks to the signed URL with no DT+ authorization header, explicit connect/write/read/total deadlines and no redirects, re-hashing as it streams. Failure evidence is the remote outcome: `not_started` (connect failed before any byte), `failed` (HTTP 4xx refusal, no quota meaning inferred) or `unknown` (timeout, disconnect, 5xx, changed file). Signed URLs live only in an opaque adapter ticket and a query-redacting `httpx` log filter; they never reach logs, errors, receipts or CLI output. After a successful PUT a fresh metadata check must return the server's reference before a receipt is `confirmed`; otherwise the record stays `unknown` and no second PUT is made. Generation still sends the LoRA's exact identifier; the receipt's remote reference is validated before dispatch but is not yet placed on the generation wire (unpinned until `3-LG4` evidence). Separate metadata-only LoRA availability enrichment uses local `FilesExist` identities and DT+ BYOM lookup. It validates usable entry structure, not local/server checksum equality, and retains source observation times/freshness separately from resolution time in `lora_inventory.json`. Fresh negative file-existence evidence overrides older Echo availability. CLI generation backend selection is implemented in Phase 3A (`dtflow generate -b cloud`; offline-validated only). The test runner adds an optional DT+ token/inventory check under `-live` and one complete, bounded DT+ service generation under `-gen`; these are skipped by default. Both use the [shared live-run layout](runtime-layout.md), outside `.dtflow/`, with versioned inventory snapshots and one credential-free summary. The local live check uses the same run root.

## Model descriptions for unlisted checkpoints

DT+ resolves checkpoints from its own model list. A checkpoint it serves without a description there (for example FLUX.1 [dev], FLUX.2 [dev], klein base 9B, Krea 2, Qwen Image 2.1, and the official FLUX.1 Schnell f16 file) runs with a default description and returns noise or degenerate previews. The request therefore carries the checkpoint's own description in `override.models` (a JSON array of one specification).

- Source: the description the server advertises in Echo when it has one (cloud Echo currently advertises none), else the bundled Draw Things community description in `resources/catalogue/community_model_specs.json`, generated by `tools/drawthings/build_model_specs.py` from the public `community-models` repository.
- Exact file only. Another quantization's description can carry different fields (`is_bf16`, `mmdit`) and made the cloud drop the connection (`grpc_unavailable`), so a file without its own entry sends no description. The only exceptions are the explicitly derived FLUX.1 entries in `core/model_profiles.py` (Schnell f16/q4p, dev q6p/q5p_svd, dev de-distill f16) and, as an owner-requested trial, community SDXL and FLUX.1 checkpoints of the niche catalogue that have no community description (about 139 SDXL, 217 FLUX.1, 5 SD 1.x): SDXL from Juggernaut XL Ragnarok's plain fields and SD 1.x from DreamShaper v8's, each with the checkpoint's own file and CLIP companions, FLUX.1 from `flux_1_dev_q8p` (or PixelWave Schnell 04 for names containing `schnell`). Fill/Kontext/Redux/Canny/Depth/inpaint/v-prediction/LCM/turbo/lightning/hyper names are excluded. Owner-tested on direct cloud 2026-10-10: Copax Pony XL returned terminal OK with no image without a description and an image with one, and most of the derived SDXL and FLUX.1 descriptions were reported working; untested files remain unconfirmed, built from sibling checkpoints whose descriptions agree except for file, name and T5 encoder; they are derived, not published by Draw Things.
- The local backend never sends descriptions. A served file is not evidence that it needs one: models that already work (for example SDXL, Z-Image, Schnell q5p) stay without.
- Evidence: owner-reported direct-cloud runs on Windows. FLUX.1 [dev] q5p produced images after the description was sent; FLUX.2 [dev], klein and Krea 2 completed with normal previews (image quality not yet confirmed); the derived Schnell f16 description is not yet confirmed.
- Development mode (`-x`) logs `model spec sent for <file>` with the field names only.

## Cancellation, ownership and limits

The generation total deadline includes credential preparation, lane admission, connection, authorization, stream and decode. Authorization failure is `not_submitted` / `not_started` for GenerateImage; its HTTP effects are not inferred. A pending task cancellation is checked after authorization so even a late mock response cannot revive RPC dispatch. After possible send, shared 2B evidence rules apply: disconnect without validated completion is unknown, no retry. Terminal OK with valid required outputs survives later terminal-event notification failure; services still save durably.

Callers cancel and await owned operations before closing the backend. Close refuses active generations, then closes the channel, requests refresh cancellation, and waits within its cleanup budget. A `finally` path always attempts HTTP pool closure with a separate cleanup budget (default 5 s for each stage). A delayed/non-cooperative refresh produces a cleanup timeout without skipping HTTP closure; repeated close is harmless once the pool is closed. Closed auth clients cannot accept late tokens. The existing service conservatively persists potentially executing state before calling an adapter; task cancellation without returned failure evidence may therefore leave an attempt unknown even when an offline test proves authorization prevented dispatch. No remote cancellation confirmation is claimed.

HTTP responses are streamed with a decoded-body cap. Failed calls project error bodies capped at 8 KiB through the shared `diagnostics.api_error_data` boundary before exposing evidence in failures, WARNING logs or UI. Complete JSON/text/XML/HTML errors are sanitized, while oversized/incomplete bodies and binary content are omitted with explicit markers; separate safe messages are capped at 2,048 characters. Success token bodies, signed URLs, private cloud references, request blobs, prompts and image payloads are not logged. Allowlisted correlation/retry/content headers may be retained. Existing [received-tensor and worker limits](drawthings-integration.md#limits-enforced-and-not-enforced) remain unchanged, including grpclib's whole-message receipt and fpzip allocation limitations. No new gRPC receipt or peak-memory limit is claimed.

`backend.api_failed` records stable transport/operation/status/code, elapsed milliseconds where measured, safe server explanation and response evidence, and unchanged submission/remote-outcome certainty. HTTP operation identifiers are `sdk.token`, `authenticate`, `get_byom_urls` and `asset_storage_put`, never signed paths. gRPC uses `Echo`, `FilesExist`, `GenerateImage` and `connect`. Sanitized gRPC messages are retained; custom binary/protobuf details are omitted with type/count evidence, and observable GenerateImage headers/trailers are allowlisted. Successful endpoint calls emit DEBUG summaries, while existing application lifecycle records remain separate. A 200 with an unusable schema is a protocol failure, not success. Server wording is descriptive evidence: neither `PERMISSION_DENIED` nor text mentioning throttling changes billing, category compatibility, retry rules or remote certainty. See the [endpoint inventory and delivery plan](../plans/2026-10-22-api-response-diagnostics.md). A `get_byom_urls` HTTP 200 answer whose `data` holds `storageLimitExceeded` (members `files` and `freeSpace`, the latter inferred as bytes) and neither `alreadyExists` nor `signedUrls` is reported as `cloud_storage_limit_exceeded` (resource limit, not submitted); an existing reference or usable upload entry still wins. Other answers with no usable entry log `backend.byom_match_failed` with bounded shape counts and never raw keys or values.

## Local completed-image counters (issue #221)

DTFlow keeps a local, informational daily count of saved final DT+ images per API key. It is an estimate from durable saved-attempt evidence, not provider-confirmed consumption, and never blocks, bills, polls or generates.

- **Evidence.** `GenerationService` records, just before an attempt becomes `succeeded`, one `cloud_usage(attempt_id PRIMARY KEY, credential_id, key_hint)` row for backends exposing `credential_usage` (only `DirectCloudBackend`). The completion time is the attempt's existing `updated_at_utc`; the image count is the attempt's artifacts minus its metadata entry. Generate, Queues, Scripts and image operations share this path, so an attempt is counted once. Failure to record is logged without credential data and leaves the attempt successful but unattributed.
- **Identity.** `CloudAuth` derives `credential_id` (a domain-separated SHA-256 digest of the stripped key, truncated to 128 bits) when it resolves the key, plus an optional four-character hint of the variable part. The owner reports DT+ keys as `dk_` followed by 25 alphanumeric characters (2026-11-04); the hint is the first four of those 25 and only a key of exactly that shape gets one, otherwise there is no hint (a neutral label) rather than guessed characters. The raw key never leaves `CloudAuth`; the digest is unsalted, which suits high-entropy keys only. Rows group by digest, never by hint; shared or missing hints get an ordinal label, not more key characters.
- **Counting.** `services/cloud_usage.py` converts the saved UTC times to the selected IANA zone and selects the half-open interval between two consecutive local midnights (23/25-hour DST days included). `persistence/cloud_usage.py` reads succeeded `drawthings-cloud` attempts in a padded UTC window through the read-only gallery reader; schema-6 databases without the table, and attempts saved before schema 7, count as unattributed. The execution writer maintains one partial `(backend_id, updated_at_utc)` index for completed attempts, so this narrow read need not scan unrelated history. Existing databases gain the index on their next normal writer open; passive startup reads never perform a migration. Until that happens, the advisory counter's background read has a bounded 15-second budget rather than the gallery's usual five seconds, so an old unindexed history has more time to finish without stalling the UI. Larger or blocked reads can still report an unavailable counter.
- **Thresholds.** Green to 400, amber 401-499, red from 500 are owner working-assumption visual guidance, independent per key; the 500/day figure is not a verified provider measurement. The active key is the one the shared credential resolution would select now (environment first), resolved locally.
- **Preference.** The reset timezone is stored in `usage_preferences.json` (see [runtime layout](runtime-layout.md)).
- **Refresh.** Shared activity changes schedule a debounced local evidence refresh regardless of the selected workspace, so the global bottom-bar pill does not depend on visiting Connection. This uses the existing read-only saved-attempt reader, not provider polling.
- **Not established.** The real DT+ reset schedule and quota unit, a provider guarantee that the key format stays stable, Windows/DPI presentation and the count for image-operation outputs beyond what the owner smoke-tested.

## Acceptance ownership

### BYOM response tolerance follow-up

PR #158's [merge-preparation evidence](../plans/2026-10-22-byom-checksum-contract.md#owner-runtime-evidence--bounded-observation-not-exact-head-acceptance) records owner-reported existing-asset preparation and saved generations separately from the unverified fresh differing-server-value upload branch. Local SHA-256 remains local content identity; the returned upload value is not required to echo it. Dispatch trusts a confirmed receipt for the current stable credential identity; no routine BYOM polling occurs. First use with another credential performs a fresh authenticated lookup, batched with other unconfirmed assets where possible. Asset schema 3 preserves separate remote references per API key and per logical LoRA filename even when two names share identical bytes; an upload failure under key B cannot invalidate key A's confirmation. Concurrent BYOM requests join until their HTTP result settles, and unrelated later missing LoRAs remain eligible for their own bounded recovery episode. When DT+ confirms identical SHA-256/size under that key but supplies a different reference, DTFlow rebinds without uploading. An unknown or unverifiable mismatch blocks without uploading; historic operation evidence and uncertain outcomes are preserved.
BYOM logs a bounded sanitized response projection and fixed branch type/count observations at INFO before interpreting the known branches. Missing/null or malformed unused branches do not invalidate usable evidence in another branch; a valid existing exact-checksum reference takes precedence over an unused upload offer. Metadata lookup returns unknown for entries without usable evidence instead of rejecting the entire batch. Explicit preparation still requires either a verified existing reference or an offer for the exact requested filename with a usable server-returned value and safe HTTPS destination; no reference, receipt or upload is guessed. An unusable HTTP 200 is logged as `backend.response_unusable`, not `backend.api_failed`, with a specific local validation reason. These source changes do not establish the shape or cause of the owner's redacted response, and no live validation was performed.

## Read-only checkpoint metadata inspection

Generate's **Details** action uses `services/checkpoint_metadata.py` to resolve exact-file
technical metadata from the bundled `community_model_specs.json` and combine it
*for presentation only* with the independent DTFlow classification catalogue,
`model_profiles.json` suggestions, and the current provider's last observed
`InventorySnapshot`. The current cloud Echo often provides only filenames; a
missing server-side model description is not filled by a guessed family variant.
The inspector intentionally excludes derived `fallback_spec` descriptions;
those retain their existing separate generation-path policy and provenance.

This read-only composition never sends a new Echo/auth/generation request, never
edits `override.models`, and never authorizes a checkpoint. A later Compute Unit
feature must validate its arithmetic against upstream Draw Things Swift reference
cases independently; no estimate or credit accounting is implemented here.

## DT+ stored-file listing and delete (#440)

DT+ has no list endpoint. `list_stored_assets` posts one `/get_byom_urls` for a made-up file identity and reads `data.storageLimitExceeded.files[{file,key,size}]` and `freeSpace` only when that member is present; entries need a non-empty string key and file and a non-negative integer size, others are counted as `skipped` (cap 5000). `delete_stored_assets` posts `/delete_uploaded_files` `{"keys": [...]}` once with the short-term token (as the official client's `LoRAStore` does); timeout or connection loss maps to `cloud_storage_delete_unknown` (possibly submitted, outcome unknown, no retry). `AssetService.delete_storage` then invalidates this key's confirmed receipts whose `remote_id` equals a deleted key (or, at 32+ characters, is contained in one); receipt-update failures are logged and reported, never retried. Keys and file names are redacted from logs and errors; logs carry counts and shapes only. Whether a held LoRA still applies in generation on an over-limit key is untested. The UI is `ui/dt_storage_overlay.py` with `forms/dt_storage_overlay.ui`. Owner runs (2026-11-14) show the over-limit answer only for a file DT+ does not hold: LoRAs it already holds get `alreadyExists` even when larger than the free space. The panel opens with a dummy lookup (`secrets.token_hex(32)` hash, size = this key's `freeSpace` + 1 MiB when learned within the same open, else 30 GiB) worked on the owner's first run (2026-11-14, key with 76.6 MB free, 1 GiB fallback size): DT+ answered with the over-limit list, 116 files, with no upload. The over-limit answer does compare the declared size with the free space: after the owner deleted 5 files (free space rose to about 1.49 GB), a 1 GiB dummy and a 74 MiB one got `signedUrls` (they fit), and a 10 GiB dummy got the list again with `freeSpace` 1487839232. Later owner logs (2026-11-14, key netec) settle the unit and the accounting: Prepares that answered `already_exists` left the listing at 105 files and `freeSpace` 2665234432; one real transfer of a 385.7 MiB file moved it to 106 files and 2260815872, a drop of 404418560 bytes (385.68 MiB); a one-file delete freed 77656064 bytes. So `freeSpace` is bytes, a real upload costs exactly its size, and a file the key already holds costs nothing. Each list entry carries only `file`, `key` and `size` and the answer only `files` and `freeSpace` (the `backend.storage_listed` log records the field names and value types). Generation sends the content SHA-256 as the LoRA `file` plus the family (`custom_lora_override` in `wire.py`), never the list `key`, so a list entry cannot stand in for a receipt. Not established: whether DT+ recognises the same content across different keys (earlier `already_exists` answers on another key may have been files it already held), and how a receipt's returned reference relates to the list `key` (delete matching treats them as equal or containing).


**Quota behaves per key and content is kept server side (owner logs, 2026-11-14, key with about 3 GB free).** Deleting a stored file frees its size on the key at once (a one-file delete freed 437.1 MiB exactly), but DT+ keeps the content: preparing the same LoRA again answered `alreadyExists` with no upload, the file reappeared on the key (100 to 101 files) and free space fell by the same 437.1 MiB. Files the key already holds cost nothing (seven prepares of 218.6 MiB left free space unchanged), and real uploads cost exactly their size. In practice the quota limits what a key holds at one time, not what can be used: delete what is not needed, and anything deleted can be restored without an upload. The over-limit answer compares the declared size with the free space exactly (a 2871.6 MiB dummy was listed, 2870 MiB free). Untested: whether a re-attach of deleted content is still allowed when it no longer fits the free space, and whether content is shared across keys.
