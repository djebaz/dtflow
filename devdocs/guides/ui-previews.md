# UI previews

The **Preview** Action (`.github/workflows/preview-ui.yml`) is the single entry point for offline UI screenshots. It replaces UI renders, Explicit UI render request, LoRA Prepare UI renders and Workflow preview screenshot. It never executes a workflow graph, contacts a generation provider or downloads models. Images remain layout evidence, not native Windows/DPI, packaged or provider acceptance.

## Requests

| Request | Selection |
| --- | --- |
| Non-draft, same-repository PR transitions to Ready for review | Change-selected representative states when the PR affects preview inputs |
| Add `preview:PART` | On a PR with preview-relevant changed paths, representatives from the cumulative PR diff; an unmapped/no-impact request uses the shared sample pack with a coverage warning |
| Add `preview:ALL` | On a PR with preview-relevant changed paths, every registered UI state plus the bundled workflow-file window/canvas capture; wins over PART |
| Manual `mode: changed` | Same representatives; requires a same-repository `pr` number |
| Manual `mode: category` | Fast registered runtime states for the selected category; `workflows` also captures the bundled workflow JSON |
| Manual `mode: all` | Every registered state and bundled workflow-file capture |
| Manual `mode: workflow` | Only the window/canvas for the chosen repository workflow JSON |

Automatic Preview requests happen only when a PR transitions to Ready for review or when `preview:PART`/`preview:ALL` is added. Opening a PR, reopening it, or pushing another commit does not request Preview. A PR created already ready does not emit a `ready_for_review` event; use a preview label or manual dispatch to request its first preview. Automatic PR events are filtered by GitHub to preview-relevant changed files before any runner starts. A PR with only documentation or unrelated workflow YAML changes does not start Preview, even when marked Ready or when `preview:PART`/`preview:ALL` is added. Manual dispatch bypasses this path filter and can request a preview for such PRs. No automatic preview work runs for draft PRs, including label additions. Mark ready to enter normal automatic eligibility. Manual dispatch is explicit and can target a draft. Fork/deleted-repository PR targets are refused. Automatic requests pin the event's exact PR head, never GitHub's synthetic merge commit; manual PR dispatch resolves the current head. Live draft/head checks before setup, capture and publication refuse superseded automatic work. A capture already in progress is not forcibly stopped when a PR becomes a draft, but it cannot replace the PR's images/comment afterwards.

There are only two preview labels: `preview:PART` and `preview:ALL`. No per-category labels or automatic label creation. Archived labels are not restored, and old `render`/`render-all` labels are not recognized. If `preview:ALL` is present when a PR transitions to Ready for review, that event selects ALL. Later commits alone never rerun Preview, even with ALL retained; remove and re-add a preview label, or dispatch manually, to request another capture. Labels cannot bypass the native path filter on docs-only PRs.

Manual inputs are `pr`, `mode`, `category` and `workflow`. Empty `pr` uses the dispatch ref and requires category/all/workflow mode. Category is ignored outside category mode. A custom `workflow` path is used only in workflow mode; automatic requests and other modes use the bundled reference. Paths must stay inside the checkout, with no traversal, and the existing strict importer must accept the file. Workflow-specific application source/reference changes add the reference window/canvas capture alongside representative states; general tooling/style changes do not. Generic Workflows state screenshots and file-based captures remain distinct.

## Selection, cost and concurrency

One runner job plans, captures and publishes. GitHub's native `pull_request.paths` allowlist matches the **cumulative PR diff** against preview-relevant files, before runner allocation. A PR changing only documentation, `ci.yml`, or other unrelated YAML does not start Preview at all; that also suppresses `preview:PART`/`preview:ALL` label events on those PRs. Manual `workflow_dispatch` is unaffected. A new commit alone never starts Preview. A Ready-for-review or preview-label event can still start a cheap gate-only run when there is no meaningful screenshot selection; the in-job check prevents unnecessary Qt setup/capture. Draft and unrelated-label events skip the job without allocating a runner. Eligibility and Qt-free selection remain early steps before apt/uv/Qt setup; there is no separately rounded planning job or duplicate checkout. A short gate-only private-repository run still consumes at least one rounded runner minute; combining the steps removes the extra minimum on runs that capture. See [GitHub runner billing](https://docs.github.com/en/billing/reference/actions-runner-pricing). The Ready-for-review gate checks changes from the PR merge base; explicit preview labels bypass that content gate. Screenshot selection uses the cumulative diff against the PR base's merge base. Missing comparison history runs conservatively, with representative selection warnings rather than silent exhaustive rendering.

`tools/ui/preview_catalog.json` owns state identities, paths, levels and fixture prerequisites. `preview_coverage.json` supplies exact component packs; `preview_dependencies.json` supplies page fallbacks. Unknown/no-impact explicit requests use the shared pack with a coverage-incomplete warning. Invalid metadata fails rather than silently requesting everything. Category requests use the same catalogue and runtime capture path as automatic selection, not the separate LoRA design-reference forms. States are deduplicated in catalogue order. Fixture preparation may execute unselected synthetic transitions without saving those images.

The minimal shared pack contains exactly one existing state per catalogue category: Connection, Generate, LoRA, Inpaint, Queues, Scripts, Workflows, Images, Logs and Shell. Preview-tooling/workflow changes use this baseline rather than expanding LoRA, Scripts or Workflows categories. Tooling rules take precedence over legacy component ownership, including deleted/renamed tooling paths. Actual application UI changes still select their mapped component/page states; mixed tooling/application diffs combine and deduplicate both selections. Tooling-only changes do not add separate workflow-file captures. Full fast-category capture remains available manually; all-state and workflow-file modes are unchanged. No hard-coded screenshot list/count is maintained in YAML.

Per-PR concurrency serializes the single job with `cancel-in-progress: false`: a docs-only update cannot abort an already useful capture before its contents are classified. Trade-off: newer relevant requests do not automatically cancel the running job, and GitHub can replace an older pending request with the newest pending one. Live-head/draft checks reject superseded requests before setup/capture/publication; an already-running capture may finish without publishing. Use an explicit PART request/manual rerun if no current code preview was captured after rapid updates. State and workflow-file captures retain separate exit codes/logs, and the second capture is attempted even when the first returns failure. State capture has a 300-second deadline; workflow-file capture has 180 seconds, within a bounded job. Failure diagnostics and partial PNGs are uploaded where available. Two offline Qt worker processes run at most concurrently in Actions.

The minimal Images state uses the existing direct gallery projection (`images-65-pager-grid-normal`), not `images-01-grid` from the older generation/asset-preparation journey. Before #423, the latter's obsolete Prepare interaction produced two 60-second waits plus shorter waits on run `43497881879`; the minimal set does not enter that path. The #423 source repair makes the detailed journey inspect each synthetic CKPT, explicitly declare Krea 2 and a valid short name in the current editor, approve Prepare, and require a confirmed in-memory receipt, refreshed listing and closed editor before continuing. Source filenames remain `fixture-style.ckpt` and `fixture-soft.ckpt`; current naming rules produce managed identifiers, with the soft LoRA applied at weight 0.8. Readiness failure warns with a traceback and skips only the unready details capture; the missing-state rule fails the run. A finally block cancels hashing, dismisses the editor, requests Stop for admitted synthetic work and cancels its unfinished runner futures, waits for settlement, releases busy state and restores fake before later shared-window captures. See the dated capture evidence below for head-specific targeted and ALL results; revised-head ALL and forced failure recovery remain separate. Gallery composition stops after its last selected capture, unwinding patch contexts and leaving shutdown/disposal to its workspace owner.

The Linux Action installs only locked runtime dependencies (`uv sync --locked --no-dev`): capture/support modules do not need the development group's Playwright, pytest/plugins or Ruff. Runtime dependencies remain intact; this does not change project metadata, the lockfile, ordinary CI or local development setup. The uv package cache lives under `tmp/uv-preview-cache` on the workspace filesystem so installation can hardlink into `.venv`; managed Python is cached too, in a Preview-specific cache namespace. Local Windows/agent environments keep their documented copy policy. Compare dependency setup and whole-job time, not just screenshot time; the first run in the new namespace is cold and cannot establish warm-cache savings.

## Review output

- One downloadable `ui-preview-…` GitHub artifact contains every produced PNG, the exact request/selection, capture outcomes, logs and state manifests. Requested retention is two days, but the manual Artifact Sweeper can delete artifacts older than 30 minutes; it is not a guaranteed two-day download window.
- PR runs publish every produced PNG to the dedicated **`preview-outputs`** branch (renamed from `ci-render-previews`, preserving the existing images). Publication replaces only that PR directory and preserves other PRs in a lease-protected parentless commit. No PNGs are committed to main or the implementation branch. Manual branch-only requests use artifacts/summary without persistent branch image publication. Existing preview bot-comment links are migrated to the new branch name; raw old-name URLs are not a compatibility contract.
- One updatable Preview comment shows exact full commit, mode/category, actual and planned counts, missing states, independent capture results, selection warnings and artifact link. Thumbnails are grouped by catalogue category, with workflow-file captures in their own group. Each category is a closed-by-default accordion with a compact inline-bold clickable title and bracketed image count (for example, **LoRA** [11]), without heading margins or “preview(s)” wording in the title; a three-column grid sits inside. The overall 48-thumbnail budget is shared round-robin across categories rather than consumed by the first filenames; category captions disclose sampling and an overall shown/total caption appears only when capped. All images remain accessible through the linked branch directory and artifact, even for ALL. Legacy bot comment markers are recognized when migrating an existing PR; historical unrelated comments are left alone.
- Image publication is best effort: failure produces an Actions warning and artifact fallback, not a false capture failure. Failed captures remain failures even if partial images publish. Superseded/draft automatic runs do not update the current PR comment or images. Preview-branch images have no time-based cleanup guarantee and are replaced on that PR's next publication; the branch is not a source of immutable historical evidence.

The comment and run summary share a compact layout: one metadata/link row (mode, linked commit, image/state counts, Run/Download/Browse), a single-line representative-coverage notice when needed, visible timeout/failure/missing-image warnings, and category accordions. Do not repeat category counts or successful capture details above the gallery. Full commit, workflow path, capture exit codes/deadlines, worker timings, retention caveat and deduplicated mapping notes sit in one closed Diagnostics section; exact complete records remain in the artifact. Only show a separate shown/total caption when the thumbnail cap actually omits images. Detailed diagnostics are collapsed, not discarded or treated as passed.

Timeout diagnostics retain individual events (`wait_timeout_events`), their total (`wait_timeout_count`), affected capture IDs (`wait_timeouts`) and count (`wait_timeout_capture_count`), and waits with no subsequent saved capture (`unattributed_wait_timeout_count`), in worker and merged manifests. Attribution is to the next saved capture in the same worker, not proof that its own fixture caused the wait; an event with a null capture is retained without inventing an owner. The parent prefers structured events (including timeout durations) from completed worker manifests; output-derived events are the fallback for missing, incomplete or legacy manifests, including crashes/stalls. Logs and the review summary distinguish captures from waits; timeout warnings prevent a Passed review heading even if PNGs were saved. Historical manifests without event totals disclose an unknown wait count rather than treating affected captures as individual waits.

The Preview Action no longer uses Drive secrets or offers upload-format inputs. Build/release Drive uploads and their shared legacy-named helper (`tools/ci/upload_ui_renders_to_drive.py`) remain unchanged and outside this migration.

## Local commands and migration

Only run captures when the owner explicitly requests them; normal development still forbids agent tests/renders and fixture additions. Use fresh ignored output directories so old PNGs cannot masquerade as current captures.

```powershell
# Qt-free selection only:
uv run --frozen python tools/ui/preview_changes.py --base origin/main --head HEAD
# Owner-authorized capture examples (not implementation validation commands):
uv run --frozen python tools/ui/preview_states.py --category lora --fast --out tmp/ui-previews/lora
uv run --frozen python tools/ui/preview_states.py --slow --out tmp/ui-previews/all
uv run --frozen python tools/ui/preview_workflow_file.py --workflow src/dtflow/resources/workflows/reference_workflow_v1.json --out tmp/ui-previews/workflow
```

The `tools/ui/render_*` screenshot modules/configs are now `preview_*`; `capture_workflow_preview.py` is `preview_workflow_file.py`. Worker reports use `preview-manifest-…` and `preview-details-…`; default state output is `tmp/ui-previews`. Stable screenshot IDs/filenames and fixture scenarios are unchanged. `preview_lora_design.py` retains the separate historical Designer-reference captures as a local-only command, not the runtime LoRA category. Old dated plans/release evidence retain their original names/paths as historical references; use this guide for current commands. Other screenshot tools, native benchmarks and application rendering APIs are not renamed.

See [development](development.md), [tool reference](../../tools/ui/README.md), and the [implementation ledger](../plans/2026-11-13-ui-previews.md). Source/static checks do not establish an executed Preview run.
