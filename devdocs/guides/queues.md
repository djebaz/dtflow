# Queues and batch plans

Queues are available on the desktop Queues page and through the [CLI](cli.md). Creation persists paused items and does not generate. Start dispatches them; local/cloud dispatch submits real generation and may consume credits. Cancel interrupts local waiting, not confirmed remote execution. Unknown attempts are never silently replayed, and they never block other work.

## Desktop controls

The selected queue's items use seven columns: Preview, Prompt, Model, LoRAs, Parameters, Status and an icon-only provider-duration header. Tiles are cropped 64 px squares; hovering shows an aspect-fit preview up to 440 px. Prompts wrap to two visible lines, filenames hide weight-file extensions, and the first three LoRAs show gauges on one shared recorded-weight scale; the whole-cell tooltip lists all LoRAs. Full identifiers remain in tooltips. Duration is recorded backend wall time, not pure inference time; missing evidence shows `—`.

**Open in Images** waits for live gallery-backed image availability, including supported mapped paths, then clears incompatible Images search/model/LoRA/date/size/ratio filters and opens the exact output in Detail. A missing/excluded result reports an inline warning rather than silently opening another image. No generation is submitted. Preview caches revalidate visible results every three seconds and are cleared on navigation. Tiles and hover previews remain visible during background revalidation rather than blinking empty; retained pixels do not authorize Open in Images while the check is pending. Failed revalidation clears both sizes; lookup failure never permits raw-path fallback. New queue hides the previous item's Additional information card.

**+ New queue**, at the top right of the center, opens the composer in place of the selected queue; **Close**, or selecting a queue in the list, returns to it without discarding the draft. On first use the composer captures Generate's request and backend, then keeps an independent draft with its own editable **base prompt**. **Use Generate settings** explicitly replaces that base with the current Generate settings; **Copy to Generate** explicitly copies the draft request back without generating or copying the whole variation plan. Returning to Queues, selecting items or editing a saved queue does not overwrite either draft implicitly.

**Variation → Mode** is **Repeat** (N items with seeds s, s+1, ...) or **Cross** / **Pair** for comparisons. In Cross and Pair, each dimension is a row of values you pick, shown as chips (click a chip to remove it): **Models** and **Samplers** open the shared searchable list (models come from the Generate inventory; *Not listed* accepts an exact identifier), **Sizes** offer Generate's size and common presets or a typed `WIDTHxHEIGHT`, and **Steps**, **Guidance** and Inpaint **Strengths** use a bounded number box with **Add**. **LoRA sets** choose which LoRAs each item uses, replacing Generate's LoRAs per item: **Add…** opens the same checkbox and weight-slider editor as Generate, starting from Generate's LoRAs: the checked LoRAs become one set chip (`A: 0.8 + B: 0.4`), and none checked adds **None**, a set without LoRAs. Both LoRA editors list every LoRA the backend reports, not only those compatible with Generate's checkpoint, because a queue may cross several checkpoints; the planner still checks each item. Add the editor again for each further set; click a set chip to edit it in the same editor (its **×** removes it); an exact identifier is added with **Add custom** in the editor. LoRA sets and LoRA weights cannot be combined in one plan. **LoRA weights** vary the weight of any LoRA, on the Generate form or not: **Edit…** opens the same checkbox and weight-slider editor on the current weights: check a LoRA and press **+** (or click anywhere on its slider, or release a drag) to collect each weight to try for it (click a weight to drop it; a checked LoRA with none collected uses its slider value). Apply replaces the chips with one `IDENTIFIER: weight` chip per LoRA and weight (a LoRA's chips are its weights, crossed or paired with the other rows). Prompts are one per line and seeds (`1; 2; 10..20`) stay typed. The item count updates as you edit and the preview table of the exact items follows a moment later; there is no Dry run button. Errors mark the field and appear in the count line. The same bounded planner serves the CLI and plan files.

**Random draws (#128).** Under *Draw at random*, a count above *Listed* draws that many distinct values at random from the values listed in the row (models, samplers, sizes, LoRA sets, steps, guidance, strengths, and LoRA weights per LoRA); for *Seed* it draws that many random seeds. One recorded **Plan seed** (with **Reroll**) drives every draw, so the same seed and inputs always give the same items and the preview table shows the exact drawn values. Each item records `plan.rng_seed` and `plan.random.<dimension>` evidence. Random ranges with a step (`min`, `max`, `step`) are available in plan files and the CLI. The planner stays bounded (at most 1000 items) and the duplicate rule still applies.

**Prompt variation (#129).** *Prompt variation* resolves the composer's base-prompt template, into many prompts, as a **Random sample** of N distinct prompts (seeded) or **Every combination** (at most 1000). Syntax: `{red|blue|green}` picks one option, `{2$$a|b|c|d}` picks two (joined with `, `), `{1-2$$...}` a range, `{3::red|1::blue}` weights an option, `__colors__` is a random entry of a wildcard list, and `\{` `\}` `\|` escape. Wildcard lists are one per line in **Wildcard lists** (`colors: red; blue; green`) or files `NAME.txt` (one entry per line, `#` comments) in the `wildcards` folder of the state directory; the file's SHA-256 is recorded. **Edit prompts** also scrambles the order of each prompt's comma-separated parts or words (*Shuffle parts* / *Shuffle words*), drops up to N parts and adds up to N of the **Parts to add** (parts are comma-separated phrases, or words with *Shuffle words*), all drawn from the same seed; edits with *Every combination* are seeded too, so the Plan seed and **Reroll** apply. A prompt that resolves to nothing is skipped. Creating a queue keeps the Plan seed, so its random draws and prompt variants repeat with unchanged inputs; image seeds follow the separate policy below. **Reroll** for new draws. Every item records its resolved prompt, and `plan.prompt_strategy`, `plan.prompt_template`, `plan.prompt_mutation` and `plan.wildcard.<name>` as evidence, so a Relaunch reuses the resolved prompts. Everything runs offline in the planner; there is no LLM rewriting, and it does not need the Scripts feature. Prompt text is never written to logs or file names. Prompt variation cannot be combined with a typed prompt list. Prompts are resolved on a background worker, so typing stays responsive (the count line reads *Resolving prompts…* meanwhile). Each draw count shows how many values its row lists (*2 of 5*). Emptying or replacing candidates preserves the requested count; impossible draws show an inline error, and a retained count stays editable so it can be reduced. *Add up to* likewise preserves its value and requires *Parts to add*. Unchanged polls preserve the current preview; only the latest background result is displayed. Generate seed 0 retains one resolved image seed across preview and creation until a queue is created or an explicit seed is observed. Referenced wildcard-file changes are detected through filenames, modification times and sizes; same-size edits preserving the observed timestamp are not detected.

The buttons at the top right of the composer create the queue: **Start now (N items)** creates it and starts it from this window (real, possibly billable generation; disabled while this window dispatches or generates, and while another process dispatches a queue), **Add to queue** saves it *up next* behind the running queue so it starts by itself (enabled only while a queue runs with a live dispatch owner), and **Save paused** saves it paused for a later Start. **Concurrency** beside them sets the new queue's cap. When the center becomes narrow (including while the right inspector stays open), all buttons (including Close) reflow together rather than leaving Close alone in an empty header; random input pairs and the prompt-edit controls adapt to two columns before falling back to one, and the plan-seed note moves below its controls. Hidden random dimensions do not leave gaps in that grid. The preview table is hidden for an invalid or empty plan and restored with valid preview rows, leaving its inline validation message visible. The composer scrolls vertically without horizontal clipping. In the left rail, the queue list alone scrolls; its Filter, Clear history and Clear paused queues controls remain fixed, with no second outer scrollbar. While you compose, the right column summarizes the queue you are about to create: backend, model, LoRAs with their weights, item count, what varies, the seed policy and Concurrency.

**Queue from any tab.** The **Queue** stack icon beside Run and the arrow on **Generate image** open the same popover. **Repeat N times** uses Generate's current request/backend; **New queue plan** uses the independent composer's captured base request/backend and current Pair/Cross plan, and is disabled without a valid plan. The popover discloses the chosen source, actual backend, the composer's **Concurrency** value and possible cloud credits before submission. **Start now** creates and starts the queue; while a queue or single generation runs, **Add to queue** saves it behind that work. After a single generation, automatic start needs this window to stay open; otherwise the queue stays paused for Start. It uses the shared creation/dispatch path; for Inpaint, Start is the consent to send the source and mask.

The left rail lists queues grouped as **Running**, **Up next** (in start order), **Paused** and **History** (finished and cancelled), newest first within a group. Each row shows the first prompt, model, LoRA count, item count and what the items vary in (for example `2 prompts, 2 step counts`), the backend, the creation time, a status chip and a small progress bar by outcome. The filter box matches any of those words, the status or the queue id. The list reads queue summaries only (counts and the first item); items and events are read for the selected queue alone, and it refreshes by itself every few seconds while the Queues tab is open (every second while anything runs), so queues created from the CLI appear without Refresh.

The selected queue's header is a card with the first prompt as its title and labelled lines below it: **Model**, **LoRAs** with their weights (one per line; *Varied per item* when items use different sets), **Plan**, **Provider** and **Created**. It has one status chip (its tooltip says which process dispatches it), one primary action that changes with the state (**Start**, **Start next**, **Pause** or **Resume**), **Cancel**, its own **Concurrency** (1 to 10, fixed once the queue has finished), **Relaunch** and **Remove**. Below it, a segmented bar shows finished items by outcome, and the ✓ ✗ ? – count chips filter the items table to succeeded, failed, no-result or cancelled items; with none checked every item shows. Outcomes of actions appear in the shared bottom overlay. **Remove** (also on the list's context menu) deletes one paused, finished or cancelled queue record after an inline confirmation; **Clear history** removes finished and cancelled ones and keeps paused queues. **Clear paused queues** (under it, showing the count) removes only paused queues that still have pending work, at once (no confirmation; the button shows the count); each queue is checked again inside the removal transaction, so one that started, went up next or finished meanwhile stays and the result reports removed and skipped counts. None of them touch attempts or saved images, and a running or up-next queue cannot be removed.

The small **Copy prompt** icon beside the selected queue title copies the complete first-item prompt to the clipboard. It does not change Generate or the composer.

**Relaunch** (header, the list's context menu, or **Relaunch last** in the empty state for the newest queue with same seeds) runs a queue's recorded items again as a **new** queue: *Same seeds* (an exact rerun), *New seeds* (items that shared a seed share one new seed), or either for *Only failed items* (failed, cancelled and no-result). The new queue starts at once, or waits up next when this window is dispatching; while another process dispatches it is saved paused. The original queue, its items and attempts are untouched: nothing is replayed and a no-result attempt stays no result. Staged Inpaint items reuse their recorded inputs and consent, which Start checks again; if the inputs are gone the relaunch is refused and nothing is created. **Retry item** in the item panel reruns the selected failed, cancelled or no-result item **in place** (#240): the same row runs its recorded request again, same settings and same seed, as a new attempt; no new queue is created. The earlier attempt stays recorded as it ended (a no-result attempt stays no result; its request may still finish on the server, so retrying it can make a second image) and the queue's history lists the retry; the item panel shows the latest attempt. Retrying an item of a cancelled queue restarts that queue for this item only (its other cancelled items stay cancelled); while the cancelled queue is still stopping, Retry is refused until it has stopped. If other items of the queue are still pending or running, the retried item joins that run (or waits for Resume on a paused queue); otherwise the queue starts again at once, or waits up next when this window is dispatching. Nothing retries without the click. Relaunch and Retry item are real, possibly billable generation, like Start.

**Edit as new queue…** loads a text-to-image queue into the composer only, without changing Generate, the original queue or execution state. Newly composed queues retain a bounded, versioned copy of their base request, source prompt, original variation settings, count and local asset selections in queue-only storage, atomically with their resolved execution items. Loading restores that authoring input rather than treating variation results as the source prompt. Change the draft, then explicitly Save paused, Add to queue or Start now. Referenced wildcard files are read from their current contents; saved authoring input does not preserve external file contents. Inpaint queues cannot be edited this way.

**Older queues** without complete composer source show a reconstruction warning. Their resolved items become Cross, Pair or Repeat dimensions where possible; a consistently recorded prompt template can be recovered, but missing random-draw settings, wildcard lists and authoring choices are not guessed. The original resolved execution items remain unchanged. **Relaunch** continues to reuse those resolved items instead of re-evaluating the authoring template.

Queues and items stay in stable order. Start, Pause, Resume and Cancel use the shared queue services. Cancel takes effect immediately, without confirmation, and does not confirm remote cancellation: an item interrupted after submission ends as *no result*. The item panel summarizes outputs with Open folder; shortened attempt IDs expose full IDs in tooltips. A failed item's **Outcome** line shows the original reason, with the provider's own wording kept (for example a DT+ quota, sign-in or permission message), for every item kind: plain generations (including ones rejected before anything was sent), script runs and their steps, and workflow runs; the Outcome line says Failed and the note under it gives the reason. Generate shows the same text. The error code appears only when a record carries no message, and nothing is inferred from a missing output.

The right-side event evidence panel presents a compact activity stream keyed by queue position (for example, `#3 submitted` and `#3 completed - 12.34 s`). The durable queue evidence still records selected backend lifecycle events (preparing, submission boundary, received final artifacts and terminal response) plus item settlement; the UI hides redundant low-level lines and full request/item identifiers from the default view. Successful settlement includes the same client-observed backend duration saved with the image metadata. That duration runs from submission boundary to terminal response and may include provider-side queueing or serialization; DTFlow does not call it pure generation/inference time. Progress and preview events are intentionally not persisted into this diagnostic stream.

**Concurrency** in the header posts a cap for the selected paused, waiting or running queue only. **Concurrency** in the composer sets the cap of queues you create; with cloud chosen it also shows and saves the shared cloud default for new cloud queues. Values above two are tinted, and the limits are explained in the tooltips. Provider and shared memory limits still apply. A saved change shows no overlay; a refused one does.

Start holds the state ownership lock for the entire dispatch run. Other processes can read, post controls and add paused queues, but cannot own another generation or dispatch in that state directory. See [runtime ownership](../architecture/runtime-layout.md).

### Reusable queue templates

In the composer, **Save template…** saves a new named text-to-image authoring recipe. **Load template…** opens a searchable local library with the source-prompt excerpt, backend requirement, model, mode and seed settings. Loading changes only the composer: it never creates a queue, changes Generate, switches the connection, uploads an asset or starts generation. If your current draft differs, Confirm explicitly replaces it; Cancel or Escape keeps it. A different backend requirement also needs explicit rebinding to the current connection, with no automatic model or LoRA substitution.

The loaded name shows **modified** after editing. Save creates a separately named recipe; it never silently overwrites the loaded one. In the library, **Update…** explicitly replaces the selected recipe with the current draft, **Rename…** changes its name, and **Delete…** removes only that recipe. Existing queues, attempts, outputs and the current draft survive template deletion. Closing/reopening the composer preserves its draft; templates also survive app restart, queue-history removal, cache cleanup and `--no-cache` launches.

Recipes retain the original positive/negative prompt, base settings, ordered Pair/Cross values, LoRA sets/weight sweeps, Repeat count, random draws, inline wildcard lists, prompt edits, plan seed, image seed and per-queue concurrency. Loading a saved cap does not change the shared cloud default. Random recipes require a valid explicit plan seed before saving; loading does not reroll it. **Reroll** remains explicit. External wildcard names use current local files, not archived contents: missing files surface in normal plan validation, and changes can change results. The plan preview and explicit queue creation use the existing shared planner.

The stored image seed is the concrete seed captured by the independent queue draft. Generate's seed-0 random choice is already resolved when that draft is captured; loading does not silently request another random image seed. Use Generate settings explicitly to capture another base request, or edit the plan's listed/incrementing seed policy. The separate plan Reroll action does not change that base image seed.

Checkpoint, sampler and LoRA availability still need validation against the chosen backend/account. Unlisted choices are retained for review, not silently dropped; local prepared-asset candidates are resolved afresh when explicitly creating a queue. A later connection change requires loading/rebinding again or explicitly using Generate settings. Templates extracted from incomplete older queue evidence stay labeled as reconstructions and require review; missing authoring input is never invented. Semantically incomplete plan text remains an editable draft with the existing validation feedback, not a promise of executable generation.

This first library supports text-to-image only. Image/mask portability, import/export, folders/tags and cloud sync are not implemented. Prompts are private durable user data, not diagnostic attachments; no template content, execution IDs, prepared receipts, credentials, private endpoints or image paths are exported to logs. Invalid/newer library schemas and out-of-range spin/combo values are refused without replacing your draft or resetting the library. Limits are 128 named recipes, 80-character names, 256 KiB per recipe and 4 MiB total serialized recipe data. Native Windows/DPI and packaged acceptance remain separate from offline tests.

### Editing and up next while a queue runs

Every Generate, LoRA, Inpaint and Plan input stays editable during a generation or a queue run (#133). A running request is the immutable snapshot taken when it started; edits only shape the next request or queue, and Generate's Effective request says so while a single run is active. The composer stays available during a run: **Save paused** saves a paused queue and **Add to queue** puts it up next.

While this window dispatches, **Start** on another paused queue reads **Start next**: the queue waits *up next* and starts by itself, on the same dispatch ownership, when the running queue ends (#125). Once the running queue has handed out its last item and a slot is free on the same backend (within the backend's own maximum), the next queue starts early and fills that slot (#174); this window owns and can Stop both, the combined cap is still enforced per backend, a start-up failure of the early queue pauses only that queue and ends early starts, queues settle in order, and a paused or cancelled queue never overlaps. Up-next queues run in the order shown in the list's Up next group (`Up next 1`, `Up next 2`, ...), each on its own recorded backend. **Earlier** and **Later** (shown only for a waiting queue) move it; **Pause** takes it out of the order and leaves it paused. Pressing **Generate** while a queue runs adds the request behind it as a one-item up-next queue (an Inpaint edit is staged the same way as a queued edit). The header run control counts the waiting queues.

**Cancel** on a waiting queue cancels it at once (it holds no reservation, so nothing of it ran); from the CLI, `queue pause` and `queue cancel` on a waiting queue likewise take it out of the order or cancel it immediately. The CLI cannot enqueue or reorder, and `queue start` runs only the queue it names.

Auto-play continues after a queue finishes or is cancelled; a paused running queue holds the order until you Resume or Cancel it. Picking the next queue and starting it are one step, so a Pause, Cancel or reorder made just before is respected. Auto-play stops when dispatch itself ends: a failure, a local stop or closing the window. Whenever the owner stops, and whenever a new owner opens the state (a restart included), every waiting queue returns to paused, so nothing starts without a live owner. Joining the order needs a live owner: once the running queue has ended, **Start next** is refused and Generate saves its one-item queue paused, saying so.

### Elapsed time and ETA

The shared bottom progress row and the header Run control tooltip show elapsed wall time since the latest dispatch start, including pauses and provider waits. A new dispatch after a stop or restart starts a new elapsed interval. If no reliable start timestamp exists, elapsed time is omitted.

After the **first successful item with a usable recorded duration**, a labeled estimate appears: median successful `backend_elapsed_seconds` × remaining items (pending + running) ÷ items actually running. Failed, cancelled and unknown items do not contribute durations; the configured maximum is never substituted for observed concurrency. A separate presentation timer counts down once a second, even while a database read is pending. Unchanged polls do not restart it; each observed item settlement, timing-sample update or change in running concurrency rebases it. The display uses minutes:seconds (hours:minutes:seconds for longer runs), reaches zero without claiming completion, and disappears while paused, cancelled, finished, without an active owner or with no running items. Resume starts a fresh estimate. Plans varying model, size or steps say the estimate is rough.

Resume rebasing uses the latest applied durable Resume event, so even Pause and Resume between two polls reset the estimate. This leaves elapsed time's dispatch-start timestamp unchanged.

Durations include provider-side queueing and are not pure inference time. The blue bar continues to show real finished counts, never estimated progress. After each item settles, the dispatcher records a durable timing snapshot event (elapsed wall time and the ETA at that moment, counting the lane the next claim refills). The Events pane lists it as `elapsed + ETA = projected total`; it is skipped before the first successful duration sample and is not a measured completion time. The countdown seeds from a snapshot only while it is newer than the latest start or Resume and no live settlement, sample or lane change has superseded it.

## CLI examples

```bash
uv run dtflow queue add -b fake -p "Offline fixture" -k 10 -j 4   # persist a paused queue of 10 items (seeds s, s+1, ...)
uv run dtflow queue add -b fake -p "Offline fixture" -r plan.json -u   # dry run: print the exact items of a plan, create nothing
uv run dtflow queue add -b fake -p "Offline fixture" -r plan.json   # persist a paused queue of the planned items
uv run dtflow queue start QUEUE                                   # become the dispatch owner and run it (Ctrl-C interrupts)
uv run dtflow queue pause QUEUE                                   # from another terminal; also resume, cancel, cap -j N
uv run dtflow queue show QUEUE                                    # items in queue order with state, attempt and outputs
uv run dtflow queue relaunch QUEUE -f -n                          # a new paused queue of the failed items, new seeds
uv run dtflow queue relaunch QUEUE -i 3                           # item 3 again, as a new one-item paused queue
```

`queue relaunch` persists a new paused queue from the named queue's recorded item requests (fresh request identities, the same backend and maximum unless `-j` is given). `-n/--new-seeds` draws new seeds, `-f/--failed` keeps only failed, cancelled and no-result items, and `-i/--item N` (repeatable) takes exactly those positions (`-f` and `-i` are exclusive). Each new item records `relaunch.source_queue`, `relaunch.source_position` and `relaunch.seed` evidence; the source queue position (and, with new seeds, the source seed policy) is dropped. It contacts no backend; `queue start` dispatches it. The original queue and its attempts are not changed.

## Dispatch, restart and uncertainty

`queue add` persists independent, immutable resolved items (it contacts no backend and does not support `-r/--prefix`; put prefixes in the prompt) in a queue that starts paused. `queue start` makes that process the single dispatch owner of the state directory, resumes the queue and rolls: it admits the next item as soon as any reservation is released, never exceeding the queue maximum (`-j` on `add` or `queue cap`) or the backend's own limit (local gRPC is one lane).

Another process can run `list`, `show`, `add`, `pause`, `resume`, `cancel` and `cap` while dispatch is running: controls are stored and polled, a queue added meanwhile is saved paused over a short separate connection, and `start` needs the state directory to itself. Up next is a desktop feature: the CLI has no command to queue behind a running dispatch, and `queue start` runs the queue it names.

A paused, idle dispatcher keeps polling until resumed or interrupted. `cancel` stops pending items and interrupts local waiting on active ones; it never claims remote cancellation, so an item interrupted after submission is `unknown`.

An `unknown` item (shown as *no result* on the desktop) means the request may have reached the server but no final result arrived, so it most likely failed. It releases its reservation, never blocks the backend, other queues or the rest of its queue, and the attempt is never replayed automatically. `queue start` exits `3` when any item is unknown, failed, cancelled or pending. The former `queue override` command is a hidden, deprecated no-op kept for old scripts; it prints a note and records nothing.

Local Draw Things runs one request at a time and stopping local waiting does not confirm that it stopped rendering. After a *no result* item, the next item is dispatched right away and may wait on the server behind the abandoned job; its total deadline includes that wait. This is accepted: the server queues requests itself, and a local run costs no credits.

After a restart queues are restored paused, completed results are kept, and no item that reached the remote boundary becomes eligible again. `queue start` exits `0` when every item succeeded, otherwise `3`.

Direct DT+ text-to-image reserves 32 MiB per in-flight request against a 320 MiB shared admission budget, permitting up to ten client-side submissions when Concurrency is ten. This is not measured process RAM or verified server-side entitlement. Image edits can reserve more; local Draw Things remains one lane. The cloud default stays four until changed.

## Plan files and dry runs

`queue add -r/--plan FILE` replaces `-k/--count` (the two are mutually exclusive) with a bounded, deterministic batch built from the resolved base request (the usual `-p`, `-m`, `-c`, `-l` options) plus varied dimensions; `-u/--dry` prints the exact item table (index, varied values, resulting seed) and the count as JSON and persists nothing, for a plan or a plain `-k`. A plan file is versioned, credential-free JSON, user-supplied (it is never copied into state; each queued item records its resolved request and `plan.*` evidence):

  ```json
  {"schema": "dtflow.queue-plan", "version": 1, "mode": "cross",
   "dimensions": {"prompt": ["a cat", "a dog"], "steps": [4, 8], "size": [[512, 512], [768, 512]],
                  "lora_weight": [{"identifier": "EXACT_LORA", "weights": [0.6, 1.0]}]}}
  ```

  ```json
  {"schema": "dtflow.queue-plan", "version": 1, "mode": "cross",
   "dimensions": {"loras": [[], [{"identifier": "STYLE_A", "weight": 0.8}],
                            [{"identifier": "STYLE_B", "weight": 0.6}, {"identifier": "DETAIL", "weight": 0.4}]]}}
  ```

  Modes are `seed` (`"count": N`, seeds increment from the base seed, the `-k` rule), `pair` (equal-length dimensions matched position by position; unequal lengths are an error, never truncated) and `cross` (every combination, the last listed dimension varying fastest).

Dimensions are `prompt`, `model`, `seed` (a list or `{"start": S, "count": N}`), `steps`, `guidance`, `sampler`, `size` (`[width, height]` pairs, never independent axes), `lora_weight` (weights for a LoRA already given with `-l`; no compatibility is inferred) and `loras` (whole LoRA sets, each a list of `{"identifier", "weight"}`; `[]` is no LoRA). A `loras` set replaces the base request's LoRAs for that item and cannot be combined with `lora_weight`; a receipt bound with `-z` stays bound only to items whose set includes its LoRA, and each item records only the receipts it carries. On the desktop, a set naming a custom cloud LoRA with a confirmed receipt binds that receipt even when the LoRA is not on Generate. Version-1 files without `loras` read as before.

**Random dimensions (version 2).** Any dimension may be `{"random": {"count": N, "from": [values]}}` (N distinct picks), `{"random": {"count": N, "min": a, "max": b, "step": s}}` (numeric: steps, guidance, strength, and `weights` inside a `lora_weight` entry), or for `seed` `{"random": {"count": N}}`. The top-level `"rng_seed"` records the plan seed; `queue add --rng-seed N` overrides it and a plan with random dimensions and no seed gets a fresh one, printed in the result. `prompt` may be `{"variation": {"strategy": "random"|"all", "count": N, "template": "a {red|blue} fox, __place__", "wildcards": {"place": ["forest", "meadow"]}, "shuffle": "parts"|"words", "drop": 1, "add": ["bokeh"], "add_max": 1}}`; without a template the base prompt is the template, `__name__` lists missing from `wildcards` are read from `--wildcards-dir` (default `STATE/wildcards`), and `--dry` prints the drawn table with the `rng_seed`.

In `pair` and `cross` the base seed stays fixed for every item unless a `seed` dimension is listed or the plan sets `"seed": "increment"`.

A plan larger than 1000 items, an empty dimension or duplicate combinations without distinct per-item seeds, unequal pair lengths, a value the request validators reject or a seed overflow fails before anything is created.

Plan files use `dtflow.queue-plan`, version 2 (version 1 files still read; random dimensions need version 2). Repeated dimension values are allowed only when each item gets its own seed; otherwise duplicate combinations are refused. See the [planning decisions](../plans/2026-10-04-phase-6-queue-planning.md#decisions-taken-in-the-pull-request) for the precise contract.
