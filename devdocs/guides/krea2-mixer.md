# Portable Krea2 mixer adaptation (#216 / PR #219)

Reimport or reload `tools/scripting/krea2_lora_mixer_portable.js` as a new immutable script version. New DTFlow builds use cached backend inventory, catalogue metadata and confirmed local receipts instead of the example's fixed LoRA list. Refresh Generate inventory explicitly first if no snapshot is loaded; Inspect/Setup never performs that network refresh automatically. The original Draw Things branch retains its fixed preset, marker-PNG settings and sequential canvas exports. The original supplied archive is not modified.

## Settings, preview and consent

The DTFlow flow is **Setup settings > Preview plan > exact chunk review > Proceed to Run Script > Run Script**. Preview forms advance the same parked child locally without creating a queue, opening a provider or granting generation permission. Choose Finish preview for a complete zero-queue preview; Reload Setup starts another preparation. Only the final Run Script action creates/adopts a queue. Cancellation, failed validation and preview completion never replay jobs. A private ScriptRun/form record may exist for preparation provenance; it is not a queued generation job.

All authoring inputs remain together in the settings view. The review shows the full plan ID, total job count, selected global range, model/steps/dimensions/sampler/guidance, prompts, negative prompt, and each chunk job's prompt index, explicit seed, LoRAs/exact weights and output filename. Metadata-mismatched and unconfirmed-availability entries are listed as skipped, not silently treated as usable. Listed, locally prepared, metadata-matched and unknown are distinct observations; selecting unknown compatibility requires its explicit option. None proves current server availability or LoRA application.

## Configuration and bounded continuation

The disclosed reduced-fidelity DTFlow configuration inherits Generate's checkpoint/steps and unchanged unsupported baseline fields, changing only currently mapped width/height, sampler, guidance, seed and LoRAs. It does not claim original `krea_2_turbo_q8p.ckpt` shift, clipSkip, tiled decoding or guidance-embedding fidelity; those mappings remain #115. Sampler and exact checkpoint/LoRA acceptance are backend-specific. No source pixels/masks or broad compatibility are added.

Plans are bounded to 10000 jobs. A chunk is at most the actual captured run allowance (1..32), not a hard-coded 30. Random selection uses a per-global-job seeded generator; comparison enumerates singles/pairs for each prompt, with a fixed image seed. Chunk start is global in both modes. Changing only start, chunk size or concurrency does not change the full plan ID; changing source version, generation context or planning inputs does. Selected jobs carry that full SHA-256 and global index as `script_plan`/`script_job` request evidence. Continue manually only after inspecting durable attempts; matching a plan ID is not proof that earlier jobs ran, succeeded or are safe to repeat. Preferences do not provide an execution cursor or automatic deduplication. Changed saved plan identity is explicitly warned about in the preview.

## Durable preferences

The plan fingerprint also binds the known content SHA/size of selected prepared LoRAs without exposing receipt IDs or raw hashes in the inventory API. The adapter rechecks it after actual admission refreshes receipts, before calling the batch hook; changed prepared content stops without a child submission and requires a fresh preview. Built-in remote model/LoRA bytes remain backend observations, not a content-verification guarantee.

Remember stores source-version authoring preferences in `<state>/script_preferences.sqlite3`, independent schema 1, not cache or output markers. Selections are keyed by LoRA identifier, not dynamic checkbox position. Bounds are 128 source versions and 256 KiB ASCII JSON per version; reaching a bound fails the preference write without evicting existing settings or truncating active inputs. Turning Remember off leaves the prior record unchanged. Unreadable/newer schemas fail clearly and are not reset. The database contains private prompts/settings; never attach it as public diagnostic evidence. It is not execution history, dispatch consent or automatic resume state.

## Read-only inventory and authoring APIs

`__dtflowScriptHost.listLoRAs(offset = 0)` returns pages of at most 100 entries from one captured projection, with `items`, `nextOffset`, `total`, `omitted`, `model`, `observedAt`, `cached` and a notice. Follow `nextOffset` until `null` to enumerate safe symbolic known definitions, including unlisted entries. The projection is bounded to 4096 LoRAs; path-like/control-character identifiers are withheld with an explicit omitted count rather than exposing private paths. Entries contain `file`, bounded display `name`, `listed`, `prepared`, `compatibility`, `compatibilitySource`, `eligible` and `reason`; no credentials, endpoints, local file paths or remote receipt IDs are returned. Refreshing the snapshot requires a new preparation after Generate inventory refresh.

The native mixer bounds candidate switches to 400. For a larger eligible pool, set its documented `LORA_NAME_FILTER` substring and reimport that source version; the API does not silently discard entries. Skipped text is bounded with an explicit indication when additional entries require API pagination. Catalogue-only entries are known definitions, not proof of remote absence or readiness.

Other DTFlow-only helpers are `runLimits()`, `setupForm(title, builder, confirmLabel)`, `loadPreferences()`, `savePreferences(object)` and `planId(object)`. `setupForm` marks one preparation-only request; it does not release the independent generation gate. Preference writes require a form answered explicitly, including explicit headless supplied answers rather than implicit defaults. The adapter detects these extensions; they are not Draw Things APIs. Headless CLI execution can open its explicitly selected backend, so the desktop's zero-provider preparation claim is not a claim about every CLI invocation.
