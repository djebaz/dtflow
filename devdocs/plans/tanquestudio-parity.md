# TanqueStudio port parity matrix

**Status:** Planned inventory; no row claims an implemented DTFlow feature.  
**Purpose:** Track the intended full port without making every feature a prerequisite for Qt.  
**References:** [roadmap](initial.md), [Phase 2](phase-2-backends.md), [Phase 3](phase-3-cli.md), [ecosystem research](../research/dtflow-ecosystem-research-report.md), [release roadmap](releases.md).

## Evidence and maintenance

This is an initial feature-family matrix based on the report's selective upstream inspection, not a claim that every TanqueStudio function has been enumerated. During Phase 2, reconcile the upstream source/UI/docs into a version-pinned feature inventory, adding missing rows before claiming full parity. Record exclusions and their rationale explicitly.

Evidence below refers to report Sections 5.1–5.7 or official backend sources in its appendix. Planned service names describe ownership, not existing Python APIs. App means Draw Things gRPC/Bridge; cloud means direct DT+; fake coverage is offline simulation. Backend support is unknown unless the report records stronger evidence.

A row advances to accepted only with implementation references, actual validation evidence and any remaining limitations. Update this matrix in the PR implementing each feature. Do not silently drop a row because an upstream API is missing: retain a blocked/conditional status and the evidence needed.

Acceptance cells describe required behavior, not independent test suites for every phase named in a row. The earliest authoritative layer owns shared semantics; later CLI/Qt/planner/workflow surfaces test only their new wiring, presentation or policy unless they introduce a genuinely different implementation path. Live/release evidence proves deployed compatibility or complete composition and does not require lower-layer protocol, persistence or scheduler matrices to be repeated.

A version-pinned inventory of the TanqueStudio sources, with additional candidate rows and exclusions, is in the [pinned inventory](../research/tanquestudio-inventory.md). Rows it marks new are not merged into the table below yet; reconcile them in a separate change.

## Phase gates and dependencies

Release gates in [the release roadmap](releases.md) require a complete Phase 5A generation/configuration path and Phase 5B queue surface for the first Qt executable. Image operations deliver in 9A/9B/9C slices; workflow files/execution in 10A precede optional richer visual authoring in 10B. These subdivisions preserve all feature rows; full parity remains tracked.

Phase 2 completes the inventory and shared contracts while implementing only the narrow initial adapters and test fixtures. Phase 3A delivers the usable txt2img CLI, bounded LoRA selection/preflight and durable attempts; Phase 3B delivers durable queues, tested rolling dispatch and custom cloud LoRA upload/reuse, including paused restart and uncertain reservations, before Qt. Phase 4 starts Qt promptly; full port parity is not its entry gate.

Testing ownership and execution tiers follow the [implementation plan](initial.md#8-validation-strategy). Before each later phase begins, refine only the scenario groups needed by the selected architecture/capability; do not turn every acceptance cell above into another integration test when its semantics are already authoritative elsewhere.

Later shared-service features should gain CLI exposure alongside implementation where meaningful. Visual painting, canvas manipulation, drag/drop and layout belong in Qt; a CLI should accept the resulting files/configuration rather than imitate interactive gestures.

Custom cloud LoRA upload/reuse is a Phase 3B pre-Qt gate for an explicitly verified converted-file subset under [the LoRA asset plan](lora-assets.md). Broad conversion, remote listing/deletion and unverified media operations remain conditional later milestones, not promises of current support. Phase 11 extends the token, secret, billing and error-handling foundations already required in Phase 2.
