# Retained-LoRA table responsiveness (#565)

## Cause and scope

[Issue #565](https://github.com/djebaz/dtflow/issues/565) reports Windows GUI gaps of 2098, 1778 and 584 ms with 96 retained files and three 1.1–1.2 s stall samples in `_render_lora_table` → `_fill_lora_table` → `_lora_row_actions`. These are owner-supplied historical measurements, not a new local profile or a measurement of this fix.

Source inspection identifies repeated work: entering Connection requests retained entries, family/format inspection, metadata/receipt reads and registry-only rows. The retained and family callbacks previously rebuilt unconditionally. The initial retained read also discarded family/format observations, forcing a second presentation change at scan completion. Independently, `GenerationPage.sync_backend` → `LoraPanel.sync_backend` → `set_enabled` requests a managed-table render even when its presentation has not changed. Every rebuild loaded `managed_lora_actions.ui`, connected two actions, polished widgets and recalculated geometry for every retained row. With 96 retained rows, that means 96 form loads per rebuild, including unchanged rows; this work matches the issue's sampled stack, but its individual timing has not been measured separately.

The owner expanded #565 on 2026-11-23 to include asynchronous catalogue setup, startup auto-connect and bounded reconciliation, then retained that scope after review. After supplying a 99-file Windows profile, the owner additionally authorized repairs to the measured worker-side family scan and Connection diagnostic coverage (AC-9/AC-10). Generation, queues, provider protocols, credential precedence, upload consent and persistent schemas remain unchanged.

## Implementation

- Retain previous family/format/q8p observations for unchanged content identities while a new worker inspection is pending; its delivered result still replaces those observations, including unreadable/missing-file outcomes.
- Compare a copied presentation snapshot, including entries, metadata, no-copy records, formats, q8p availability, selected-key confirmations, backend and current busy state. An identical render request leaves the table and selection untouched.
- Reuse each existing row's canonical Designer action host. Update its current identity and metadata before enabling its controls; click handlers resolve those current values rather than an old row's captured identity. Existing eligibility, status text, tooltips and service calls remain authoritative.
- Reconcile changed cells and reused/new controls against an 8 ms cooperative GUI-thread budget, continuing with a zero-delay timer instead of paying a timer interval for every row. A single row/form operation cannot be preempted, so this is not an 8 ms latency guarantee. Busy/eligibility-only changes update existing controls without replacing cells.
- Keep unchanged rows selected. On a physical reorder, restore by exact content identity unless a newer user selection/deselection wins. Current rows remain actionable during reconciliation; clicks validate the visible identity against current metadata, backend/key and busy state. A genuinely obsolete action gets visible feedback rather than silently doing nothing.
- Removal cancels index-based update work and restarts from a fresh projection on completion, including failure/no-op outcomes. Qt timers are window-owned and shutdown callbacks refuse further work.
- Keep the existing GUI-gap, stall-sample and retained-read diagnostics unchanged. No competing diagnostic writer or new sink is introduced.

## Owner-requested follow-up: AC-6 through AC-8

- Catalogue construction starts with an empty, I/O-free `Catalogue(deferred=True)`. `services/catalogue_setup.py` reads a fresh in-memory catalogue snapshot and computes family/checkpoint choices on a worker. Snapshot consumers do not stat/reread user metadata from GUI callbacks; metadata changes explicitly request another snapshot. Cold profile/community classification reads are warmed by the worker, and dependent presentation waits for catalogue readiness without pruning saved LoRAs.
- One active catalogue read and one replaceable latest request bound preparation. Qt builds detached selector models in batches of 16 with zero-delay continuation, then swaps them with signals blocked. Previous choices remain visible until publication; stale backend/key/settings/shutdown work is rejected. Credential revalidation returning the same inventory observation resubmits pending filter/selection intent under the new revision instead of losing it. Missing cached inventory still permits an empty classification snapshot to finish loading.
- Catalogue failures retain an explicit retry message through subsequent statistics refreshes and expose failure, not perpetual loading, to the meter. Refresh or a filter change retries explicitly. Worker setup and subsequent filtering share one LoRA-candidate rule.
- Startup auto-connect already runs once on the shared `AsyncRunner`, independently of catalogue readiness; credentials are read off Qt and the service owns provider timeout/cleanup. Preserve that behavior: an early edit changes which current selection is checked; an early manual Check consumes the queued automatic check. The new shutdown-result guard stays. No second runner, polling, generation or upload is added.
- Presentation snapshot comparison excludes descriptive source metadata that the table does not display, avoiding a full copy of that unrelated per-file payload on every render request. Canonical metadata remains available to the existing explicit metadata overlay.

The attached review of `20d75d0` reports Linux/offscreen timings of 3–7 ms for catalogue setup and about 4 ms for cells/reused controls. Those are reviewer-supplied measurements, not Windows attribution or measurements run by this agent. The owner explicitly chose to keep async scope and repair the reported races/friction, not waive AC-6/AC-8. Catalogue I/O originally occurred in the Generate-controller phase; the broad later backend/setup phase also includes Connection wiring and cannot be attributed to catalogue work alone. No startup speedup is established.
