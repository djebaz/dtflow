# ComfyUI + Draw Things: integration and reuse audit

**Date:** 2026-11-04. **Status:** Preliminary, source-backed research; further investigation stopped at the owner's request to preserve the weekly token allowance. This is not the originally requested complete audit or an implementation decision. Section 10 records the owner decisions taken afterwards.

**Update (2026-11-04):** Subsequent owner discussion resolved the product direction and V1 boundaries. [Section 10](#10-owner-decisions-and-current-v1-findings-2026-11-04) records those **decisions and current DTFlow source observations** (10.7 adds code-checked constraints and 10.8 a proposed implementation plan with open owner decisions), separate from the original static audit and its still-unverified upstream behavior. See [issue #223](https://github.com/djebaz/dtflow/issues/223) for implementation tracking. The older options and open decision gate below are preserved as historical research.

**Question:** Should DTFlow reuse the official Draw Things ComfyUI extension or ComfyUI execution machinery to support multistep image workflows instead of reproducing Draw Things' implicit canvas/workspace scripting semantics?

## Executive assessment

The official extension establishes a concrete architectural option: ComfyUI owns a graph and Draw Things performs generation through gRPC. Its sampler accepts explicit image/mask inputs and returns images that can feed later operations. This matches the desired direction better than emulating a moving, zoomable virtual canvas. However, the inspected extension is **not a drop-in replacement for DTFlow's generation services**: automatic generation retries, partial-result handling, optional error images, global cancellation state and absent direct DT+ authorization are material differences.

**Recommendation, not an approved plan:** retain DTFlow's generation, authentication, attempt, input-snapshot and saving authorities. Consider either a narrow ComfyUI-to-DTFlow adapter or native explicit image/mask workflow operations. Do not copy the extension wholesale or fork ComfyUI's executor before deciding whether existing ComfyUI graph/custom-node compatibility is actually required. The useful discovery is an existing integration to study, not proof that adopting its whole runtime is the lowest-cost solution.

## 2. What the official extension actually provides

The [pinned README](https://github.com/drawthingsai/draw-things-comfyui/blob/91fe91bc4eb849bc2cadde14e320d274499df45f/README.md) describes a ComfyUI custom-node extension connecting to the Draw Things application or `gRPCServerCLI`. Its cloud route is the application's **DT+ Bridge Mode**, not DTFlow's native direct-cloud route.

The [sampler interface](https://github.com/drawthingsai/draw-things-comfyui/blob/91fe91bc4eb849bc2cadde14e320d274499df45f/src/nodes.py#L50-L159) exposes explicit image and mask inputs, prompts, model, seed, dimensions, strength, LoRA, ControlNet, upscaler, refiner and hints, returning IMAGE/AUDIO ports. This permits graph-level image handoff without upstream JavaScript canvas emulation. It does not establish arbitrary model compatibility, durable step recovery or correctness of every exposed setting.

The three bundled [example workflows](https://github.com/drawthingsai/draw-things-comfyui/tree/91fe91bc4eb849bc2cadde14e320d274499df45f/example_workflows) cover text-to-image, inpainting, and LoRAs/upscaler/refiner. Each contains one DrawThingsSampler. They are examples of ports/composition, **not a supplied, accepted two-generation output-to-input chain**. Upscaler/refiner fields are generation configuration modifiers, not evidence of independently callable image-processing services ([configuration mapping](https://github.com/drawthingsai/draw-things-comfyui/blob/91fe91bc4eb849bc2cadde14e320d274499df45f/src/config.py#L153-L174)).

## 4. Image, mask and configuration differences

- **Fitting differs:** the extension resizes to fill the target and center-crops. DTFlow's preparation contract uses recorded centered aspect-preserving fitting/padding and source-grid masks. Directly swapping encoders can change regions and composition ([extension fitting/encoding](https://github.com/drawthingsai/draw-things-comfyui/blob/91fe91bc4eb849bc2cadde14e320d274499df45f/src/image_handlers.py#L415-L509), [DTFlow contract](../architecture/image-operations.md#preparation-contract-source-implementation)).
- **Mask threshold differs:** extension byte values below 50 become 0; others become wire value 2 after fitting. DTFlow thresholds luminance above 127 into binary source masks before controlled fitting. Both using 0/2 on the wire does not make their preparation semantics equivalent ([mask encoding](https://github.com/drawthingsai/draw-things-comfyui/blob/91fe91bc4eb849bc2cadde14e320d274499df45f/src/image_handlers.py#L512-L574)).
- **Batch handoff is not arbitrary mapping:** ordinary source/mask encoding uses the default batch index 0; a Comfy IMAGE batch must not be assumed to generate independently for every input image ([source preparation](https://github.com/drawthingsai/draw-things-comfyui/blob/91fe91bc4eb849bc2cadde14e320d274499df45f/src/draw_things.py#L105-L125)).
- **Seed fidelity needs review:** `int(seed % 4294967295)` maps the upper uint32 value to zero and negative one to 4294967294. This is a source-arithmetic observation, not a run result ([seed mapping](https://github.com/drawthingsai/draw-things-comfyui/blob/91fe91bc4eb849bc2cadde14e320d274499df45f/src/config.py#L247-L248)).
- **Falsy defaulting changes explicit zero:** `refiner_start or 0.7` substitutes 0.7 for zero; do not mechanically inherit this configuration mapping ([mapping](https://github.com/drawthingsai/draw-things-comfyui/blob/91fe91bc4eb849bc2cadde14e320d274499df45f/src/config.py#L153-L174)).

A DTFlow workflow should record exact parent output identity, selected output index, normalized input identity, fit/crop transform, mask identity, effective settings and child attempt. That is a proposed requirement, not an existing general workflow schema. Current script request construction still rejects masks and constructs the supported txt2img subset ([ScriptHost](https://github.com/djebaz/dtflow/blob/6d8401f022df3ffa209cdfb0d077b700986f9e1d/src/dtflow/scripting/host.py#L244-L314)); this audit does not enable image chaining by itself.

These are not sufficient evidence for credential-scoped fresh dispatch authority.

Preserving selected models on disconnect and coalescing metadata queries are useful UX references, not reasons to copy network or ownership policy. A future integration needs explicit permission boundaries for authoring-time network access, source/mask transfer, generation and custom-node code. A workflow/custom-node installation must not be treated as harmless declarative data or as equivalent to DTFlow's bounded JavaScript subprocess.

## 6. Can we reuse ComfyUI's engine itself?

The selected current [executor](https://github.com/Comfy-Org/ComfyUI/blob/5f415e31abfd837870bbc733ba1e158de71ed985/execution.py) imports torch, model/memory management, node registries, caching and application components. The [graph implementation](https://github.com/Comfy-Org/ComfyUI/blob/5f415e31abfd837870bbc733ba1e158de71ed985/comfy_execution/graph.py) also depends on Comfy node interfaces. Therefore extracting a standalone scheduler is an engineering/refactoring project, not a verified lightweight package substitution.

The selected `PromptQueue` implementation stores its queue/history in process lists/dictionaries ([source](https://github.com/Comfy-Org/ComfyUI/blob/5f415e31abfd837870bbc733ba1e158de71ed985/execution.py#L1310-L1456)). This observation is limited to that queue implementation; it is not a claim that every Comfy subsystem lacks persistence. Its history API must not be assumed to supply DTFlow's crash-safe attempt or no-replay guarantees. API submission/progress/history documentation describes integration mechanics, not acceptance of our recovery contract ([official examples](https://github.com/Comfy-Org/docs/blob/main/development/comfyui-server/api-examples.mdx)).

### Additional static findings retained before stopping

- The extension registers routes on ComfyUI's PromptServer singleton, so it is host-dependent rather than a standalone workflow library ([routes](https://github.com/drawthingsai/draw-things-comfyui/blob/91fe91bc4eb849bc2cadde14e320d274499df45f/src/routes.py#L7-L13)). Its browser modules depend on Comfy/LiteGraph globals rather than Qt ([frontend integration](https://github.com/drawthingsai/draw-things-comfyui/blob/91fe91bc4eb849bc2cadde14e320d274499df45f/web/src/util.ts#L121-L139)).
- The inspected request does not opt into chunked outputs; response collection does not assemble chunkState fragments. This is an unsupported optional path, not proof that the default nonchunked path fails ([collection](https://github.com/drawthingsai/draw-things-comfyui/blob/91fe91bc4eb849bc2cadde14e320d274499df45f/src/draw_things.py#L185-L258)).
- Final tensor decoding trusts header dimensions/channels and has no DTFlow-equivalent bounded decompression budget in the reviewed helper; stronger preview checks do not establish final-output safety ([decoder](https://github.com/drawthingsai/draw-things-comfyui/blob/91fe91bc4eb849bc2cadde14e320d274499df45f/src/image_handlers.py#L41-L72)).
- The node fingerprint represents tensors by shape/dtype, not content. Comfy's graph caching also participates, so this alone does not prove same-shaped images are incorrectly cached. It must not become durable content identity ([fingerprinting](https://github.com/drawthingsai/draw-things-comfyui/blob/91fe91bc4eb849bc2cadde14e320d274499df45f/src/nodes.py#L35-L51)).
- Code-generation tooling fetches floating upstream content. Any selective reuse needs the committed generated files and their provenance pinned, not an unreviewed regeneration from current main ([generator](https://github.com/drawthingsai/draw-things-comfyui/blob/91fe91bc4eb849bc2cadde14e320d274499df45f/scripts/genCode.mjs#L5-L49)).

## 7. Dependencies, licensing and validation evidence

The extension declares torch, torchvision, numpy, Pillow, grpcio, FlatBuffers, protobuf, typing_extensions and fpzip. Its metadata has no `requires-python`, and the inspected tree has no Python lockfile ([metadata](https://github.com/drawthingsai/draw-things-comfyui/blob/91fe91bc4eb849bc2cadde14e320d274499df45f/pyproject.toml)). DTFlow currently uses Python 3.13, uv, a locked dependency set, grpclib and a deliberate NumPy 2.3.5 older-CPU override ([project configuration](../../pyproject.toml)). No compatible combined environment or packaged footprint was established.

The extension root [LICENSE](https://github.com/drawthingsai/draw-things-comfyui/blob/91fe91bc4eb849bc2cadde14e320d274499df45f/LICENSE) and Python metadata identify GPLv3, while [package.json](https://github.com/drawthingsai/draw-things-comfyui/blob/91fe91bc4eb849bc2cadde14e320d274499df45f/package.json) says ISC. DTFlow is GPL-3.0-only. This makes reuse worth investigating, but the metadata discrepancy, per-file notices, frontend assets and dependency distribution obligations need resolution before copying/shipping. This is a recorded licensing investigation, not legal clearance.

The extension's checked-in [validation workflow](https://github.com/drawthingsai/draw-things-comfyui/blob/91fe91bc4eb849bc2cadde14e320d274499df45f/.github/workflows/validate.yml) invokes `comfy-org/node-diff@main`; it is not a Python/Playwright runtime suite. The successful [registry publication run](https://github.com/drawthingsai/draw-things-comfyui/actions/runs/40138246165) does not establish generation acceptance. [Generation tests](https://github.com/drawthingsai/draw-things-comfyui/blob/91fe91bc4eb849bc2cadde14e320d274499df45f/tests/gen.spec.ts#L13-L87) are explicitly gated by RUN_GEN_TESTS and require running services/models; the img2img case is commented out with a Bridge Mode limitation. Other configuration/preview/frontend tests exist, but were read rather than executed. No current Windows, direct-cloud or two-stage compatibility claim follows.

## 8. Decision options

| Option | Value | Main cost/risk | Preliminary verdict |
| --- | --- | --- | --- |
| External ComfyUI + official extension unchanged | Existing graph editor/ecosystem; DT gRPC generation. | Bypasses DTFlow's execution authority and direct-cloud path; source safety mismatches above. | Useful comparison architecture; not an accepted DTFlow integration. |

Ordinary custom nodes remain a separate trust domain. | Strong candidate if Comfy workflow compatibility is the goal; not yet designed. |

| Fork/embed ComfyUI executor | Potential reuse of graph scheduling machinery. | Dependency extraction, maintenance fork and persistence/safety adaptation. | Do not choose without a bounded dependency/ownership feasibility study. |

## 9. Unfinished audit and next decision gate

The owner stopped further research before a complete review of transport codecs/chunk assembly, TLS/certificate and shared-secret behavior, arbitrary workflow/custom-node trust, route security, every frontend setting/migration, dependency closure/licence notices, and full Comfy execution/interrupt/cache semantics. No exploitability, exhaustive correctness or total implementation effort is asserted. A source finding about one path must not be generalized into acceptance or a claim that every backend shares the limitation.

Before implementation, choose **Comfy ecosystem compatibility** versus **DTFlow-native composable workflows**. Then define one minimal contract: generate A, consume a selected committed output in image operation B, retain both attempts and their input relationship, stop dependent admission on failure/uncertainty, and never regenerate A implicitly. Follow with bounded offline fixtures and separately authorized exact-backend/checkpoint live evidence; no such work was run here.

This report does not amend the scripting epic, close Tier B/C issues, change the [TanqueStudio parity matrix](../plans/tanquestudio-parity.md), or approve a replacement engine. It supplies an evidence-backed starting point for that decision while preserving existing work.

## 10. Owner decisions and current V1 findings (2026-11-04)

**Status and provenance:** This is a dated addendum to the preliminary audit above, not a retroactive claim that its upstream investigations were completed. Product behavior described as *agreed* below was chosen in the owner's subsequent discussion; a source observation is identified separately; implementation and compatibility remain unverified unless explicitly supported. [Issue #223](https://github.com/djebaz/dtflow/issues/223) tracks the work. The open choice in Section 9 and the option comparisons in Section 8 describe the **earlier** research state; the choice is now resolved as follows.

**Current state (2026-11-05):** owner decisions D1 to D8 are all taken (10.8). The detector downloads are owner-verified and pinned (10.3.1). The editor library is chosen: the nodeeditor-qtpy POC merged in [#228](https://github.com/djebaz/dtflow/pull/228) and the owner accepted it on Windows (10.8 step 6). Still open: the canonical reference fixture and contract (10.8 step 1), the pinned ComfyUI frontend release and round-trip behaviour (10.6 item 2), and real checkpoint support for inpaint/img2img (10.6 item 3). No workflow executor exists yet.

### 10.1 Direction: native workflows, ComfyUI-style saved files

- **Agreed:** Build DTFlow's own **visual node editor and execution system** on existing DTFlow services. Do not embed/fork the ComfyUI executor, make ComfyUI an execution dependency, or replace DTFlow's local/DT+ authorization and output ownership with the official extension.
- **Agreed:** Use the **ComfyUI saved/editor workflow JSON v1.0 structure** as the starting file contract: node identity/type, layout, typed links and per-node values. The [official ComfyUI workflow JSON schema](https://github.com/Comfy-Org/docs/blob/main/specs/workflow_json.mdx) is the format reference. It is **not** the separate ComfyUI API/prompt submission format. The precise DTFlow node catalogue, widget/value mapping and import/export semantics need a reviewed reference fixture and schema validation.
- **Agreed V1 compatibility rule:** DTFlow accepts imports **only when the entire file is understood and compatible** with its supported node/port/configuration subset. Reject the whole import with an actionable explanation for any unknown or unsupported node, edge, value or requirement; do not partially import, silently discard data, repair, infer an alternative operation or translate arbitrary Comfy graphs. Exports must follow the chosen saved-workflow structure.
- **Boundary:** A syntactically valid ComfyUI-format document with **DTFlow-specific node types** is **not thereby executable in stock ComfyUI**. Nor is every stock ComfyUI workflow importable into DTFlow. No cross-application execution/round-trip compatibility has been demonstrated.
- **Agreed:** Support long **acyclic** chains and branching graphs, without arbitrary two-, five- or ten-node ceilings. Use typed IMAGE and MASK ports, explicit dependencies and stable per-node/output identities. Resource and concurrency limits are separate practical concerns. The early two-step example was a test case, **not** a product cap.

### 10.2 Reference V1 dataflow and settings

The agreed reference is **generate image → detect face / create its mask → inpaint → img2img refinement → save image**. The generated image is passed to both the detector and the inpainting node; the detector's MASK and the original generated IMAGE converge on inpainting. The inpainting IMAGE is then passed to img2img refinement. This is a representative workflow, not a prescribed maximum length or mandatory node sequence.

```text
Generate [checkpoint A, LoRA set A]
   ├──────────── IMAGE ───────────────┐
   └── IMAGE → Face detection → MASK ─┤
                                     ▼
                          Inpaint [checkpoint B, LoRA set B]
                                     │ IMAGE
                                     ▼
                          Img2img refine [checkpoint C, LoRA set C]
                                     │ IMAGE
                                     ▼
                                  Save
```

- **Confirmed segmentation semantics and V1 selection:** The source [class labels and selectors](../../src/dtflow/services/person_selection.py) define `Face` and `Hair` as **separate SegFormer classes** (`face: (11,)`, `hair: (2,)`). **Agreed V1 choice:** the face-mask node exposes `mask_region` with `face_skin` (**Face skin only**, default) or `face_skin_and_hair` (**Face skin + hair**). The second option unions the selected person's `Face` and `Hair` pixels; unrelated body skin is not included. The bounding-box face detector (required for this node, D4) corrects/constrains `Face` versus `Skin` classifications, but does not detect or add hair. These are intended *workflow mask semantics*, not an already implemented node or proof of model accuracy. The owner-approved reference JSON is currently a conversation artifact, not yet a tracked repository fixture. The isolated POC ([#228](https://github.com/djebaz/dtflow/pull/228)) carries a stand-in, `tools/node_editor_poc/reference_workflow_v1.json`, with placeholder model ids; it is not the canonical fixture (10.8 step 1).
- **Critical dependency:** The mask **cannot be supplied upfront as though it matched a not-yet-generated image**. It is computed against the actual Step 1 output, after that output exists. Pre-uploaded or manually painted masks for an intermediate generated image are **not** the primary automated V1 path.
- **Agreed:** Each *generative/editing* node—including **inpainting**—has its **own** exact checkpoint, optional multiple LoRAs with individual weights, prompt/negative prompt, seed, steps, guidance, sampler and relevant dimensions/strength/denoising options where supported. These are node-owned settings, not a global workflow model/LoRA set. Validate the exact backend/checkpoint/operation combination instead of assuming compatibility.
- **Agreed:** Carry actual image/mask data and lineage between operations; keep saved outputs inspectable and record the relevant effective settings. Image/mask alignment and transformations matter, given the fitting/polarity differences recorded in Section 4.
- **Source boundary:** Current DTFlow has image preparation, img2img/inpaint dispatch paths and local person-selection services; these are **not evidence** that a native graph executor, arbitrary img2img chain or every model/LoRA/backend combination already works. Retain existing image-operation evidence/permit constraints and verify advertised combinations separately.

### 10.3 Local automatic mask detection and model provisioning

- **Agreed:** Local analysis is acceptable even when generative nodes run on **DT+ Cloud**. Prefer reusing DTFlow's existing CPU-only person/face/body/clothing-selection implementation rather than adding a second detector engine or running ComfyUI.
- **Current DTFlow source observation:** [`services/person_selection.py`](../../src/dtflow/services/person_selection.py) operates on owner-selected ONNX model files. [`persistence/person_models.py`](../../src/dtflow/persistence/person_models.py) stores local paths and SHA-256 hashes, explicitly stating that model weights are **not bundled or downloaded**. The release notes describe local person/body-part/clothing/optional face detection. The equivalent JavaScript [detection hooks](../../src/dtflow/scripting/hooks.py) are still marked **planned** under [#117](https://github.com/djebaz/dtflow/issues/117); do not equate hook declarations with an end-to-end script or workflow implementation.
- **Agreed V1 enhancement shared with Generate:** Provide an approved catalogue of supported detection models and a common mechanism to detect missing local weights, offer/download them from trusted, pinned sources, verify integrity, install/reuse them locally and automatically **load** them when needed. Preserve existing user-selected local model paths. Do **not** invent model URLs, hashes, licences or file sizes. The chosen files, pinned revisions, hashes and sizes are in 10.3.1 (D8).
- **Before a workflow starts:** Preflight required detection models and other required assets, then present **one confirmation** for missing-model downloads, showing each model's licence (D7). Do not begin potentially billable DT+ generation before required local detectors are ready. During ordinary execution, model loading is automatic and no download prompt should interrupt the run.
- **In Generate's native detection feature:** Offer the same missing-model **download/install** action, rather than requiring the user to source ONNX files manually. The common provisioning service should not diverge between Generate and Workflows.
- User-confirmed downloads **before execution** are in scope; silent network downloads mid-workflow, installing arbitrary untrusted models and an extensive model-management platform are not.

#### 10.3.1 Candidate public ONNX downloads and anonymous-access status (2026-11-04)

Owner decision: use **the SHA-256 of the exact selected public download artifact**, not necessarily the checksum of a user's existing local ONNX. ### 10.4 Runtime behavior and exceptional human decision

- **Agreed:** V1 is automatic under normal conditions. No ordinary mid-run manual mask painting, upload or other interactive authoring node.
- **Agreed detection exception (branch scope explicitly confirmed by owner, 2026-11-05):** If face/person/body-part detection returns no suitable target, **pause only the affected image branch** and show an overlay such as **“No face detected. Continue anyway?”**, identifying the branch. **Continue** bypasses that branch's mask-dependent inpainting and forwards its unchanged source image only through connections where that substitution is type/semantically valid, with a clear skipped-step indication. **Stop** ends only that branch and retains already produced outputs. If nobody responds, that branch **stays paused**, issuing no further remote generation requests for it. Sibling branches keep running; this is not a workflow-wide pause or stop.
- This is a **small exceptional pause/continue requirement**, not a general interactive workflow engine. Failure/uncertainty must be reported against the appropriate node; remote ambiguous outcomes must not be silently replayed.
- **Deferred:** Rich selective re-execution, granular recovery/caching, general interactive pauses for drawing/uploading masks, and extensive conditional logic. Future manual steps should be possible conceptually without being built in V1.

### 10.7 Code-checked constraints for V1 (review of this addendum, 2026-11-04)

**Scope of this check:** static reading of DTFlow `main` at `9dd2506` and of the official workflow schema page; no application launch, model load, download, inference, generation or test run. Each item below is a **current-code constraint** that a V1 behaviour in #223 must meet or that needs an owner decision (10.8). None of it is a new product decision.

**Workflow file format (official schema page, read 2026-11-04).** The published [v1.0 JSON Schema](https://github.com/Comfy-Org/docs/blob/main/specs/workflow_json.mdx) requires top-level `version` (const `1`), `state` (`lastNodeId`, `lastLinkId`, `lastRerouteId`, `lastGroupid`) and `nodes`; `links`, `groups`, `reroutes`, `config`, `extra` and `models` are optional. A node requires `id`, `type`, `pos`, `size`, `flags`, `order`, `mode` and `properties`; `inputs`/`outputs` items require `name` and `type`; `widgets_values` may be an **array or an object**. In v1.0, links are **objects** (`id`, `origin_id`, `origin_slot`, `target_id`, `target_slot`, `type`, optional `parentId`), not the positional arrays of the older 0.4 format (the 0.4 page was not read here). `additionalProperties: true` is allowed almost everywhere, and `extra` is the extension slot. The page says nothing about how the ComfyUI editor treats unknown node types, so the ComfyUI behaviour on DTFlow node types stays unverified (10.6 item 2). Consequences for the DTFlow contract:

- The schema is **permissive**, so "valid against the official schema" is not enough for DTFlow's strict import. DTFlow needs its own stricter check on top: known `type` values only, known `widgets_values` keys only, no unknown keys in DTFlow-owned objects, and link `type` equal on both ends.
- **`widgets_values` form: owner decision D1 (2026-11-04): export an array**, the conventional positional form of ComfyUI's ordinary serializer. The schema accepts array or object equally, so neither is more compliant, and an array does not make DTFlow nodes loadable or executable in stock ComfyUI. Rules: (1) each supported node type has a fixed parameter order per DTFlow contract version; (2) DTFlow uses named parameter objects internally and converts to arrays only when reading/writing the file; (3) the file order is independent of the inspector/widget display order; (4) import applies strict version, length, type, range and semantic validation, because length and type alone would not catch two swapped numeric parameters; (5) an unsupported or unknown contract version is rejected, never guessed or silently migrated. A contract change bumps the DTFlow version in `extra.dtflow`, not ComfyUI's top-level `version`.
- **Pin a target ComfyUI frontend version for compatibility claims.** Per the owner's reading of upstream (not re-checked here), serialization depends on widget configuration and lifecycle, some nodes omit `widgets_values`, and current `ComfyUI_frontend` `main` also writes a `widgets_values_named` companion ([`LGraphNode.ts`](https://github.com/Comfy-Org/ComfyUI_frontend/blob/main/src/lib/litegraph/src/LGraphNode.ts), [`WIDGET_SERIALIZATION.md`](https://github.com/Comfy-Org/ComfyUI_frontend/blob/main/docs/WIDGET_SERIALIZATION.md)). Pin one frontend release, record how the strict importer treats `widgets_values_named` and missing `widgets_values` for that release, and keep unknown-node save/reopen preservation as the separate round-trip check (10.6 item 2).
- `extra.dtflow` carries the DTFlow contract version (for example `{"schema": "dtflow-workflow", "version": 1}`). An import with a missing or newer DTFlow version is rejected whole, matching the existing "newer schema is rejected" rule in [`person_models.py`](../../src/dtflow/persistence/person_models.py).
- Groups, reroutes, subgraphs and `models` are not needed for the reference workflow. V1 can reject files that use them instead of half-supporting them (consistent with the strict import rule).

**Image operations need a permit or a per-run probe consent.** [`generate_image_once`](../../src/dtflow/services/session.py) refuses any img2img/inpaint without an exact-scope `ImageOperationPermit` (backend, endpoint, checkpoint, operation). No permits ship; the Generate editor creates an `owner_probe` permit and passes `allow_image_probe=True` only after the user confirms that exact scope ([`generation_page.py` `_generate_edit`](../../src/dtflow/ui/generation_page.py)). A workflow's inpaint and refine nodes hit the same gate. **Owner decision D2 (2026-11-04): no extra confirmation.** Building and starting the workflow is the owner's consent; each image node creates its own exact-scope `owner_probe` permit and runs with `allow_image_probe=True`, as the Generate editor does. If the checkpoint does not support the operation, that node simply fails with the backend's reason, like any other node failure. The preflight confirmation of 10.3 stays limited to missing-model downloads.

**Image operations are single-output.** The same entry refuses a base request unless `batch_size * batch_count == 1`: one source image in, one result out. **Owner decision D3 (2026-11-04): fan out.** When a node produces several images (batch size/count > 1), every downstream node runs **once per image**, each as its own single-output image operation. So batch 4 on Generate gives 4 masks, 4 inpaints and 4 refines, each with its own lineage. Consequences for the contract: each image carries a branch index (`generate[2] → inpaint[2] → refine[2]`) recorded in provenance; batches compound (batch 4 feeding a node with batch 2 gives 8 downstream results), so validation shows the total number of generations before the run; the no-detection pause applies **per branch** (Continue/Stop for that image, other branches keep running); a failed branch does not stop sibling branches. A converging node (Inpaint takes IMAGE and MASK) pairs inputs from the **same** branch, never a cross product.

**Which bytes are handed on.** An image operation saves the untouched provider `raw-1.png` and a separate application-owned final, which is the **source-sized composite** when `preserve_outside` is on ([`image_artifacts.save_image_artifacts`](../../src/dtflow/services/image_artifacts.py), [`composite_image`](../../src/dtflow/services/image_preparation.py)). `GenerationOutcome.final_image` is documented as **display only**. The workflow should hand the next node the **saved final artifact** from `output_paths`, never the display bytes and never the raw provider image. Record the parent image path and effective settings as provenance; attempt ids stay in diagnostics, not in the UI (10.9). Because the composite keeps source size, the refine node receives the generate node's dimensions, not the inpaint target's; that is the expected behaviour but should be stated in the node contract.

**Mask handoff already fits the existing preparation path.** [`apply_selection`](../../src/dtflow/services/person_selection.py) returns a source-sized 0/255 mask; [`prepare_image_bytes(source, w, h, mask_bytes=..., grow=..., feather=...)`](../../src/dtflow/services/image_preparation.py) takes in-memory source and mask bytes, requires the mask to match the source size, thresholds luminance >127 and fits both jointly. No new mask format is needed. The inpaint node should expose the same `grow`, `feather`, `strength` and `preserve_outside` the editor already passes, so a workflow inpaint and a manual inpaint use identical preparation.

**What the face-mask node really depends on** (expands 10.6 item 1):

- `segmentation` (YOLO26 end2end) is **always required**; it finds up to `MAX_PEOPLE = 10` people, strongest first.
- The **clothes model (SegFormer) is required** for `face` and `hair`. Without it, `PersonLayers.layer("face")` returns `None`. So both `mask_region` values need SegFormer, not only a "face detector".
- In current code the **faces model is optional**, and it changes what `face_skin` means. SegFormer paints neck and chest as `Face`; only when face boxes are found does `_cap_face` relabel those far-from-face pixels as synthetic `skin`. So without the faces model, `face_skin` can include neck/chest. That contradicts the issue's "Face skin only" wording unless the faces model is present. Decision D4. **Owner decision D4 (2026-11-04): the faces model is required for this node**; the auto-download provides it.
- **A face detector that finds nothing does not empty the mask.** `analyze_people` only applies `_cap_face` when `face_boxes` is non-empty, so zero detected faces leaves every SegFormer `Face` pixel in place. The "No face detected" pause must be defined explicitly: the selected person's chosen-region mask is empty, **or** no person was found, **or** (when the faces model is configured) it returned zero boxes. Decision D4 covers which of these trigger the pause. **D4 decided:** all three conditions trigger the pause.
- **Several people.** Nothing headless picks a person today; the editor lets the user click one. The node needs a `person` parameter. Natural options: `strongest` (index 1, the highest YOLO score), `largest_face` (most face pixels), or `all` (union of every person's region). Decision D5. **Owner decision D5 (2026-11-04): `strongest` (default) or `all`.**

**Model files, download and the stored-model schema.**

- The ONNX contract checks are strict and decide which public files can be catalogued. `_segmentation_session` needs one `[1,3,640,640]` input, outputs `[1,300,38]` and `[1,32,160,160]`, and metadata `task=segment`, `end2end=true` and `names[0]=person`. `_faces_session` needs a 320×320 input, Ultralytics metadata `task=detect` with contiguous `names`, at least one `FACE_*` class, and one `[1, 4+len(names), N]` output. `_clothes_session` needs one NCHW float input and an `[N,18,h,w]` output. All files must be ≤ 256 MiB (`MAX_MODEL_BYTES`); the YOLO26 (10.7 MB) and SegFormer (110 MB) candidates fit; so does the chosen NudeNet file (11.59 MiB).
- **Faces model contract: owner-checked (2026-11-04).** The owner reports that the NudeNet `320n.onnx` file has been checked and is accepted by DTFlow's faces contract (`_faces_session`: Ultralytics `task=detect`, `FACE_*` names, 320×320 input). D8 ships that `zhangsongbo365` file (10.3.1). The owner's `classify_models` run also accepted the official `yolo26n-seg.onnx` and both SegFormer files.
- `person_models.json` is schema 1 and stores only `path` + `sha256` per role, and a newer schema is rejected rather than rewritten. A catalogue download can stay inside that schema: save the file to a DTFlow-managed folder (for example `<state>/models/person/<sha256>.onnx`), then record it as an ordinary `ModelRef`. That needs **no schema bump**, keeps older builds able to read the file, and preserves user-chosen paths. The catalogue itself (URL, pinned revision, SHA-256, size, licence) can be a small read-only data file shipped with the app.
- The existing readiness check `model_issue` only opens each file; full SHA-256 checking happens at load. Workflow preflight can reuse `model_issues` for "is it present and readable", then hash once when the download completes.

**Execution home: reuse the Scripts queue pattern.** Scripts already run as **one queue item with child steps** (queue `kind`, store `SCHEMA_VERSION = 7` with "script kind" and "script child slots"; design in [`2026-11-02-script-queue-item.md`](../plans/2026-11-02-script-queue-item.md)). A workflow run has the same shape: one run, several durably linked generations, shared backend reservations, pause/cancel, no replay after a crash. Adding a `workflow` kind means another one-way store bump (7 → 8). The alternative, a runner outside the queue, would duplicate admission, ownership and Stop. Decision D6. **Owner decision D6 (2026-11-04): one queue item of a `workflow` kind.**

**Progress feedback.** The activity bar already shows a `stage`/`wide` text per row ([`activity_bar.py`](../../src/dtflow/ui/activity_bar.py), [`activity_strip.py`](../../src/dtflow/ui/activity_strip.py)), and generation emits `preparing` events with stages (`validating_image_inputs`, `binding_assets`, `opening_session`, `session_ready`). Person analysis does not report stages today: the editor runs it as one `_task("Find people", ...)`. The labels in #223 (`Loading model`, `Detecting people`, `Analysing clothing`) need a small stage callback in `analyze_people` (around `_verified_session`, `_instances` and `_clothes_layers`); downloads need a byte-count callback. Both can reuse the existing `stage` text, with no new progress widget.

**Scripting hooks are still planned.** `detectFaces`, `createBodyMask` and related hooks are `PLANNED` under #117, and `pipeline.run()` still rejects `mask` (#116). Workflows should not wait for them; the node and the hooks should call the same new headless helper (10.8 step 3), so #117 gets it for free.

### 10.9 Alignment with the #220 simplification direction (2026-11-04)

[#220](https://github.com/djebaz/dtflow/issues/220) asks for proportionate safeguards, easy Retry, a small bounded automatic retry, plain outcome wording, no attempt internals in the UI, and no new elaborate recovery. #220 is a direction, not an implemented change, so workflows must work with today's services. They should also avoid **adding** defensive machinery that #220 would later remove. Reviewing 10.7 and 10.8 against it:

**Kept, because they are product requirements and not defensive extras:** strict whole-file import (#223 asks for it explicitly); never showing an unknown outcome as success or failure; preserving saved images and core provenance; the no-detection pause (#223); SHA-256 checks on downloaded weights. The SHA check is a single hash at install, and loading already re-hashes.

**Simplified in this plan:**

- **Image-operation permits.** D2 already turns the permit into an automatic, invisible owner probe per node. Workflows build nothing on top of permits. The existing consent gate is not sacred: D2 authorizes **simplifying** that path for workflows (for example, one direct call with probing allowed) rather than adding replacement confirmations or a permit framework.
- **Handoff and lineage.** Use the saved final file from `output_paths` directly, without a second cross-check against the attempt record (the attempt store already committed it). Provenance means parent image, node settings, checkpoint/LoRAs/seed. Attempt ids go only to diagnostics.
- **Run storage.** D6 reuses the Scripts **queue item**, but not a second store: the workflow file snapshot, per-node status and output paths live in the item's own record. No `ScriptRunStore`-style database, child-slot table or reconcile logic beyond what the queue already does. After a crash, the item is marked interrupted and the user presses **Run again** or **Retry**; nothing resumes automatically and there is no selective recovery (#223 and #220 agree).
- **Validation.** "Range and semantic" checks in D1 reuse the existing request validation (`ResolvedGenerationRequest`, LoRA preflight) for each node, rather than a second workflow-specific validator. The workflow layer adds only graph checks (types, cycles, fan-out pairing) and the contract version and length.
- **Readiness checks.** Preflight uses `model_issues` once for presence and readability. Nothing else is checked again mid-run.

**Retry and failures, per #220:**

- Each failed or unknown node shows the plain cause (preserving DT+ provider, auth and quota text, never "output missing") and a **Retry** button that reruns that node with its original settings, then continues its downstream branch. No attempt ids, recovery states or extra confirmation.
- An automatic retry, if #220 adopts one, uses the **same** small fixed cap as Generate and Queues; workflows do not define their own policy. Definitive auth, permission or quota refusals are not retried automatically.
- **Loop guard, made concrete by fan-out (D3).** Fan-out can multiply generations, so the guard is one number. Before the run, show the total generations the graph will submit. During the run, stop the workflow if submissions exceed that total plus the automatic-retry allowance. That single counter is the bounded-behaviour criterion of #220 for workflows. It needs no classifier and no extra UI.
- A failed or unknown branch stops only its own downstream nodes; sibling branches continue; the run ends **partial** with per-node outcomes.

**Practical rule (owner, 2026-11-04):** reuse what simplifies; remove what adds friction without protecting a meaningful outcome. #220 guides #223 throughout implementation and is **not** a prerequisite project. Reuse queue and output services where useful, without copying every Scripts lifecycle abstraction. Fan-out lineage means simple branch/output references, not a recovery system.

**Changed risk.** The 7 → 8 store bump (D6) stays, but should add only the `workflow` kind value. Workflow state lives in the item record, so no new tables are needed.
