# ControlNet Depth and HiRes resize investigation (#637)

Date: 2026-11-27. DTFlow main inspected at [1c5ea66](https://github.com/djebaz/dtflow/commit/1c5ea661058424259776bf7ae2b76585482060c9); observed Windows revision cd5db92. No live generation, tests or renders executed by the agent.

## Finding

A width/height argument reversal is confirmed in public upstream source; its role in the reported DT+ failures is not confirmed. The current upstream main retrieved for this investigation is exactly the pinned [cb2d4c61](https://github.com/drawthingsai/draw-things-community/commit/cb2d4c61d1b58816ce1843481e74293a240e5bf4). No fix is present in that revision. The deployed DT+ revision is unknown.

- [First pass](https://github.com/drawthingsai/draw-things-community/blob/cb2d4c61d1b58816ce1843481e74293a240e5bf4/Libraries/LocalImageGenerator/Sources/LocalImageGenerator.swift#L4777-L4805): both depth and custom tensors use height ratio as widthScale and width ratio as heightScale. Second-pass resizing has the same discrepancy ([5152–5176](https://github.com/drawthingsai/draw-things-community/blob/cb2d4c61d1b58816ce1843481e74293a240e5bf4/Libraries/LocalImageGenerator/Sources/LocalImageGenerator.swift#L5152-L5176)). The same reversed arguments are confirmed at 6150–6151, 6164–6165, 7593–7594, 7700–7701, 8631–8632 and 8688–8689. In contrast, the ordinary first-pass image resize at 4663–4667 uses the correct order.
- The upstream [Package.resolved](https://github.com/drawthingsai/draw-things-community/blob/cb2d4c61d1b58816ce1843481e74293a240e5bf4/Package.resolved) pins s4nnc 9c912b34 and ccv 72be6f75. [Swift Upsample](https://github.com/liuliu/s4nnc/blob/9c912b34f8242deeccd5d78fe28a140c0137b2ff/nnc/ModelAddons.swift#L1597-L1602) forwards width then height; [ccv model](https://github.com/liuliu/ccv/blob/72be6f75b62de7f504e38bf5fa6589952f7a68c4/lib/nnc/ccv_cnnp_model_addons.c#L4061-L4096) preserves them; [ccv output shape inference](https://github.com/liuliu/ccv/blob/72be6f75b62de7f504e38bf5fa6589952f7a68c4/lib/nnc/cmd/upsample/ccv_nnc_upsample.c#L24-L34) applies height to NHWC dimension 1 and width to dimension 2, rounding to nearest integer.
- Static data flow shows the second pass starts from the original full-sized hint, not the first-pass resized hint; its guard bypasses Upsample if the original matches the target. Pre-resizing to the first-pass size merely moves the mismatch to pass 2: 384×512 → 704×1024 would predict 768×939 with reversed scales. Neither guard behavior nor resulting shapes were observed at runtime.
- Custom hints require a distinction: the resized firstPassCustomImage/secondPassCustomImage feed encodeImageCond at 4807–4812 and 5178–5183, but generateInjectedControls at 4845–4852 and 5204–5211 receives the original custom tensor. The customRGB helper at 2739–2779 uses correctly ordered scales (or aspect fitting) and can fit that original per pass. Native Depth instead receives firstPassDepthImage/secondPassDepthImage, and its branch replicates the one-channel tensor without a corrective resize. Thus the custom resize defect is real, but it does not establish that Pose, Canny or Segmentation control injection is affected in the same way as Depth; any impact through image conditioning depends on the selected modifier/model.

## DTFlow request review

Current wire.py uses native depth transport even with HiRes, with official Depth checkpoints using Unspecified input override (native modifier), and union Depth using Depth override. The retained prepared input is fitted at final size. image_inputs.py takes one grayscale channel from the RGB map and validates the 68-byte CCV header, dimensions, channel count and payload length; the SDK [v0.4.0 ImageBuffer.to_tensor](https://github.com/kcjerrell/drawthings-py/blob/v0.4.0/src/drawthings_py/image/image_buffer.py) normalizes uint8 to float16 [-1,1] in HWC order. The native upstream [Depth branch](https://github.com/drawthingsai/draw-things-community/blob/cb2d4c61d1b58816ce1843481e74293a240e5bf4/Libraries/LocalImageGenerator/Sources/LocalImageGenerator.swift#L2874-L2905) expects one channel and applies 0.5*(depth+1) when adjustRGB is true, then replicates it to RGB. The request references tensor bytes by SHA-256 and carries them in contents. The final width/height and effective first-pass fields are independently decoded and verified by wire.py; core/advanced.py snaps each axis to 64 pixels, halves up, unless explicitly supplied. No incorrect width/height exchange was found in these inspected DTFlow paths. This is static review, not captured actual wire bytes.

The three failing attempts in #637 are not available as retained local request records in the repository. The supplied issue summary reports 704×1024, Realistic Vision v5.1 Q6P/Q8P, 14 steps, DPM++ 2M Karras, no LoRAs; exact control checkpoint/type, seed, guidance range, map and effective first-pass fields for a specific failure remain unknown. The issue signposts identify two failed and one successful HiRes attempts, and all three identifiable single-pass attempts succeeded; the final failed attempt is unclassified. A deterministic shape mismatch at identical effective geometry would be expected to recur, so the successful HiRes attempt is evidence against attributing every failure to the swap without knowing its first-pass settings and control path. Two no-final-output and one transport-inactive failure do not establish a provider crash or quota exhaustion. AC-1 remains incomplete until sanitized request metadata or owner reproduction is available.

## Resolution

Do not change DTFlow request construction or admission: no silent dimension adjustment, control substitution, retry or blocking. Offer the user the optional workaround of choosing proportional final/first-pass sizes, or turning HiRes off. For final W×H and first-pass w×h, the exact general condition is w×H = h×W, with both first-pass sides valid multiples of 64 and at least 128. For integer factor k, final sides divisible by 64k are a sufficient rule when the resulting first pass meets the minimum (at 2×, both final sides divisible by 128). For noninteger factors or explicit first-pass sizes, check the actual displayed dimensions rather than relying on divisibility alone. At 704×1024 the reduced ratio is 11:16; the smallest positive proportional pair on the 64-pixel grid is already 704×1024, so no smaller proportional first pass exists. Choose another final size, such as 768×1024 → 384×512 at factor 2, or disable HiRes. Neither is guaranteed to resolve cloud failures. Existing exact saved settings and Retry stay intact.

## Draft upstream report (not submitted)

Title: HiRes depth and custom hint resizing swaps width and height scales for unequal axis ratios

At cb2d4c61, LocalImageGenerator.swift lines 4777–4805 and 5152–5176 compute widthScale from height and heightScale from width, whereas pinned s4nnc/ccv applies them to their named NHWC axes. A full-sized 704×1024 depth or custom map with first pass 384×512 should resize to 384×512 but shape inference predicts 352×559. Equal-axis ratios hide the discrepancy. The same swap is present at 6150, 6164, 7593, 7700, 8631 and 8688. The customRGB helper uses correct scales and receives the original custom tensor for control injection, so the custom image-conditioning discrepancy should not be conflated with native Depth injection. Please check these resize sites; use widthScale = targetWidth/inputWidth and heightScale = targetHeight/inputHeight, retaining the existing mode and guards. A non-square unequal-ratio fixture would distinguish the correction. DT+ deployment and runtime causality remain unverified; observed client errors were missing final output and transport inactivity, not a confirmed server assertion. The source links and reproduction matrix above are the evidence. No private logs, credentials, prompts or image payloads are included.

Do not file externally without owner approval.
